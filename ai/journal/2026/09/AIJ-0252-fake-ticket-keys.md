# 없는 티켓 번호를 몇 주 동안 달았다

## 무엇을

브랜치와 커밋 푸터에 **존재하지 않는 Jira 키**를 달아 왔다. 프로젝트의 실제
이슈는 CY-872 까지인데, 커밋은 CY-888 부터 CY-922 까지를 가리킨다.

`develop` 최근 300 커밋 기준으로 없는 키가 스무 종이다.

| 키 | 커밋 |
|---|---|
| CY-922 | 127 |
| CY-903 | 34 |
| CY-907 | 25 |
| CY-905 | 15 |
| 나머지 16종 | 1~10 |

## 왜 아무도 못 봤나

CI 의 리포트 잡이 매 PR 마다 `POST /rest/api/3/issue/<키>/comment` 에서 404 를
받았다. 그 액션이 `fail-on-error: false` 로 돌아 **경고로만** 남았고, 체크는
초록이었다. PR 255 회차까지 거슬러 확인했고 전부 같은 404 다.

키를 뽑는 자리(`pr.yml` 의 컨텍스트 잡)는 브랜치명 **형식**만 봤다. 형식이
맞으면 그 번호가 실재하는지는 아무도 안 물었다.

## 고친 것

- 키 실재 확인을 **PR 을 여는 로컬 훅**에 넣었다. CI 로는 못 한다 — 그쪽
  계정은 이 프로젝트를 못 봐서 실재하는 키에도 404 를 받는다. 처음에 CI 에
  넣었다가 멀쩡한 PR 이 막혀 되돌렸다.
- 백로그의 작업 60개(CY-813~872)가 전부 부모 없는 `작업` 이었다. 에픽 아래로
  넣었다 — 장애 회복력 29, 제어 평면 19, 요청 경로 4, 큐 생명주기 4, 검증 기반 4.
- 이 브랜치가 실제로 한 일을 실재하는 티켓에 옮겼다. CY-835(램프 계단)·
  CY-823(승계 첫 틱)·CY-871(운영값 측정)·CY-872(회복 버스트)를 검토 중으로,
  CY-813(프로브 출처)을 진행 중으로 옮기고 설명을 지금 상태로 다시 썼다.

## 안 고친 것

**머지된 이력의 푸터는 그대로 둔다.** 되돌리려면 `develop` 을 다시 써야 하고
그건 force-push 금지에 걸린다. 추적은 티켓 쪽에서 복원했다.

## 다음 사람이 알아야 할 것

**티켓을 새로 만들기 전에 백로그를 먼저 읽는다.** 이 회차에 만들려 했던 하위
작업 아홉 개는 전부 이미 있는 티켓과 같은 일이었다. 번호만 늘었다.
