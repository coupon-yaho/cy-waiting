# 레디스가 느린 날 배분 발행이 절반으로 줄었다

## 무엇을

티켓은 명령 상한 아래 지연 300ms 에서 리더는 유지되는데 발행이 멎는다고 적었다. 루프를 켠 시나리오로 재 보니
**300ms 에서는 리더부터 잃었다** — CY-847 에서 사실로 받아들인 연장 밴드다. 리더가 사는 가장 높은 지연대인
200ms(명령 상한의 0.4 배)로 옮겨 쟀다. 8초에 서로 다른 발행이 넷이었다. 한 번이라도 오르면 통과로 두던 판정은
이것을 초록으로 넘겼다.

## 원인 셋

1. **읽기가 차례로 기다렸다.** 틱은 가용량 읽기 → 운영값 읽기 → 회차 순이었다. 읽기마다 틱의 4분의 1 시한이라
   느린 날 틱의 절반을 먹었다
2. **쿠폰별 적용이 차례로 나갔다.** 왕복이 쿠폰 수만큼 쌓였다
3. **스케줄러가 완료 뒤 한 틱을 통째로 쉬었다.** 회차가 1초 걸리면 주기가 2초가 된다. 1·2 를 고쳐도 발행이 그대로
   넷이었던 이유가 이것이었다 — 로그에 배분 실패는 두 번뿐이었다

## 고친 것

- 가용량·운영값 읽기를 동시에 돌리고, 회차는 그 읽기와 **동시에** 수요를 읽는다. 나누기는 두 읽기가 끝난 뒤라
  "운영값을 먼저 읽고 배분한다" 는 그대로다
- 쿠폰별 적용을 동시에 보낸다. **이중 방어 하나를 걷었다** — 순차일 때는 쿠폰마다 쓰기 직전에 리더를 다시 물었다.
  옛 임기의 쓰기는 적용 스크립트의 펜스가 막는다(`옛_임기의_적용은_안_들인다`). 사용자와 정해 펜스에 맡겼다. 순차
  재확인 시험은 동기로 잃는 경우만 남는다
- 쉬는 시간을 틱에서 직전 회차 시간을 뺀 만큼으로 줄였다. 밀린 틱은 만회하지 않고 최소 4분의 1은 쉰다 — 기록된
  근거인 "느린 구간에 틱이 쌓였다 한꺼번에 터지지 않게" 와 "끝나야 다음을 잡는다" 는 지킨다. 옛 시험이 완료 뒤 한 틱
  통째를 못 박고 있어 시작 간격을 직접 재는 시험 둘로 바꿨다
- 회차 시간은 끝나는 신호 **전에** 적는다. 끝난 뒤(`doFinally`)에 적었더니 반복이 다음 지연을 먼저 계산해 옛 값을 썼다

## 어떻게 검증했나

- 200ms 지연에서 발행: 넷 → 읽기 동시만 넷 → 적용 동시·간격 맞춤 여섯 → 수요 동시까지 일곱(두 번 연속)
- 판정 한계를 여섯에 둔다

## 남은 것

- 틱이 1초에 왕복이 다섯쯤이라 지연이 조금만 더 커도 한계에 닿는다. 연결 하나에 명령을 섞어 보내 배분 명령 뒤에 줄
  선 연장 명령이 시도 상한을 넘는 것도 관측됐다(200ms 에서 한 번 "리더 확인 실패"). 리더 명령을 따로 떼는 것은 안 했다
- 느린 레디스를 전보다 자주 두드린다 — 주기가 2초에서 약 1.1초로 줄었다
