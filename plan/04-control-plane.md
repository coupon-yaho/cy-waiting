# Phase 4 — Control Plane

> 스냅샷 갱신, 가용량 수집, 리더 선출, 배분 스케줄러.
> **요청 경로가 아니라 배경 루프**다. 여기가 느려지거나 멎으면 데이터 플레인이
> 낡은 판정을 하게 되므로, 낡음을 두 종류로 구분해 다루는 것이 핵심이다.

**선행**: Phase 2, Phase 3 · **상세 수준**: 제목 + 근거 (진입 시 승격)

---

## Goal

> **배분이 리더 하나에서만 돌고, 낡음을 두 종류로 구분해 다룬다.**
> 노드가 늘거나 백엔드가 돌아와도 크레딧 초과 배분이 생기지 않는다.

| 통과 수치 | |
|---|---|
| 10노드 시뮬레이션에서 배분 실행 | **정확히 1대** |
| 리더 강제 종료 후 승계 | **≤ 3틱**, 크레딧 중복 ≤ 1틱분 |
| 틱 지연 p99 (20,000 부하 중) | **< 100ms** |
| 노드 증가 시 총 통과가 `globalCredit` 초과 | **0건** (F5) |
| `dataStale` 시 503 을 내는 노드 | **0대** (전원 이탈 방지) |

**낡음을 두 종류로 나누는 것이 이 페이즈의 핵심이다.** 섞으면 스케줄러 장애가
전 게이트웨이 동시 이탈로 번져 100% 장애가 된다.

### 타이밍 — 게이트가 판정할 수 있으려면 먼저 정해야 한다

위 수치는 전부 **틱**과 **락 수명**에 걸려 있다. 값이 없으면 절대 시간으로
환산할 수 없어 판정이 불가능하다.

**발행 주기와 갱신 주기는 다르다.** 스케줄러가 스냅샷을 내는 주기와, 각 노드가
그것을 받아 가는 주기가 별개다. 둘의 합이 판정 재료의 낡음이다.

| 설정 | 기본값 | 관계 |
|---|---|---|
| `scheduler.tick` | **1s** | 스냅샷 발행·배분 주기. **문서에서 "틱"은 이것** |
| `snapshot.fetch` | **500ms** | 각 노드가 스냅샷을 받아 가는 주기 |
| → **스냅샷 낡음** | **≤ 1.5s** | 두 주기의 합. R3 매진 종결의 안전 근거가 이 값에 걸려 있다 ([07](07-queue-lifecycle.md) 3.1 · [00](00-requirements.md) R3) |
| `leader.lease` | **2s** | **= 2틱.** 리더가 죽으면 이만큼 뒤 락이 만료된다 |
| `leader.renew` | **500ms** | **= lease / 4.** 연장을 세 번 놓쳐도 락을 잃지 않는다 |
| `data-stale-after` | **5s** | `dataStale` 판정 임계 (3절) |

**`lease = 2틱` 이라 승계는 2틱에 끝난다.** `G4.2` 의 상한은 3틱이므로 **1틱이
여유**다 — 상한에 딱 맞추면 측정 오차 한 번에 게이트가 깨진다.

`renew` 를 `lease` 보다 충분히 짧게 두는 것은 임차 갱신의 통상 설계다
(Kubernetes `LeaseDuration` / `RenewDeadline` 과 같은 관계). 한 번의 GC 나 네트워크
흔들림으로 리더가 바뀌면 평활화 상태가 매번 초기화되어 진동한다.

**C10(STW 3초)은 `lease` 2초를 넘으므로 리더가 반드시 교체된다.** 의도한 동작이고,
평활화 상태는 `F9`(4.6.7)가 이월한다. 경계값이 겹치지 않게 둔 이유이기도 하다 —
`lease` 를 3초로 잡았으면 C10 의 결과가 실행마다 달라진다.

승계 2초는 `data-stale-after` 5초보다 충분히 짧다. **리더 교체가 `dataStale` 로
번지지 않는다**는 뜻이고, 이게 두 값을 따로 두는 이유다.

### 배포 형태 — 붙여 두고, 재보고 나서 뗀다

바이너리는 하나다. `waiting.scheduler.enabled` 토글로 배분 루프를 켠다.

| | 설정 | 무엇 |
|---|---|---|
| **Phase 4 기본** | 게이트웨이 전 노드 `scheduler.enabled=true` | 능력은 전부가 갖고 **리더 1대만 배분 루프를 돈다** |
| 분리 후 | 게이트웨이 `false` · 스케줄러 노드 `true` + `gateway.enabled=false` | 배포 단위 둘 |

**"모든 노드가 스케줄러를 갖는다"가 위험한 것은 전부가 각자 배분할 때**이고,
그건 리더 선출이 막는다 (`G4.1` — 10노드에서 배분은 정확히 1대). 배분 루프는
전용 단일 스레드에서 돌아 붙여 둔 상태에서도 **요청 처리 뒤에 줄 서지 않는다**
(4.6.2).

**분리 조건**: 틱 지연 p99 가 `G4.3` 임계(100ms)에 근접할 때. 4.6.8 이 그 값을 잰다.
미리 쪼개지 않는 이유는 샤딩과 같다 — 배포·감시·장애 지점이 하나 늘고, 지금은
늘려야 한다는 신호가 없다.

**분리해도 리더 선출은 버려지지 않는다.** 스케줄러를 HA 로 여러 대 띄우면 그중
하나만 배분해야 하므로 같은 장치가 그대로 쓰인다.

## 2. 왜 폴링이고, 왜 통째 교체인가

**pub/sub이 아니라 폴링**: pub/sub은 at-most-once다. 재시작하거나 재연결한 노드는
놓친 메시지를 영영 못 받고 **자기가 놓쳤다는 사실조차 모른다**. `HGETALL`은 언제
붙어도 전체를 복구한다. 변화가 없어도 신선도 판단을 위해 매 틱 방송해야 하므로
트래픽 이득도 없다.

**키별 캐시가 아니라 통째 교체**: miss가 나면 그 순간 Redis로 요청이 몰린다 —
오픈 첫 초에 정확히 피해야 할 상황이다. 그리고 쿠폰마다 낡음 시점이 다르면
"이 판정이 얼마나 낡았나"를 측정할 수 없다.

**낡음을 두 종류로 나누는 이유**: 섞으면 스케줄러 장애가 전 게이트웨이 동시
이탈로 번진다.

| 종류 | 의미 | 대응 |
|---|---|---|
| `fetchStale` | **이 노드의 루프가 돌지 않음** | liveness 실패 → 재기동 |
| `dataStale` | 판정 재료가 낡음 (원인 불문) | 200 유지 → fail-open 상한으로 버틴다 |

**`fetchStale` 은 "루프가 도는가" 지 "받아 왔는가" 가 아니다.** 마지막 *성공
수신* 으로 재면 레디스가 모두에게 느릴 때 **전 노드가 동시에 503** 이 된다 —
바로 아래 "Redis 연결 끊김 → 200 유지" 와 같은 상황에 반대를 지시하게 된다.

루프가 도는데 못 받는 것은 **공유 원인일 수도 국소 원인일 수도 있고, 그 자리에서
구분할 수단이 없다.** 구분할 수 없으면 안 빼는 쪽이 맞다 — 국소 장애를 안 빼는
대가는 그 노드 하나가 낡은 값으로 판정하는 것이고(그건 `dataStale` + fail-open
상한이 유계로 만든다), 공유 장애를 빼는 대가는 **100% 장애**다.

루프 **자체가** 멈춘 것은 다르다. 그건 이 프로세스의 결함이므로 조용히 빠지는
대신 **재기동시킨다** — readiness 가 아니라 liveness 의 일이다.

> **대가가 하나 더 있다: 서빙은 하는데 분모에는 없는 노드.** 커넥션이 국소로
> 고장 난 노드는 이제 로테이션에 남는다. 그런데 같은 커넥션으로 하트비트(4.3.1)도
> 못 쓰므로 리더는 `staleAfter` 뒤에 그 노드를 `N` 에서 뺀다. 남은 노드가
> `credit/(N-1)` 씩 쓰면 합계가 이미 `credit` 이고, 거기에 빠진 노드의 fail-open
> 통과분이 **전역 크레딧 밖에서** 더해진다 — 불변식 2 가 깨진다.
>
> 그래서 `dataStale` 노드의 상한은 별도 천장이 아니라 **마지막으로 알던 자기 몫**
> (`credit/N`) 으로 묶는다. 분모에서 빠져도 합계가 `credit` 을 안 넘는다.
> 4.3.1 과 fail-open 상한을 만들 때 이 제약을 함께 넣는다.

> **종료 중인 파드는 예외다.** 종료 신호를 받으면 드레이닝(6.7)에 들어가는데,
> 그동안 루프를 내리면 `fetch-stale-after`(2초) 뒤에 liveness 가 실패한다.
> graceful shutdown 기본 대기가 30초라 **in-flight 요청을 든 파드가 kill 된다.**
> 종료 플래그가 서면 liveness 판정에서 `fetchStale` 을 뺀다.

로컬 수신 시각만 쓰면 후자를 영영 못 잡는다 — 스케줄러가 죽어도 게이트웨이는 같은
해시를 계속 받아 "방금 갱신했다"고 스스로를 속인다.

## 3. F5 — 노드 수 증감 반영은 비대칭이어야 한다

각 노드는 `credit / N`을 자기 몫으로 쓴다. `N`(신선한 게이트웨이 수)이 바뀔 때:

| 변화 | 반영이 늦으면 | 위험도 |
|---|---|---|
| 노드 **증가** (스케일아웃·배포) | 기존 노드들이 작은 `N`을 계속 써서 **총합이 credit 초과** | **위험** |
| 노드 **감소** (종료·장애) | 남은 노드들이 큰 `N`을 써서 **총합이 credit 미달** | 안전 |

둘을 같은 임계로 처리하면 증가 방향에서 그 시간만큼 크레딧 초과 배분이 일어난다.

**결정**: 비대칭 반영.

- **증가는 즉시** — 새 노드가 하트비트를 남기면 다음 틱에 바로 분모에 포함
- **감소는 천천히** — `staleAfter` 경과 후에야 분모에서 제외
- 즉, 분모는 항상 **관측된 최대치 쪽으로 보수적**으로 잡는다

부작용: 노드가 실제로 줄었는데 분모가 크면 총 통과가 미달된다. 하지만 미달은
지연일 뿐이고 초과는 장애다. **비대칭이 옳다.**

추가로: 노드가 자발적으로 종료할 때는 `PreDestroy`에서 즉시 등록 해제해
`staleAfter`를 기다리지 않게 한다.

## 4. F6 — 콜드 백엔드 인스턴스가 가용량을 과대 보고한다

발급 계층 인스턴스가 자기 여유를 보고하는 방식은 옳다 — 밖에서 추측하면 항상
틀리고, 인스턴스 목록을 알 필요도 없어진다. 하지만 **재기동 직후**에 취약하다.

```
인스턴스 재기동  →  커넥션 풀이 비어 있음  →  "유휴 200" 보고
                 →  게이트웨이가 트래픽을 보냄
                 →  실제로는 JIT 콜드 + 캐시 미스로 느림  →  즉시 포화
```

**결정**: 램프업을 양쪽에서 건다.

1. **인스턴스 측**: 기동 후 60초 동안 `credits × min(1, 경과/60s)` 로 보고한다.
   자기 상태를 가장 잘 아는 쪽에서 하는 것이 정확하다 (A-12, 합의 완료)
2. **게이트웨이 측(방어)**: 처음 관측된 `instanceId` 에 같은 60초 램프를 건다 (A-13)

**둘이 다 걸리면 같은 창 안에서 곡선이 가팔라진다.** 게이트웨이는 보고값 하나만
보고 전체 용량을 모르므로, "작은 쪽을 쓴다" 를 구현할 두 번째 값이 없다. 방향이
과소라 안전하고 60초 안에 스스로 풀리므로 그대로 둔다.

2번만으로도 동작하는 것이 요점이다 — 상대 구현이 늦거나 빠져도 보호가 남는다.

카오스 C7이 이를 검증한다.

<a id="f9"></a>
## 5. F9 — 리더 전환 시 평활화 상태가 유실된다

`CreditSmoother`의 EWMA 값과 히스테리시스 상태(마지막 전이 시각)는 리더 프로세스의
메모리에 있다. 리더가 바뀌면 리셋되고, **회복 직후가 정확히 진동하기 가장 쉬운
구간**이다.

**결정**: 평활화 상태를 스냅샷 메타에 실어 보낸다.

- 리더가 매 틱 EWMA·전이 시각을 스냅샷에 기록
- 새 리더가 기동 시 스냅샷에서 읽어 이어받음
- 스냅샷이 없으면(완전 콜드 스타트) 첫 관측치로 초기화하고, 그 사실을 메트릭으로 남김

비용: 스냅샷 메타에 쿠폰당 몇 바이트. `CreditSmoother` 상태를 직렬화 가능하게
설계하는 것이 Phase 2 (2.6.3 상태 직렬화)의 요구사항이었던 이유다.

### 6.5 리더 선출

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 4.5.1 | 획득 — `SET key <소유자ID> NX PX <lease>` | 이미 잡힌 락을 뺏지 않음 |
| **4.5.2** | **소유자ID 는 기동마다 새로 만드는 난수** | 재기동한 자신을 이전 소유자로 오인하지 않음 |
| **4.5.3** | **연장은 소유권 확인 후** — Lua 로 `GET == 내ID` 일 때만 `PEXPIRE` | 남의 락 수명을 늘리지 않음 |
| **4.5.4** | **해제도 소유권 확인 후** — Lua 로 `GET == 내ID` 일 때만 `DEL` | 남이 잡은 락을 지우지 않음 |
| 4.5.5 | Redis 실패 시 **리더가 아니라고 답한다** | fail-open 하면 배분이 N번 돈다 |
| 4.5.6 | 종료 시 락 해제 (4.5.4 경유) | 다음 리더가 lease 만료를 기다리지 않음 |
| 4.5.7 | 리더 전환 로깅 | |
| 4.5.8 | 스플릿 브레인 시 크레딧 2배 발행이 **정합성으로 번지지 않음** | 재고는 발급 계층 원자 차감이 지킨다 |

> **연장과 해제를 소유권 확인 없이 하면 락이 락 구실을 못 한다.** STW 로 A 의
> lease 가 만료되고 B 가 잡았는데, 깨어난 A 가 그냥 `PEXPIRE` 를 걸면 **B 의 락을
> A 가 연장**하고, 그냥 `DEL` 하면 **B 가 리더인 채로 락만 사라진다.** 둘 다 Lua
> 한 번으로 원자적으로 확인한다 — 펜싱 토큰을 안 쓰기로 한 것과는 별개의 문제다.

> **펜싱 토큰을 쓰지 않는 근거**: STW GC로 A의 락이 만료되고 B가 잡았는데 A가
> 깨어나 한 틱을 더 돌면 크레딧이 2배 발행된다. 그러나 **크레딧은 재고를 예약하지
> 않으므로** 최악의 경우 한 틱 동안 예정의 2배가 앱으로 들어올 뿐이고, 재고는
> 발급 계층이 막는다. 실패가 유입 스파이크로 끝나고 정합성으로 번지지 않는다.
> **이 근거가 바뀌면 — 크레딧이 재고를 예약하는 구조가 되면 — 펜싱이 필수가 된다.**

### 6.6 배분 스케줄러

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 4.6.1 | 틱 루프 — `repeatWhen`, 완료 후 다음 주기 | 회복 시 크레딧 몰아 발행 없음 |
| 4.6.2 | 전용 단일 스레드 | 트래픽 뒤에 줄 서지 않음 |
| 4.6.3 | 첫 틱 지연 | 기동 직후 하한 배분 방지 |
| 4.6.4 | 수요 수집 — 파이프라인 ZCARD (Lua 아님) | 클러스터 호환 |
| 4.6.5 | `stock` MGET 별도 조회 | 샤드 무관 키 |
| 4.6.6 | 배분 적용 — HSET + **임계 산출 후 SET** (D-8·D-10) | 크레딧이 큐보다 커도 `+inf` 를 쓰지 않음 |
| 4.6.7 | **평활화 상태 이월** (F9) | 리더 교체 후 EWMA 유지 |

| 4.6.9 | 게이지는 한 번만 등록, 값은 필드로 갱신 | 첫 틱 값에 멈추지 않음 |
| 4.6.10 | **`runtime` 을 발행한 `(credit, waiting)` 에서 유도** | 아래 |

> **두 값을 다른 시점에 재면 쿠폰이 사라진다.** `credit` 을 산출한 뒤 `waiting` 을
> 다시 읽으면 그 사이에 사람이 빠져 `QUEUEING` 인데 `credit >= waiting` 인 조합이
> 발행된다. 도메인이 I3 로 막는 조합이라 코덱이 **그 쿠폰만 떨구고**, 떨어진 쿠폰은
> 판정에서 없는 쿠폰 — 즉 **매진**으로 보인다. 정상 동작이 전면 차단으로 번진다.
>
> 그래서 `runtime` 은 **발행하는 그 쌍에서 유도한다.** 한 번 읽은 `waiting` 을
> 들고 `credit >= waiting ? DRAINING : QUEUEING` 을 계산해 같이 쓴다. 경계는
> `CouponState` 의 I3 와 같은 자리여야 한다 — 갈리면 배분기가 생성자에 막히는
> 값을 계속 발행한다.

### 6.7 헬스체크

**readiness 는 "내가 판정할 수 있는가"만 본다.** 의존성 상태를 넣으면 공유 장애가
전 노드 동시 이탈로 번진다 — `G4.6` 이 막으려는 것이 정확히 그것이다.

| 조건 | readiness | 근거 |
|---|---|---|
| 갱신 루프가 돌지 않음 | **liveness 실패** | 이 프로세스의 결함이다. 빼는 것이 아니라 재기동 |
| 루프는 도는데 못 받음 | **200 유지** | 공유인지 국소인지 못 가린다. 못 가리면 안 뺀다 (2절) |
| 첫 스냅샷 미적재 (`Instant.EPOCH`) | **503** | 판정 재료가 없으면 못 받는다 (4.1.2) |
| 루프가 **아직 한 번도 안 돎** | **503만.** liveness 는 아니다 | 아래 |

> **기동 직후를 루프 정지로 세면 크래시 루프다.** 아직 한 번도 안 돈 것과 돌다
> 멎은 것은 `tickAge` 로는 같은 값이다. 그대로 liveness 에 물리면 첫 판을 못 돈
> 파드가 죽고, 재기동해도 또 첫 판 전이라 또 죽는다. **liveness 는 "한 번이라도
> 돈 뒤 임계 초과" 로 한정하고**, 첫 판 전 구간은 readiness 와 `startupProbe`
> 가 맡는다. `SnapshotHolder.첫_회전_전인가()` 가 이 둘을 갈라 준다.
| 종료 신호 수신 | **503** | 드레이닝 시작. LB 가 먼저 빼야 5xx 가 안 샌다 |
| `dataStale` — 판정 재료가 낡음 | **200 유지** | `G4.6` — 전 노드가 같은 값을 본다. 빼면 100% 장애 |
| Redis 연결 끊김 | **200 유지** | 요청 경로에서 Redis 를 안 친다. 넣으면 Redis 장애 = 전면 장애 |
| 뒷단 서킷 오픈 | **200 유지** | 서킷이 열려도 큐·종결 응답은 해야 한다 |

**관리 포트를 서비스 포트와 분리한다.** LB 는 관리 포트로 체크하고 서비스 포트로
포워딩한다 — 관리 엔드포인트를 외부에 노출하지 않으면서 LB 만 보게 하는 방법이다.

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 4.7.1 | 루프 정지만 liveness 실패 | 받아오기 실패는 200 유지 · `dataStale` 은 detail |
| 4.7.2 | 전용 헬스 그룹 (`readiness`) | LB가 이것만 본다 |
| 4.7.3 | `OUT_OF_SERVICE` → 503 매핑 | |
| 4.7.4 | detail에 진단 정보 | tick, 쿠폰 수, 두 age |
| **4.7.5** | **관리 포트 분리** — 체크는 관리 포트, 트래픽은 서비스 포트 | 관리 엔드포인트가 서비스 포트로 안 열린다 |
| **4.7.6** | **Redis·뒷단 상태가 readiness 에 들어가지 않는다** 회귀 테스트 | 의존성을 넣으면 `G4.6` 이 깨진다 |
