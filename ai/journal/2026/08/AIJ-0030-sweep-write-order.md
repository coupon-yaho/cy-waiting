# 쓰기 순서가 계약이다 — 청소가 제거를 먼저 하고 있었다

## 무엇이 잘못돼 있었나

청소가 큐에서 **제거를 먼저** 하고 유예 기록을 나중에 했다. 대상이 많으면
기록 단계가 인자 한계에 걸리는데, 그때 제거는 이미 커밋된 뒤다.

```
3999명 → 정상.  queue 3999→0, grace 3999
4000명 → ERR too many results to unpack
         queue 4000→0, grace 0      ← 그 인원이 흔적 없이 사라진다
```

호출부는 에러만 받고 **사라진 사실조차 모른다.** 반환값이 없기 때문이다.

계획서가 이 청소를 Lua 로 둔 이유가 *"제거와 유예 이동이 나뉘면 자리 유실"*
인데, **현재 순서가 그 상황을 그대로 만들고 있었다.** 원자성은 확보했는데
순서를 안 봐서, 막으려던 것이 스크립트 안에서 일어났다.

## 왜 기록이 먼저여야 하나

인자가 쌍이라 기록 쪽이 한계에 **먼저** 걸린다. 걸리는 순간 큐는 아직
그대로고, 실패해도 남는 것은 "아직 안 빠진 사람" 이다 — 다음 틱에 다시
처리된다. **무해한 실패**로 바뀐다.

인원 상한을 둬도(CY-278) 이 순서가 필요하다. 기록 단계는 메모리 부족이나
자료형 오류로도 실패할 수 있고, 그때마다 같은 유실이 난다.

## 덤으로 치명 하나가 같이 닫혔다

메모리 상한에서 쓰기 거부가 **비대칭**이다. 실측:

| 명령 | 상한 도달 시 |
|---|---|
| `ZADD` (등록·하트비트) | `OOM command not allowed` |
| `ZREM` (청소) | **통과한다** |
| `SET NX PX` (리더 획득) | `OOM command not allowed` |
| `PEXPIRE` (리더 연장) | 통과한다 |

레디스는 스크립트가 **이미 쓰기를 한 뒤에는** OOM 으로 중단하지 않는다.
제거가 먼저면 청소는 그대로 완주하고, 아무도 하트비트를 못 하는 동안
**앞에서부터 매 틱 큐를 지운다.** 메모리를 줄이는 정상 경로(입장 확정)도
하트비트 쓰기에서 먼저 막혀 **자력 회복이 안 된다.**

기록(`HSET`)은 거부 대상이라, 순서를 뒤집으면 청소가 **첫 쓰기에서 통째로
막힌다.** 파괴 경로가 사라진다 (CY-295).

## 시험도 같은 한계에 걸려 있었다

큐를 채우는 픽스처가 한 번에 넣다가 **같은 인자 한계에 먼저 걸려**, 검증하려던
자리에 닿기도 전에 시험이 죽었다. 나눠 넣도록 고쳤다.

이게 왜 안 드러났나 — 기존 청소 시험이 도는 규모가 **최대 50명, 검사 범위
10** 이다. 실패는 4000명에서 난다. **운영 규모가 시험 규모의 400배**다.

## 확신이 낮은 부분

- **4000 은 이 배포판의 값이다.** Lua 의 인자 한계라 판이 바뀌면 달라진다.
  시험이 상수로 8000/2 를 쓰고 있어서, 한계가 바뀌면 시험이 먼저 깨진다 —
  깨지는 편이 조용히 통과하는 것보다 낫다.
- **OOM 조합은 카오스 시나리오에 없다.** 메모리 상한 도달은 설계가 스스로
  예상하는 상태인데(20,000 대기 × 쿠폰 수) 시나리오 목록에 빠져 있다.

## 검증

- 되돌리면 실패한다 (자기검증)
- 3999 정상 / 4000 에서 큐가 그대로 남는 것까지 단언
- 단위·통합·카오스 전 계층 통과

## 다음 사람에게

**Lua 로 묶었다고 원자적인 것이 아니다.** 롤백이 없으므로 실패 지점 앞의
쓰기는 남는다. 그래서 **무엇을 먼저 쓰는지가 계약**이다 — 실패했을 때 남는
상태가 무해한 쪽을 앞에 둔다.
