# 회원 신원을 JWT 로 검증할 수 있게 한다

## 무엇을

`waiting.auth.mode` 를 `JWT` 로 두면 게이트웨이가 Bearer 토큰을 검증하고, 그 클레임으로 `X-Member-Id` 와
`X-Member-Grade` 를 새로 싣는다. 기본은 `NONE` 이라 지금처럼 앞단이 인증을 끝냈다고 믿고 헤더를 형식만 본다.

## 왜 (근거)

지금 게이트웨이는 회원 헤더를 형식만 본다. 앞에 인증 계층이 없는 배치에서는 누구든 남의 식별자로 줄을 설 수
있고, 한 사람이 식별자를 바꿔 가며 줄을 여러 번 설 수도 있다. 공정성 불변식이 신원을 믿는 데서 출발하므로,
신원을 검증할 자리가 게이트웨이 안에도 있어야 했다.

**스타터를 안 쓰고 `spring-security-oauth2-jose` 만 넣었다.** 스타터를 넣으면 보안 필터 체인이 자동으로 서서
모든 경로에 인증을 걸고, 우리 필터 순서와 헬스 체크 경로를 따로 풀어야 한다. 필요한 것은 검증기 하나다.

**알고리즘은 설정으로 고정한다.** 토큰 머리의 `alg` 를 믿으면 두 공격이 선다. `none` 으로 서명 없는 토큰이
통과하고, RSA 공개키를 HMAC 비밀로 써서 만든 HS256 토큰이 통과한다. 둘 다 시험으로 막혀 있다.

**틀린 설정은 기동에서 멈춘다.** 알고리즘별 하한보다 짧은 HMAC 비밀, 알고리즘과 어긋난 키 공급, 공개키와 JWKS 를
같이 적은 것, https 가 아닌 JWKS 주소, 빠진 대상이 그렇다. 안 멈추면 첫 요청부터 전원이 401 이거나, 약한 키로
서명된 토큰이 통과한다.

**입장 토큰 헤더 이름이 신원 헤더와 겹치면 기동을 막는다.** CY-981 에서 사용자가 `x-member-id` 를 예약어로
두지 말라고 했다. 인증을 끈 배치에서는 그 이름을 쓸 이유가 있을 수 있어서다. 그런데 인증을 켜면 클라이언트가
보낸 입장 토큰 값이 검증된 신원을 덮는다. 그래서 막는 조건을 인증을 켰을 때로 좁혔다.

**식별자와 등급은 헤더 모드와 같은 계약이다.** 처음에는 토큰의 식별자를 문자 모양으로만 봤고 등급 클레임은
선택이었다. 시험 검토가 짚었다. 뒷단 계약은 식별자가 앞의 0 없는 양의 정수이고 등급이 필수다. 서명됐다고 뒷단이
모르는 모양을 넘기면 안 되므로 헤더 모드의 검사를 그대로 쓰고, 등급 클레임은 기본을 `grade` 로 두고 없으면
401 로 했다.

**보안 검토가 짚어 고친 것.**

- 모르는 kid 를 단 위조 토큰 하나가 발급자 호출 하나가 됐다. 라이브러리의 원격 키 원천은 캐시에 없는 kid 마다
  다시 받고 시한도 없다. 직접 캐시(`JwkSetCache`)를 꽂아 다시 받기를 10초에 한 번으로 묶고, 실패한 시도의 결과도
  그 동안 돌려주며, 3초에 끊는다. 5분마다 새로 받아 발급자가 뺀 키가 계속 통하지 않게 했다
- 키 집합을 못 받으면 라이브러리가 `IllegalStateException` 을 내서 500 이 됐다. 토큰 탓이 아니므로 503 이다
- 만료 없는 토큰이 통과했다. 라이브러리 기본이 허용이다
- 대상과 발급자가 선택이라 같은 발급자의 다른 서비스 토큰이 통했다. 대상은 필수, JWKS 를 쓰면 발급자도 필수다
- JWKS 를 http 로 받았다. 중간자가 키를 바꿔 끼우면 전원 사칭이다. `allow-http-jwks` 로만 연다
- 비밀 하한이 HS384·HS512 에서도 32바이트였다. RSA 공개키 크기는 안 봤다
- 라우트가 `/api/` 밖이면 신원 필터를 안 탄다. 인증을 켰을 때는 기동에서 막는다
- 재검토에서, 발급자를 못 닿는 동안 받아 둔 키로 끝없이 버티는 것이 나왔다. 마지막으로 받은 뒤 한 시간까지만 버틴다

**스타일 점검이 짚어 고친 것.** 401 은 `BadJwtException` 만이다. 라이브러리는 암호 처리 실패도 `JwtException` 으로
감싸는데, 그것까지 401 이면 내부 장애가 다시 로그인하라로 보인다. 거절은 사유별(`missing`·`invalid`·`unavailable`)로
`waiting.auth.rejected` 에 센다. 요청마다 로그를 남기지 않는다. 키 집합 장애는 버티는 동안 WARN, 쓸 키가 없으면 ERROR,
돌아오면 지속 시간과 실패 횟수를 INFO 로 남긴다. 결과를 가르던 같은 값의 센티넬 둘은 sealed 타입으로 나눴다.

`AuthProperties.Jwt` 는 불변식이 얽혀 있지만 record 로 둔다. 설정 바인딩이 생성자 하나로 값을 받아 거기서 막는 것이
기동 실패를 가장 앞에 둔다.

## 버린 것

- **`jwt` 틀을 설정 파일에 빈 자리로 두기.** 빈 알고리즘으로 레코드가 만들어져 `NONE` 에서도 기동이 멈춘다.
  주석으로 적고, 환경 변수는 relaxed binding 으로 읽힌다.
- **EC 공개키를 JWK 집합으로 감싸 kid 없이 넘기기.** Nimbus 의 선택기가 토큰의 kid 로 키를 거르므로 kid 가
  있는 토큰은 전부 떨어진다. 키가 하나라 토큰의 kid 를 이름표로 붙였다. 고르는 데는 안 쓰인다.
- **입장 토큰 충돌 검사에 `Authorization` 넣기.** 입장 토큰 쪽이 이미 예약해 둬서 닿지 않는 분기였다. 단언을
  메시지까지 좁히고서야 드러났다.

## 어떻게 검증했는가

HS256/384/512, RS256/384/512 PEM, ES256 PEM(kid 유무), JWKS(시험 안의 HTTP 서버) 경로가 검증된 신원을 넘기고,
다른 알고리즘·다른 키·모르는 kid·만료(경계 29초와 31초)·nbf·다른 발급자·다른 대상·서명 없음·알고리즘 바꿔치기는
401 이다. 거절마다 `WWW-Authenticate` 값과 뒤로 안 넘어간 것을 같이 본다. 캐시는 가변 시계로 위조 kid 100 건에
발급 요청이 한 번인지 쟀다. `./gradlew build` 와 기계 검사를 통과했다.

## 다음 사람이 알아야 할 것

- **조회 합치기가 인증 모드에서 사실상 꺼진다.** `QueryCoalescingFilter` 는 `Authorization` 이 실린 요청을 안 모으는데,
  인증 모드에서는 모든 요청에 실린다. 신원 헤더로 합칠 수 있는지는 따로 본다
- **`Authorization` 은 뒷단까지 간다.** 뒷단이 토큰을 로그에 남기면 거기서 샌다
- **헤더 모드에서도 `/api/` 밖 라우트는 형식 검사를 안 탄다.** 이번에는 인증 모드에서만 막았다
- 발급자에 닿지 못해도 받아 둔 키로 버틴다. 인증 실패를 fail-open 으로 돌리지는 않는다
- private static 에 걸린 헬퍼를 가시성만 바꿔 넘기려다 지적받았다. 검사를 생성자로 되돌리고, 나머지는 인스턴스
  메서드로 옮겼다
