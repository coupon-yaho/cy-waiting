# CI 파이프라인 구축과 Atlassian 액션 분리

## 무엇을

`.github/` 에 CI 를 세우고, Jira 연동을 별도 저장소(`ci-actions`)의 TypeScript
액션으로 뺐다. git flow + Jira 티켓 브랜치 규칙을 WF-3 에 명문화했다.

- composite action 3 + 재사용 워크플로 6 + 진입점 4
- `ci-actions`: Jira · Confluence 액션 + 공통 HTTP 계층 (테스트 69개, 구문 100%)
- CodeRabbit 을 라벨·제목·경로로 끌 수 있게 함

## 왜 (근거)

**최소 단위 분리**: 하나의 거대한 워크플로는 어느 단계가 왜 실패했는지 알기 어렵고
재사용도 안 된다. 두 계층으로 나눴다 — composite action 은 잡 **안의 스텝**
(같은 러너, 캐시 공유), 재사용 워크플로는 **잡 자체**(별도 러너, 실패 격리).
테스트를 계층별 잡으로 나눈 것은 **실패했을 때 어느 계층이 깨졌는지가 잡 이름만
보고 드러나야** 하기 때문이다.

**PR/main 분리**: 카오스는 PR 에서도 돈다 — 회복력이 이 프로젝트의 무게중심(R5)이라
병합 후 발견은 늦다. 반대로 뮤테이션은 PR 에서 뺐다. 40분을 기다리게 하면
아무도 PR 을 안 연다.

**Atlassian 연동을 별도 액션으로**: 셸 composite 로는 재시도·멱등성·형식 변환을
감당할 수 없다. 특히:

- Jira Cloud v3 는 코멘트 본문으로 평문을 받지 않는다(ADF 요구). 400 이 떨어지는데
  메시지가 불친절해 원인을 찾기 어렵다
- 조직 단위 레이트 리밋이 있어 CI 가 몰리면 429 가 실제로 난다. 재시도가 없으면
  그때마다 파이프라인이 빨개진다
- 전이 실패 시 **가능한 전이 목록**이 없으면 Jira 관리 화면을 열어야 원인을 안다
- Confluence 는 본문으로 XHTML 을 받는다. 마크다운을 그대로 보내면 **오류 없이
  저장되고 페이지에 원문이 그대로 보인다** — Jira 의 400 보다 나쁘다. 성공한 척한다

**두 액션을 한 저장소에 둔 이유**: 같은 사이트·같은 인증·같은 레이트 리밋을 쓴다.
재시도 로직을 두 번 짜면 **한쪽만 고쳐지는 일이 반드시 생긴다.** `shared/` 로 뺐다.

**TypeScript 선택**: Go·Rust 는 Docker 컨테이너 액션이 되어 실행마다 10~30초가
붙는다. PR 하나에 여러 번 도는 액션에 그 비용은 그대로 대기 시간이다.

**CodeRabbit 에서 문서 제외**: 한글 산문에 대한 지적은 오탈자·문체이지 설계 비평이
아니다. 그런 지적이 쌓이면 **코드에 대한 진짜 지적이 그 안에 묻힌다.**
`plan/` 의 설계 검토는 사람과 `.claude/agents/` 의 역할이다.

## 고려했으나 택하지 않은 것

- **`atlassian/gajira-*` 사용** — 공식에 가깝고 손이 덜 간다. 버렸다.
  `login`→`find`→`comment`→`transition` 4스텝이라 outputs 를 넘기다 **오타 하나로
  조용히 건너뛴다.** 위의 재시도·ADF·전이 진단도 없다.
- **서드파티 Jira 액션을 그대로 두고 재시도만 워크플로에서 처리** — `continue-on-error`
  + 재실행으로 흉내낼 수 있다. 버렸다. 재시도 사이 백오프를 못 넣어
  429 를 429 로 갚는다.
- **Go 로 작성** — 단일 바이너리라 의존성이 없다. 버렸다. Docker 액션의 기동
  비용이 이 액션의 실행 빈도와 안 맞는다. composite + 사전 빌드 바이너리 다운로드
  방식도 검토했으나 릴리스 파이프라인이 하나 더 생긴다.
- **Confluence 페이지 ID 를 시크릿으로** — 공개 액션 대부분이 쓰는 방식이다.
  버렸다. **페이지를 다시 만들 때마다 시크릿을 고쳐야 하고, 잊으면 CI 가
  엉뚱한 페이지를 덮어쓴다.** 제목을 키로 쓰면 그 문제가 없고 시크릿도 하나 준다.
- **완전한 마크다운 파서 도입** — `marked` 등을 쓰면 변환이 정확해진다. 버렸다.
  번들 크기와 공급망 표면이 늘고, CI 리포트에 쓰는 문법은 일곱 가지뿐이다.
- **하나의 거대한 `ci.yml`** — 파일이 하나라 읽기 쉽다. 버렸다.
  잡 이름으로 실패 지점이 드러나지 않고, main/nightly 가 PR 과 다른 것을 돌 때
  `if` 조건이 얽힌다.
- **CodeRabbit 을 아예 끄기** — 노이즈가 걱정이면 가장 단순하다. 버렸다.
  기본은 켜고 **필요할 때 라벨로 끄는** 편이 안전하다. 꺼두면 켜는 것을 잊는다.
- **`auto_review.labels` 로 허용 목록 구성** — CodeRabbit 네이티브 기능이다.
  버렸다. 허용 목록이라 **매번 라벨을 붙여야 리뷰가 돈다** — 방향이 반대다.

## 확신이 낮은 부분 / 남은 위험

- **CodeRabbit 의 `@coderabbitai pause` 동작을 실측하지 못했다.** 문서화된 채팅
  명령이지만 실제 PR 에서 확인한 적이 없다. 동작하지 않으면 `path_filters` 와
  제목 키워드만 남는다 — 그 둘은 PR 도중에 켜고 끌 수 없다
- **CodeRabbit 요약 코멘트의 형식에 의존한다.** `relay` 워크플로가
  `Actionable comments posted: N` 문자열을 파싱하는데, CodeRabbit 이 형식을 바꾸면
  지적 건수가 항상 0 으로 보고된다. 실패가 조용하다 — 알림은 계속 가는데 숫자만 틀린다
- **`timeout-minutes: ${{ inputs.* }}`** 가 모든 GitHub 런타임에서 동작하는지
  확신이 없다. 재사용 워크플로에서 표현식이 허용된다고 알고 있으나 실행 확인은 못 했다
- **Jira 전이 이름(`In Review`, `Done`)이 실제 워크플로에 있는지 모른다.**
  없으면 액션이 가능한 목록을 에러로 출력하므로 진단은 되지만 첫 실행이 실패한다
- 어느 워크플로도 **실제 GitHub 에서 돌려보지 않았다.** YAML 문법과 참조 무결성만
  검증했다. 첫 푸시에서 표현식·권한 문제가 나올 것으로 본다

## 어떻게 검증했는가

- YAML 문법 18개 파일 통과 (`yaml.safe_load`) — 양 저장소
- 재사용 워크플로·composite action 참조 무결성 통과
- 문서 링크 무결성 통과 (양 저장소)
- `ci-actions`: 타입체크 통과, **테스트 69개 통과**, 커버리지 구문 100% / 분기 82%,
  두 액션의 ncc 번들 빌드 성공
- **GitHub 에서의 실행은 검증하지 못했다** — 저장소가 아직 원격에 없다

작성 중 워크플로 결함 3건을 실측으로 잡았다:

| 결함 | 증상 |
|---|---|
| `issue.labels.*.name \|\| pull_request.labels.*.name` | GitHub 표현식에서 **빈 배열은 truthy** 라 `pull_request_review` 이벤트에서 PR 라벨을 영영 보지 못한다 |
| `nightly.yml` 의 `scenario` 입력 | 선언만 하고 쓰지 않아, 지정해도 조용히 전체가 돈다 |
| 브랜치 검사가 외부 액션 의존 | 액션이 없으면 **모든 PR 이 첫 잡에서 막힌다** |
| `nightly` 의 `continue-on-error: true` | 스텝을 통과시키면 **잡 결과가 success** 가 되어, 리포트가 늘 "이상 없음" 으로 나온다 |

링크 검사기의 오탐 2건(펜스 블록·인라인 코드 안의 `](...)`)도 함께 고쳤다 —
오탐이 잦은 검사는 곧 무시되고, 무시되는 검사는 없는 것과 같다.

`nightly` 의 것이 가장 위험했다. 야간 검증이 **늘 초록불로 보고되는** 상태였다.
`fail-fast: false` 만으로 "하나가 깨져도 나머지를 끝까지 돌린다" 는 목적이
달성되므로 `continue-on-error` 는 애초에 필요 없었다.

## 다음 사람이 알아야 할 것

- 조직명은 `coupon-yaho` 다. 워크플로가 `coupon-yaho/cy-ci-actions/actions/*@v1` 을
  참조하므로 **그 저장소가 GitHub 에 있고 `v1` 태그가 달려 있어야** 한다
- **브랜치 규칙 검사는 외부 액션에 의존하지 않는다.** PR 의 첫 관문이라
  거기서 외부 저장소를 참조하면 그 저장소가 없는 순간 모든 PR 이 막힌다.
  인라인 셸로 남겼다 — 문자열 검사에 의존성을 만들 이유가 없다
- **`ci-actions` 를 먼저 푸시하고 `v1` 태그를 단 뒤** `waiting` 을 푸시한다.
  순서가 바뀌면 첫 CI 가 액션을 못 찾는다
- `coderabbit-relay.yml` · `coderabbit-control.yml` 은 **기본 브랜치의 파일**로
  실행된다. 고쳐도 `main` 병합 전까지 반영되지 않는다
- `dist/` 를 커밋하지 않거나 빌드를 잊으면 **옛 동작이 조용히 실행된다.**
  `ci-actions` CI 가 검사하지만, 로컬에서는 `npm run verify` 를 습관으로 둔다
- **journal 제외 목록이 두 곳에 있다** — `.claude/hooks/remind-journal.sh` 와
  `.github/workflows/_verify-conventions.yml`. 한쪽만 고치면 훅은 조용한데 CI 가
  PR 을 막는다. 실제로 `.gitignore` 에서 어긋나 있었다
- **계획 문서에 커밋 해시를 적지 않는다.** base 작업 구간은 amend 로 이력을
  다듬고 있어 해시가 계속 바뀐다. 실제로 세 개 중 두 개가 낡아 있었다
