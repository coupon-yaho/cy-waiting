# 병합을 막는 유일한 검사가 아무것도 안 막고 있었다

## 무엇을

`판정` 잡이 결과를 출력만 하고 **늘 0 으로 끝났다.** 브랜치 보호가 요구하는 검사는
`컨텍스트`·규범 둘·`보안 / 시크릿 유출`·`판정` 다섯이고 **개별 잡은 요구 목록에 없다.**
그래서 카오스·빌드·커버리지가 빨개져도 `판정` 이 초록이라 병합이 열렸다.

G8.13 이 요구하는 것이 정확히 이것이다 — "카오스 잡이 CI에서 자동 실행되고 **실패 시
병합 차단**". 실행은 되고 있었고 차단은 안 되고 있었다.

## 어떻게 찾았나

G8.13 을 닫으려고 `pr.yml` 의 `needs` 를 따라가다 `.github/actions/verdict` 를 열었다.
`if/else` 로 출력만 쓰고 끝나는 스크립트였다. `set -uo pipefail` 이 있어 오히려
"제대로 만든 것" 처럼 보인다.

## 왜 오래 안 보였나

**초록이 세 겹으로 겹쳐 있었다.** 개별 잡이 초록이면 `판정` 도 초록이라 아무 차이가
없고, 슬랙 리포트는 `verdict.outputs.ok` 를 읽어 실패를 정확히 알린다 — 사람 눈에는
"실패가 보였다". 보이는 것과 막히는 것이 다르다는 것이 여기서 갈렸다.

## 고친 것

규칙을 `.github/scripts/verdict.sh` 로 뺐다. 인라인이면 자기검증을 못 건다.

- 실패·취소가 하나라도 있으면 **잡을 실패시킨다**
- 결과 목록이 비어 있어도 실패시킨다. 못 받은 것은 "이상 없다" 가 아니라 "안 봤다"
  다 — 통과로 넘기면 `needs` 를 잘못 엮는 순간 게이트가 조용히 사라진다
- `skipped` 는 그대로 통과. 문서 PR 이 빌드를 건너뛰는 것은 정상이다

리포트 잡은 `if: !cancelled()` 라 판정이 실패해도 돈다. 실패한 잡의 출력도 읽히므로
슬랙·Jira 전이는 그대로다.

## 자기검증을 같이 넣었다

`.github/scripts/verdict-selftest.sh` — 열 가지를 본다. 옛 동작(출력만 내고 0 으로
끝나기)을 되돌려 넣으면 **다섯 줄이 빨개진다.** 그것을 확인하고 넣었다 (TS-9·TS-12).

`_verify-conventions.yml` 과 `.claude/hooks/review-branch.sh` 양쪽에 건다 — 로컬이
CI 와 같은 스크립트를 돌려야 왕복이 안 는다.

## 리뷰가 같은 병을 셋 더 찾았다

`security-reviewer` 를 돌렸다. 고친 자리 옆에 같은 모양이 셋 더 있었다.

**야간은 여전히 열려 있었다.** `nightly.yml` 의 판정이 `[test, load, waste, security]`
만 본다. 그런데 앞의 셋이 다 `needs: build` 라, 빌드가 깨지면 셋이 통째로
`skipped` 가 되고 `security` 만 남는다 — JAR 을 한 번도 못 만든 밤에 "이상 없음"
이 나간다. `skipped` 를 통과로 보는 규칙은 맞지만, **무엇이 건너뛰었는지는 판정이
안 본다.** `build` 와 `plan` 을 넣었다.

**구분자에 기대고 있었다.** 정규식이 공백 구분자를 전제했는데 `join()` 의 기본
구분자는 쉼표다. 새 워크플로가 `join(needs.*.result)` 라고만 쓰면 — 가장 자연스러운
형태다 — `"success,failure"` 가 안 잡혀 게이트가 조용히 사라진다. 낱말 경계로
바꾸고 쉼표·탭·쌍반점을 자기검증에 넣었다.

**자기검증이 배선을 안 봤다.** 스크립트만 부르므로, 액션이 그 스크립트를 안 불러도
통과한다. 옛 동작을 액션 쪽에 되돌려 넣어 봤더니 자기검증도 워크플로 셸 검사도
안 물었다 — **고친 그 회귀가 그대로 재발해도 아무도 안 잡는다.** 액션이 스크립트를
부르는지 보는 줄을 넣고, `workflow-shell.sh` 의 대상에 `actions/*/action.yml` 을
더했다. composite action 의 `run:` 은 그때까지 셸 문법 검사조차 안 받고 있었다.

곁가지 둘도 같이 고쳤다 — `main.yml` 의 `dependency-graph` 가 판정 밖이라 의존성
제출이 실패해도 초록이었고, `_load-test.yml` 이 `workflow_dispatch` 입력을 셸에
직접 보간하고 있었다(`env` 로 넘긴다).

## 고려했으나 택하지 않은 것

- **브랜치 보호에 개별 잡을 다 넣는다** — 잡 이름이 바뀔 때마다 설정을 따라가야 하고,
  그 설정은 저장소 밖이라 리뷰가 안 붙는다. 집계 하나가 제대로 실패하는 편이 낫다
- **`판정` 을 없애고 개별 잡만 요구한다** — 취소를 통과로 세지 않으려고 이 잡을 뺀
  것이라(주석에 그렇게 적혀 있다) 되돌리는 셈이 된다

## 확신이 낮은 부분 / 남은 위험

- **`skipped` 를 통과로 보는 규칙이 남아 있다.** 문서 PR 에서 빌드를 건너뛰는 것은
  정상이라 필요하지만, "선행 잡이 깨져서 건너뛴 것" 과 "이 PR 에 해당이 없어서
  건너뛴 것" 을 판정이 구분하지 못한다. 야간은 `needs` 를 채워 막았지만 규칙
  자체는 그대로다
- **브랜치 보호 설정 자체는 코드 밖이다.** 요구 검사 목록이 바뀌면 이 수정도 무력해
  진다. 그것을 지키는 검사는 아직 없다
- `main.yml`·`nightly.yml` 도 같은 액션을 쓰므로 이제 실패하는 잡이 생긴다. main 이
  빨개지면 그것이 새 결함이 아니라 **원래 빨간 것이 이제 보이는 것**이다

## 다음 사람이 알아야 할 것

집계 잡을 새로 만들 때는 **출력과 종료 코드를 같이 낸다.** 출력만 내는 집계는
대시보드지 게이트가 아니다.
