# 큐 순서를 순번에서 timestamp 로 — 차단 결정 5건이 함께 풀렸다

## 무엇을

`INCR seq` 로 순번을 발급하던 것을 **Redis 시계 μs 를 ZSET score 로 쓰는 방식**으로
바꿨다. 그 결과 Phase 3·8 의 착수 차단이 풀리고 결정 5건(D-P1·D-R1·D-S1·D-T1·D-Q1)이
확정됐다. 운영 환경도 EC2 노드 여러 대로 확정.

## 왜 (근거)

**질문 하나에서 시작했다** — "ZSET 에 INCR 을 쓰는 거였나, 그냥 timestamp 아니었나".

문서를 다시 보니 이 질문이 **서로 다른 두 페이즈의 아픈 곳을 동시에 짚고 있었다.**

| 어디 | 무엇 |
|---|---|
| F2 (D-P1) | 카운터가 되감기면 중복 순번 → 순위 역행 → 불변식 3 위반 |
| Phase 10 | `INCR seq` 가 **유일한 직렬화 지점**. 샤딩의 1차 목적이 이 카운터를 쪼개는 것 |

둘이 같은 원인이었다. 원인을 없애니 둘 다 사라졌다.

## 고려했으나 택하지 않은 것

- **`appendfsync always` (D-P1 A안)** — 원래 문서의 권장안이었다. 버렸다.
  순번이 사라져 중복 발번 위험이 없어졌고, 남은 유실은 대기자 증발이다.
  증발한 사람은 재등록하면 되고 **새 score 가 더 크므로 줄 선 사람을 추월하지
  않는다.** 20,000 스파이크에서 쓰기 지연을 치를 이득이 없다.
- **Eureka · Consul (D-R1)** — 디스커버리가 주는 건 "누가 있나"인데 필요한 건
  "각자 지금 얼마나 받나"다. Eureka 는 레지스트리 복제가 느려 초 단위로 변하는
  가용량을 못 따라가고, Consul KV 에 넣으면 **Consul 을 Redis 대신 쓰는 셈**이 된다.
  가용량은 R2 때문에 어차피 매초 Redis 를 지난다.
- **정적 목록 (D-R1)** — 한 번 골랐다가 되돌렸다. 운영이 EC2 라 IP 가 언제
  바뀔지 모른다는 사실이 뒤에 나왔다. k8s 면 DNS·Endpoints 라는 대안이라도 있는데
  EC2 에는 없다.
- **`String.hashCode()` (D-S1)** — 의존성 0 이라 권장했으나 CRC16 으로 갔다.
  timestamp 전환으로 해시가 순서 정합성에 영향을 안 주게 되어 분포 문제만
  남았고, 그러면 `redis-cli` 로 대조되는 쪽이 낫다.
- **게이트웨이가 토큰을 1회용으로 관리 (D-T1)** — 통과 경로에 Redis 쓰기가 생기고,
  그래도 결국 발급 계층 멱등성이 필요하다. 두 번 막을 이유가 없다.

## 확신이 낮은 부분 / 남은 위험

- **`always` 를 안 쓰기로 한 판단이 측정이 아니다.** "1초 유실은 재등록으로
  덮인다"가 전제인데, 오픈 직후 1초는 가장 붐비는 구간이라 증발 인원이 클 수 있다.
  Phase 1 부하 하네스로 재봐야 한다
- **Redis `TIME` 을 쓰는 Lua 의 복제 안전성.** Redis 5+ 는 효과 기반 복제라
  괜찮다고 알고 있지만 실측하지 않았다. Phase 3 에서 확인한다
- **μs 동점을 member 사전순으로 가르는 것**을 그냥 받아들였다. 100K 피크면
  ms 당 100건이라 μs 충돌은 드물지만 0 은 아니다
- **폴링마다 `ZCOUNT` 가 붙는다.** 20,000 대기 × 폴링 주기의 Redis 부하를
  아직 안 재봤다. 뺄셈이던 것이 O(log N) 호출이 됐다
- **D-C1 이 🔴 로 올라갔다.** Phase 9 전체가 뒷단 팀의 계약 변경에 달렸다.
  전에는 램프업 협의라 미뤄도 됐는데 이제 아니다

## 어떻게 검증했는가

검증한 게 아니라 **문서를 대조했다.** 코드가 없으니 실측할 대상이 없다.

- score 산술: μs epoch ≈ 1.7×10¹⁵ < 2⁵³ ≈ 9×10¹⁵ (ZSET score 정수 정확도)
- `seq` 언급 43곳을 전수 확인해 현행 서술과 이력 서술을 갈랐다
- 링크 전수 — 깨짐 0
- 훅 자기검증 50건, 문서의 커밋 예시 검사 통과

## 반영하다 나온 것 — 결정이 6건 더 생겼다

전환을 문서에 적는 과정에서 파생 결정이 나왔다. **큰 결정 하나는 그 자리에서
파생 결정을 여러 개 만든다**는 걸 다시 확인했다.

| ID | 무엇 | 왜 지금 필요했나 |
|---|---|---|
| E-9 | Redis 7.x · slew 보정만 | 설계가 처음으로 Redis 버전을 요구하기 시작했다 |
| E-10 | `maxscore` enqueue 마다 24h TTL | 새 키를 만들었으니 수명을 정해야 한다. 안 지우면 키가 쌓이고 지우면 방어가 사라진다 |
| E-11 | 바닥값은 `maxscore` 하나만 읽는다 | 처음엔 ZSET 마지막 원소도 읽게 썼는데, 효과 기반 복제의 원자성 때문에 군더더기였다 |
| D-10 | 크레딧 > 큐 크기면 임계는 큐 최대 score. **`+inf` 금지** | `+inf` 면 이후 도착자가 줄을 서지 않고 통과한다 |
| R-7 | 보고 만료는 Redis TTL 이 아니라 `ts` 읽기 측 필터 | **해시 필드에 개별 TTL 이 없다** (`HEXPIRE` 는 7.4+). 처음 쓴 설계가 틀렸다 |
| R-8 | in-flight 를 보고 수신 시 리셋 | 누수가 누적되면 그 인스턴스에 트래픽이 영구히 안 간다 |

**R-7 이 실수였다.** "TTL 3~5초" 라고 적었는데 해시 필드에는 걸 수 없다.
읽는 쪽이 `ts` 로 거르는 편이 버전에 안 묶이고 `SCAN` 도 필요 없다.

**C13 이 새로 생겼다.** E-6 이 복구를 복제본 승격에 의존하게 만들었는데 기존
카오스에는 승격 시나리오가 없었다. 시계 역행이 실제로 일어나는 지점이 거기다.
Phase 1 하네스가 시계 조작과 `failover` 를 지원해야 한다는 제약이 따라온다.

**Phase 10 ops 예산이 6 → 8 로 늘었다.** 직렬화 지점은 없앴지만 명령 수는 늘렸다.
성격이 달라(전부 O(1)/O(log N), 파이프라인 가능) 계산으로 판단하지 않고 측정하는
기존 방침을 유지한다.

## 뒤늦게 드러난 것 — 질문 하나가 결함 셋을 꺼냈다

"Phase 2 는 대기열인데 초과 발행을 어떻게 테스트하나, 뮤테이션은 뒷단 없이
어떻게 하나" 라는 질문에서 나왔다. **둘 다 답은 있었는데 답을 확인하다 셋이 나왔다.**

**1. 용어가 한 글자 차이로 계층을 넘나들었다.** `초과 발행`(배분 총합 > 크레딧,
게이트웨이)과 `초과 발급`(발급 수 > 재고, 발급 계층)이 문서에 섞여 있었다.
질문자가 걸린 게 그 증거다. `크레딧 초과 배분` 으로 바꿨다.

곁가지로 **A-7 과 모순되는 문장이 세 곳에 있었다** — "이 계층의 오류가 곧 초과
발급" 이라고 썼는데, A-7 은 "크레딧은 재고를 예약하지 않으므로 초과 발급으로
번지지 않는다" 다. 같은 혼동의 산물이라 같이 고쳤다.

**2. 순위 단조성의 책임이 조용히 옮겨갔다.** 전에는 `my_seq - admitted_seq` 가
둘 다 단조라 **도메인이 증명**할 수 있었다. score 전환 후 `localRank` 는 어댑터의
`ZCOUNT` 결과라, 도메인은 "입력이 단조면 출력도 단조"까지만 본다.
**입력이 단조라는 보장이 Phase 3 으로 갔는데 거기 게이트가 없었다.** G3.11 신설.

큰 변경은 검증의 위치를 옮긴다. 옮긴 자리에 게이트를 안 놓으면 **양쪽 다
안 보는 구간**이 생긴다.

**3. 유예 재입장이 두 문서에서 반대로 적혀 있었다.** `03` 은 "원래 순번 복원",
`06` 은 "추월은 유지". 같이 성립할 수 없고, 원래 score 로 복원하면 뒤에 있던
사람들의 `ZCOUNT` 순위가 1 늘어 **순위 역행 0(타협 불가)이 깨진다.**
D-11 로 "새 score 재등록"을 확정했다.

**대가는 정직하게 적어둔다**: 짧은 네트워크 끊김도 자리를 통째로 잃는다.
grace 로 풀 문제가 아니라 `alive` TTL 을 넉넉히 잡아 **grace 로 떨어지는 일 자체를
드물게** 만드는 게 맞다. 그렇지 않으면 사용자가 화낼 설계다.

## 다음 사람이 알아야 할 것

- **단조 가드는 선택이 아니다.** `TIME` 은 벽시계라 NTP·복제본 승격으로 뒤로 간다.
  뒤로 가면 **줄 선 사람이 추월당한다.** 큐가 빈 동안의 역행까지 막으려면
  `maxscore:{cid}` 가 필요하다
- **"몇 명 보냈는지"를 세지 않는다.** 라우팅은 장부가 아니라 되먹임이다 —
  보낸 결과는 다음 초의 가용량 보고에 나타난다. 전역 카운트를 하려면
  요청마다 Redis 를 쳐야 하고 그건 A-1 위반이다
- **라우터를 만드는 게 아니다.** Spring Cloud LoadBalancer 의 확장점 둘
  (`ServiceInstanceListSupplier`, `ReactorServiceInstanceLoadBalancer`)만 구현하면
  `lb://` 가 URI 를 고른 인스턴스 IP 로 갈아끼운다
- 이번 전환으로 **Phase 7 의 크레딧 낭비 문제가 절반 완화됐다.** 개수 기반
  `INCRBY` 는 떠난 사람의 자리를 소모했는데, `ZRANGEBYSCORE` 는 실제 구성원을 집는다
