# 서명 없는 값을 검사하는 것은 방어가 아니다

## 무엇을 만들었나

회원 헤더의 형식만 보는 필터. 값 자체는 안 믿는다.

## 무엇을 막고 무엇을 안 막는가

이 서비스에는 로그인이 없다. 회원 식별자와 등급을 헤더로 받고 **위조가 자유롭다.**
그러니 여기서 하는 일은 신원 확인이 아니다 — 깨진 값이 뒷단까지 흘러가서 거기서
터지는 것을 막는 것뿐이다.

남의 자리를 건드리는 것은 게이트웨이가 서명한 토큰이 막는다. 헤더를 바꿔 봐야
얻는 것이 없어야 한다.

## 라우트가 아니라 필터에 둔다

순번 조회는 게이트웨이 라우트를 안 탄다 — 게이트웨이가 직접 답하기 때문이다.
라우트 필터로만 검사를 붙이면 **정확히 그 경로가 통째로 뚫린다.**

필터 계층이 게이트웨이 라우트와 직접 응답 양쪽에 걸리는 유일한 자리다.

## 앞뒤를 값으로 못 박는다

CORS 필터와 이 필터의 순서를 안 정했더니 사전 요청이 막혔다. 브라우저는 사전
요청에 회원 헤더를 안 붙이는데, 형식 검증이 앞서면 그게 400 이 되고 브라우저는
본 요청을 아예 안 보낸다 — 대기 화면이 통째로 안 돈다.

선언 순서에 기대면 파일 안에서 자리를 옮기는 것만으로 다시 깨진다. 값으로 적었다.

## 자릿수 판정을 넓게 쓰면 안 된다

표준 라이브러리의 숫자 판정은 아라비아 숫자 밖의 자릿수도 참이다. 그걸 쓰면
`١٢٣` 가 통과해 뒷단에서 파싱이 터진다. 문자 범위를 직접 본다.

앞의 0 도 안 받는다. 받으면 같은 사람이 `1` 과 `01` 두 값이 되고, 그게 리미터
키와 캐시 키가 되면 상한이 두 배가 된다.

## 이유를 안 나눈다

어느 헤더가 왜 틀렸는지 알려 주면 형식을 맞추는 데 쓰인다. 봉투는 발급 계층과
같은 것을 쓴다 — 다르면 클라이언트가 게이트웨이 응답과 뒷단 응답을 다르게
다뤄야 한다.

## 어떻게 검증했는가

| 되돌린 것 | 죽는 시험 |
|---|---|
| 검증 통째로 제거 | 식별자가_수치가_아니면_막는다 · 등급이_아는_값이_아니면_막는다 · 순번_조회에도_걸린다 외 |
| 관리 경로 제외 제거 | 관리_경로는_안_본다 |
| 등급 검사 제거 | 등급이_아는_값이_아니면_막는다 |
| 자릿수 판정을 넓힘 | 식별자가_수치가_아니면_막는다 (아라비아 숫자 밖) |
| CORS 를 뒤로 보냄 | 사전_요청은_회원_헤더_없이_통과한다 외 CORS 전건 |

## 고려했으나 버린 것

- **게이트웨이 라우트 필터로 붙이기.** 순번 조회가 빠진다. 이 절이 존재하는
  이유가 그것이다.
- **헤더를 정규화해 뒷단에 넣어 주기.** 인증 계층이 없어 넣을 검증된 신원이 없다.
  정규화한 값을 넣으면 뒷단이 그걸 검증된 것으로 오해할 여지가 생긴다.
- **등급으로 판정하기.** 자격 대조는 발급 계층 몫이다 (비목표).

## 확신이 낮은 부분 · 남은 위험

**등급 목록이 사본이다.** 발급 계층 명세에 적힌 네 값을 여기 다시 적었다.
거기서 등급이 늘면 여기가 막는다. 계약을 기계로 잇는 자리가 아직 없다.

**식별자 상한을 자릿수로 잡았다.** 뒷단이 어떤 정수 폭을 쓰는지 계약에 없어서
19자리로 뒀다. 그보다 좁으면 통과시킨 값이 거기서 넘친다.

**폴링 경로의 부하를 안 쟀다.** 이 필터는 모든 요청을 지난다. 헤더 두 개를
보는 비용이지만, 실측은 부하 시험 자리다.
