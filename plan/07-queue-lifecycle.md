# Phase 7 — Queue Lifecycle

> 큐에 **들어가는** 경로는 Phase 5에서 만들었다. 이 페이즈는 **나가는** 경로다.
> 매진·이탈·유예는 별개의 사건처럼 보이지만 **"큐에서 사라져야 하는데 사라지지
> 않는 사람"**이라는 하나의 누락된 개념이다. 함께 설계해야 중복 작업이 없다.

**선행**: Phase 4, Phase 6 · **상세 수준**: 제목 + 근거 (진입 시 승격)

---

## Goal

> **큐에서 나가야 할 사람이 반드시 나간다 (R3).**
> 매진·이탈·유예 만료 — 세 경로가 전부 동작한다.

| 통과 수치 | |
|---|---|
| 매진 후 종료 신호 수신 | **1회 폴링 내** |
| `SOLD_OUT` 응답 시 Redis 명령 | **0건** |
| 매진 쿠폰의 백엔드 도달 요청 | **≤ 노드 수** (노드당 1건) |
| 이탈 30% 주입 시 크레딧 낭비 | **< 5%** |
| 매진 쿠폰이 `pollScale` 에 주는 영향 | **0** |

기존 구현에는 **입장 경로만** 있었다. 나머지 셋이 없어 매진 시 대기자가
영구히 갇히고, 이탈자가 크레딧을 허공에 소비했다.

## 2. 큐에서 나가는 네 가지 경로

| 경로 | 트리거 | 결과 |
|---|---|---|
| **입장** | `score <= admitted` | ZREM + 입장 토큰 |
| **매진** | `remainingStock <= 0` | `SOLD_OUT` 응답 + 큐 일괄 정리 |
| **이탈** | `alive` 의 만료 시각이 지남 | ZREM + grace 에 **재방문자로 기록** (자리는 보관하지 않는다 — D-11) |
| **유예 만료** | grace 보관 기간 경과 | 완전 삭제 |

> **grace 는 자리 보관이 아니다.** 원래 score 로 되돌리면 그 사람 뒤에 있던
> 사람들의 순위가 1 늘어나 **순위 역행 0 이 깨진다**. 재입장은 새 score 로 하고,
> 대신 `alive` 의 수명을 넉넉히 잡아 **grace 로 떨어지는 일 자체를 드물게** 만든다
> ([90-decisions.md](90-decisions.md) D-11).

기존 구현은 **입장 경로만** 있었다. 나머지 셋이 없어서:

- 매진 시 대기자가 `WAITING` 상태로 영구 고정 (`etaSec=-1`, 30초마다 영원히 폴링)
- 이탈자가 ZSET에 영구히 남아 `ZCARD`가 유령을 포함

> **score 전환(A-9)으로 절반이 완화됐다.** 입장 임계를
> `ZRANGEBYSCORE ... LIMIT N-1 1` 로 잡으면 실제 구성원 N명을 집으므로,
> 개수 기반 `INCRBY` 처럼 **떠난 사람의 자리를 소모하지 않는다** (D-8).
> 남은 것은 `waiting` 표시값의 과대이고 그건 D-9 의 표본 보정이 다룬다.
- grace에 **쓰는 코드가 없어** 유예 재입장 로직 전체가 데드코드

## 3. 매진 처리 — 세 겹

### 3.1 왜 게이트웨이가 재고를 판단해도 되는가

스냅샷은 최대 1.5초 낡는다(스케줄러 1s + 갱신 500ms). 그럼에도 매진 방향의
판정을 게이트웨이가 종결해도 안전한 이유는 **오판이 한 방향뿐이고 스스로 낫기**
때문이다 — 위험한 방향(매진인데 통과 = 초과 발급)은 재고가 줄기만 하는 구간에서
일어나지 않고, 안전한 방향(재입고 직후 `SOLD_OUT`)은 다음 스냅샷이 되돌린다.

| 판정 오류 방향 | 가능한가 |
|---|---|
| `stock<=0`으로 봤는데 실제로는 재고가 있다 | **재입고 직후 최대 1.5초** 가능. 다음 스냅샷이 되돌린다 (B-11) |
| `stock>0`으로 봤는데 실제로는 매진 | 가능. 백엔드가 `409` + `COUPON-306` 으로 처리 (B-10) |
| **재고를 못 읽었는데 0 으로 접었다** | 가능. 아래 참조 — 자동으로 안 낫는다 |

**negative cache 를 영구 보관하지 않는 이유가 이것이다** (B-11) — 캐시가 스냅샷보다
오래 살면 자동 회복이 안 된다.

**셋째 줄은 위 둘과 성질이 다르다.** `AllocationRedisPort.stocks` 는 재고 키가
없으면 그 쿠폰을 아예 안 담고, `DemandCollector` 가 빈 자리를 0 으로 접는다.
"못 읽었다" 와 "다 팔렸다" 가 같은 값이 되므로, 재고 키를 잃은 쿠폰은 줄에 사람이
남아 있어도 `CLOSED` 가 되어 종결된다 — 재고가 실제로 돌아오는 것이 아니라서
스냅샷도 이것을 안 되돌린다.

지금은 상태 기계가 `waiting>0` 을 함께 요구해 줄이 빈 쿠폰까지 끊는 것은 막았지만,
접힘 자체는 남아 있다. 미상과 0 을 자료형에서 가르는 일은 제어 평면의 계약을
바꾸므로 별도 티켓으로 뗀다 → [`CY-702`](https://shseol.atlassian.net/browse/CY-702).

**이 근거를 코드 주석에 남긴다** — "왜 게이트웨이가 재고를 판단하냐"는 반박에
그대로 답이 된다.

### 3.1.1 명시적으로 받는 노출 — 이미 입장한 사람

`queue_status.lua` 는 큐에 없는 사람을 만나면 grace 해시의 입장 표시(`a:`)를
먼저 본다. 그 분기가 있는 이유는 하나다 — **자기 차례를 받은 사람이 응답을
놓쳤을 때 다시 서서 뒤로 밀리지 않게 하는 것**(불변식 4).

매진 종결은 그 스크립트가 돌기 전에 답을 내므로 이 분기를 건너뛴다. 배분이
크레딧을 이미 쓴 사람이 종료를 통보받을 수 있다.

**그런데도 이 노출을 받는다.** 재고가 0 이면 그 사람이 다시 서도 받을 것이
없고, 발급 계층도 `409` + `COUPON-306` 으로 튕긴다. 다시 서지 않으므로 **뒤로
밀리지도 않는다** — 불변식 4 가 막으려는 것은 추월이지 종료가 아니다.

노출이 실제 손해가 되는 구간은 하나다: 재입고됐는데 게이트웨이가 든 스냅샷은
아직 `stock` 이 0 이라고 말하는 창. 그 창에서 입장자가 종료를 받으면 자기 몫과
입장 토큰을 잃는다.

**창의 길이가 곧 손해의 상한이다.** 다음 발행까지가 보통 1.5초(스케줄러 1s +
갱신 500ms)이고, 발행이 밀려도 낡음 한계를 넘으면 `isDataStale` 이 참이 되어
종결 자체가 꺼진다. 그래서 상한은 **낡음 한계**이고, 그것이 이 종결을 받아들일
수 있는 이유다.

로컬로 좁힐 수 있는 길은 요청이 유효한 `EntryToken` 을 실어 올 때 단락을
건너뛰는 것인데, **응답 유실 케이스는 못 덮는다** — 토큰을 못 받은 사람이
문제이기 때문이다. 그래서 좁히지 않고 받아 적는다.

### 3.2 세 겹의 방어

```
1겹 — 스냅샷:        stock <= 0 → REJECT_SOLD_OUT (판정 최우선, Phase 2 4.5)
2겹 — negative cache: 백엔드 409 + `COUPON-306` 관찰 (B-10). 노드 로컬 기록
3겹 — 큐 종결:       CLOSED 상태에서 폴링 시 Redis 안 치고 SOLD_OUT 반환
```

2겹의 효과: 노드당 최초 1건만 백엔드에 도달한다. 20대면 20건.

### 3.3 매진이 폴링 예산을 잠식하는 문제

`expectedPollRps(waiting, drainRate=0)`은 `waiting / 30`을 반환한다.
10만 명이 갇히면 **3,333 RPS**로 계산되어 예산 4,000의 83%를 죽은 큐가 먹는다.
그 결과 `pollScale`이 올라 **살아 있는 쿠폰의 대기자까지 폴링 간격이 늘어난다.**

`FairShareAllocator`가 쿠폰 간 기아를 구조적으로 막아둔 것과 정확히 반대 방향의
누수다. 배분은 격리했는데 폴링 예산은 격리가 없었다.

→ Phase 2의 `PollBudgetPlanner`(2.5.4)에서 비활성 쿠폰을 제외한다.
이 페이즈에서는 큐를 실제로 비워 근본 원인을 없앤다.

#### 3.3.1 그 계산에는 호출부가 없었다 (CY-723)

`PollBudgetPlanner` 는 프로덕션에서 아무도 안 불렀고 배수는 어디서나 1.0 이었다.
비활성 쿠폰을 빼는 필터는 정확했지만 그 함수가 안 돌았으므로, 죽은 큐가 예산을
먹든 안 먹든 운영에서는 같았다. 이제 한 판이 배수를 내어 스냅샷 메타에 싣고,
조회·등록·거절 응답이 그것을 지킨다. 예산의 단위는 노드다.

**배수는 폴링 간격 상한 60초까지만 유효하다.** 가장 먼 밴드(30초)에서는 배수 2
이상이 전부 같은 값이 되므로, 그 위는 노드 증설이나 죽은 큐 정리로만 줄어든다.
상한을 올리면 생존 신호 수명이 같이 늘어 이탈 판정이 느려진다 — 맞바꿈이다.

**천장은 흔들림의 위쪽 끝에 건다.** 흔든 뒤에 자르면 상한 위로 흩어진 값이 전부
상한 하나로 모여, 배수가 걸린 밴드에서 지터가 정확히 0 이 된다 — 그 밴드 전원이
같은 초에 돌아오고, 그것이 조회 상한을 다시 밀어 올려 파도를 주기마다 재생산한다.
그래서 실효 평균은 60 이 아니라 60/(1+지터) 다.

**차례가 온 사람은 배수에서 뺀다.** 그는 이미 줄에서 빠졌고 손에 든 것은 수명
있는 토큰뿐이라, 배수만큼 멀리 보내면 토큰이 죽어 줄 맨 뒤에 새 순번으로 다시
선다 (불변식 3·4). 예산 모델도 이 요청을 안 센다 — 조회 폴링만 세므로 늘려도
예산은 안 줄고 토큰만 죽는다. 폴백과 보호 차단의 토큰 갈래가 같다.

근거와 버린 대안은 [AIJ-0143](../ai/journal/2026/08/AIJ-0143-poll-scale-wiring.md).

## 4. 이탈자 청소 — 한계를 먼저 인정한다

### 4.1 왜 앞부분만 검사하는가

20,000명 전수 검사는 틱마다 불가능하다. 큐 앞부분 K명만 검사한다
(`K = admit × 안전계수`) — 이번 틱에 배수할 인원 근처만 정확하면 크레딧 낭비는 막힌다.

### 4.2 그러나 이것으로 해결되지 않는 것

**K 뒤의 유령은 남는다.** 따라서:

| 항목 | 앞부분 검사로 해결 | 남는 문제 |
|---|---|---|
| 크레딧 허공 발행 | ✅ | |
| 배수 대상 정확도 | ✅ | |
| `ZCARD` 정확도 | ❌ | ETA가 실제보다 길게 표시 |
| 폴링 예산 계산 | ❌ | `pollScale`이 과대 |

ETA 정확도까지 필요하면 별도 대책이 든다 → [90-decisions.md](90-decisions.md) D-Q1:

- (a) 유령 비율을 표본으로 추정해 `ZCARD`에서 차감
- (b) 큐 전체를 순회하는 저속 배경 스위퍼를 따로 둠
- (c) 오차를 감수하고 ETA를 보수적으로(길게) 표시

**(a)를 권장한다.** 표본 100명의 alive 신선도로 전체를 보정하면 비용이 거의 없고,
ETA 오차는 통계적으로 유계다. Phase 9의 순위 추정과 같은 성격의 근사다.

### 4.3 Redis 키스페이스 알림을 쓰지 않는 이유

`expired` 이벤트는 **배달 보장이 없다.** 구독자가 잠깐 끊겨도 그 사이 만료된
항목을 영영 못 받고, 못 받았다는 사실도 모른다. 스케줄러 틱에서 폴링하는 방식은
언제 시작해도 현재 상태를 본다 — 스냅샷을 폴링으로 만드는 것과 같은 논리다.

### 5.1 매진 상태 모델 (Phase 2 확장 적용)

|---|---|---|

| 7.1.2 | `CLOSED`가 배분 대상에서 제외됨 | credit 0 |
| 7.1.3 | 조회 응답에 `status:"SOLD_OUT"` · `reason:"STOCK_EXHAUSTED"` | 값으로 단언 |
| 7.1.4 | 순번 조회 시 `RuntimeState.CLOSED` 면 **Redis 미호출** | 왕복 0건 계측 |
| 7.1.5 | 매진 응답에 `Retry-After` 미부착 | 재시도 유도 금지 |
| 7.1.6 | 매진 단락이 **조회 상한보다 앞** | 상한이 차도 종결 |
| 7.1.7 | 줄에 없는 경우는 `reason:"NOT_IN_QUEUE"` | 매진과 사유가 갈림 |

### 5.2 매진 negative cache

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 7.2.1 | `SoldOutCache` — 노드 로컬 맵 | |
| 7.2.2 | 백엔드 매진 응답 감지 | `409` + `COUPON-306` 을 함께 본다 |
| 7.2.3 | 판정 앞단에서 캐시 조회 | 두 번째 요청은 백엔드 미도달 |
| 7.2.4 | **관찰보다 나중에 발행된** 재료가 `stock>0` 이면 해제 | 재입고 대응 |
| 7.2.5 | 절대 TTL (안전판) | 해제 신호를 놓쳐도 무한 지속 안 함 |
| 7.2.6 | 맵 크기 상한 | 미지 쿠폰으로 증식 불가 (Phase 5 5.3.4와 연동) |
| 7.2.7 | 관찰 횟수·담긴 수·상한 | 상한에 닿는 순간이 보여야 한다 |

**7.2.4 의 "나중에" 가 핵심이다.** "지금 `stock>0` 이면 해제" 로 쓰면 관찰을
만든 바로 그 재료가 관찰을 지운다 — 캐시가 존재하는 창이 곧 "재료는 아직
재고를 말하는데 뒷단은 이미 매진" 인 창이라, 그 창의 상태로 캐시를 판단하면
논리가 자기를 무너뜨린다. 발행 시각을 비교해야 "재입고를 봤다" 가 성립한다.

**낡은 재료에서도 계속 끊는다.** 사다리 1번(스냅샷 `stock<=0`)이 낡음을 견디는데,
뒷단이 낸 `409` 는 그보다 직접적인 증거다. 약한 증거만 낡음을 견디면 비대칭이고,
그 비대칭은 **낡음이 뜨는 순간 전 노드에서 동시에** 매진 보호를 끈다 — 나이가
같은 재료에서 파생되므로 노드들이 같은 초에 뒤집힌다. 뒷단 유입이 0 에서 노드
상한으로 한 번에 뛴다.

**대신 해제를 낡은 재료로는 안 한다.** 낡음은 못 믿겠다는 뜻인데, 못 믿는 재료로
방패를 부수는 것만 허용하면 방향이 한쪽으로만 열린다. 특히 회복 첫 판에 도착한
스냅샷이 장애 중 쌓인 관찰을 전부 지우면 회복 순간에 다시 몰린다. 잘못 든 관찰은
절대 TTL 이 푼다 — 그것이 7.2.5 가 있는 이유다.

### 5.2.1 조회 경로는 캐시를 안 본다

`QueueStatusFilter`(7.1)는 스냅샷만 본다. 그래서 재료가 아직 재고를 말하는 창에서
**신규 유입은 종결을 받고 줄 선 사람은 계속 기다린다** — 줄 안 선 사람이 먼저 끝을
안다. 추월은 아니지만 방향이 반대다.

일부러 이렇게 둔다. 이 관찰은 **발급을 시도했다가 거절당한 사실**이고, 줄 선
사람에게 그것은 "네 차례가 오면 못 받는다" 를 뜻하지 않는다 — 관찰을 만든 요청은
줄을 앞지른 신규 유입이었을 수도 있다. 조회까지 이 관찰로 종결하면 **관찰 하나로
5만 명의 줄을 끊는** 셈이고, 잘못 든 관찰(요청별 사유로 인한 `COUPON-306`)이
그대로 그 규모의 사고가 된다.

창의 길이는 다음 발행까지, 길어도 낡음 한계다. 그 뒤에는 스냅샷이 `CLOSED` 를
싣고 조회도 종결한다.

**차례가 온 사람도 이 창에서는 끊긴다.** 관찰은 사다리 1번과 같은 자리, 곧
토큰 검사(2번)보다 **위**다. 그래서 조회는 "곧 차례" 라고 말하는데 발급은
매진으로 끊는 순간이 같은 노드 안에 생긴다.

재고가 정말 0 이면 그게 맞는 답이다 — 토큰이 있어도 받을 것이 없다. 위험한 것은
**잘못 든 관찰**(CY-708)이고, 그때는 기다린 사람이 신규 유입보다 먼저 잘린다.
5.2.1 이 조회를 캐시에서 떼어 놓은 이유와 정확히 같은 위험이 발급 경로에는
남아 있다는 뜻이다. 관찰 조건을 좁히는 것이 CY-708 의 본론이다.

| 7.3.1 | `CLOSED` 관측 후 N틱 유예 뒤 **줄과 생존 신호만** 삭제 | 나머지 키가 남음 |
| 7.3.2 | 유예 시간 설정화 | **폴링 최대 간격(60초)보다 클 것** |
| 7.3.2b | 유예 중 `stock>0` 을 보면 삭제를 취소 | 재입고 시 원래 순번이 남음 |
| ~~7.3.3~~ | ~~`coupons:active` 에서 제거~~ | **철회.** 아래 참조 |
| 7.3.4 | 정리 실패가 배분을 막지 않음 | 다음 틱 재시도 |
| 7.3.5 | 리더가 아니면 안 지움 | 판 안의 유일한 비가역 쓰기 |

**7.3.3 을 철회한다.** 활성 목록에서 빼면 그 쿠폰이 스냅샷에서 사라지는데,
**없는 쿠폰은 매진 쿠폰이 아니다.** 조회는 `state == null` 이라 종결을 안 하고
레디스로 내려가고, 발급은 사다리 1번 대신 미지 쿠폰 경로로 가서 404 를 내며,
재료가 낡으면 그 경로가 **fail-open 으로 뒷단에 흘린다.** 사다리 1번이 낡음보다
앞에 있는 이유(매진 쿠폰이 fail-open 상한을 갉아먹지 않게)를 재료에서 쿠폰을
빼는 방식으로 우회하는 셈이다. 게다가 이 집합은 `cy-be` 소유이고(O-3) 게이트웨이
쪽에 다시 넣는 코드가 없어 **복구 경로 자체가 없다.**

틱당 명령 수는 줄을 지우는 것만으로 준다 — `ZCARD` 가 없는 키에 0 을 내므로
그 뒤로는 왕복이 하나로 줄고, 폴링 예산 계산에서도 `waiting` 이 0 이 된다.

**지우는 것을 줄과 생존 신호로 좁힌다.**

| 키 | 지우나 | 왜 |
|---|---|---|
| `queue:{cid}` | 예 | 이것이 폴링 예산을 먹는 본체다 |
| `alive:{cid}` | 예 | 줄이 없으면 생존 신호도 뜻이 없다 |
| `admitted:{cid}` | **아니오** | 입장 임계다. 지우면 임계가 뒤로 가고, A-7 이 세운 단조성이 깨져 **이미 입장한 사람이 두 번째 토큰**을 받을 수 있다 |
| `grace:{cid}` | **아니오** | `a:` 입장 표시가 여기 있다. 차례가 왔던 사람이 종료를 안 받게 막는 유일한 장치이고 보관이 5분이다 |
| `maxscore:{cid}` | **아니오** | 시계 역행 바닥값(A-9). 지우면 승격된 복제본에서 새 score 가 앞으로 가 줄 선 사람이 통째로 추월당한다 |

**유예 기준은 낡음 한계가 아니라 폴링 최대 간격이다.** 마지막 폴링이 언제
오는지를 정하는 것은 우리가 클라이언트에게 준 간격이고, 먼 밴드는 60초를 받는다.
낡음 한계(5초)로 잡으면 그 사람이 다시 왔을 때 줄이 이미 없다. 기본은 90초다.

### 5.3.1 배선을 잇기 전에 있어야 하는 것

정리는 이 저장소에서 **되돌릴 수 없는 유일한 쓰기**다. 그래서 판단만 돌리고
실제 삭제는 아직 안 잇는다. 세 가지가 갖춰져야 잇는다.

| 조건 | 왜 |
|---|---|
| **재고 미상과 재고 0 을 가름** (CY-702) | 자동으로 안 낫는 오판이 자동으로 되돌릴 수 없는 삭제가 된다 |
| **삭제 직전의 재고 확인** | 수집과 삭제 사이에 재입고되면 살아난 줄을 지운다. 메모리 안의 취소는 **다음 스냅샷이 와야** 도는데, 삭제는 그 전에 나간다 |
| **리더십 울타리** | 지역 검사는 울타리가 아니다. 검사와 삭제 사이에 리스가 끝나면 옛 리더가 새 리더의 줄을 지운다. 소유권을 레디스가 확인해야 한다 |

가운데 것은 `stock` 키를 삭제 스크립트에서 직접 읽어 풀 수 없다 — 지금은
`queue:{cid}` 와 같은 슬롯이지만 샤딩을 켜면 태그가 갈린다. 큐와 같은 슬롯에
**재고 세대**를 두고 그것을 비교하는 형태라야 한다.

**`waiting == 0` 을 조건으로 못 쓴다.** 매진 쿠폰에서 그 값을 줄이는 주체가
하나도 없다 — 크레딧이 0 이라 아무도 입장으로 안 빠지고, 폴링은 게이트웨이가
종결하므로 큐에서 빼는 스크립트가 안 돌고, 스위퍼는 5.4 절대로 매진 중 멈춘다.
줄을 지우는 것이 곧 `waiting` 을 0 으로 만드는 일이다.

### 5.4 이탈자 sweeper

**`alive` TTL 과 스위퍼**

| 설정 | 기본값 | 관계 |
|---|---|---|
| `alive` TTL | **250s** | 최대 폴링 간격(60초)의 네 배 + 여유 10초. 세 번 놓쳐도 안 지워진다. 정책이 내는 값이고 코드는 `PollIntervalPolicy.aliveTtl()` |
| grace 보관 | **6m** | 재방문자 식별 구간. `max(300s, 입장 토큰 수명 × 2)` 이고 코드는 `GraceRetention.SECONDS` |

**장애 중에는 스위퍼를 멈춘다.** `alive` 는 사용자가 폴링할 때 갱신되는데
장애 중에는 폴링이 실패해 갱신이 끊긴다. 그 상태로 스위퍼가 계속 돌면

```
장애로 폴링 실패 → alive 갱신 끊김 → 장애가 TTL 보다 길면
  → 성실히 줄 선 사람이 이탈자로 판정 → ZREM + grace
  → 회복 후 재입장은 새 score (D-11) → 줄 맨 뒤
```

**`RC5`(장애 중 자기 자리 유지)가 장애가 아니라 우리 청소 로직 때문에 깨진다.**

**매진 중에도 같은 이유로 멈춘다.** 7.1 이 매진 조회를 게이트웨이에서 종결하면서
그 쿠폰의 폴링은 `queue_status` 를 안 부른다. 생존 신호를 갱신하는 곳이 거기
하나뿐이므로, **매진으로 보이는 동안 줄 선 전원의 `alive` 가 일제히 멎는다.**
장애 문단과 글자 그대로 같은 사슬이다 — TTL 을 넘기면 성실히 줄 선 사람이
이탈자로 판정되고, 재입장은 새 score 다.

| 스위퍼가 도는가 | 조건 |
|---|---|
| 아니다 | 장애 중 (위 문단) |
| **아니다** | **쿠폰이 `CLOSED` 인 동안** — 폴링이 멎은 것이지 사람이 떠난 것이 아니다 |
| 그렇다 | 그 밖 |

이것이 **7.1 의 종결이 순번을 안 깨뜨리는 조건**이다. 7.4 를 붙일 때 이 줄을
빠뜨리면 매진 종결이 곧 전원 이탈 판정이 된다. 큐를 통째로 지우는 7.3 과 달리
스위퍼는 개별 항목을 빼므로, 7.3.2b 가 큐 키를 살려 둬도 그 안이 이미 비어 있다.

**이 순서는 뒤집을 수 없다.** 7.4 가 7.1 보다 먼저 들어가면 그 사이에 매진되는
쿠폰의 줄이 통째로 걷힌다.
그래서 `7.4.8` 로 `dataStale` 중 sweep 을 멈추고, `7.4.9` 로 회복 직후 한 틱을
건너뛴다 — 밀렸던 폴링이 `alive` 를 다시 채울 시간을 준다.

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 7.4.1 | `QueueSweeper` — 리더만 실행 | 중복 실행 없음 |
| 7.4.2 | **입장 임계 위** 앞부분 K명 검사 | 유령이 창을 막지 않는다 |
| 7.4.3 | K를 `admit × 계수`로 산정 | |
| 7.4.4 | alive 없는 항목 ZREM + grace HSET | **grace에 항목이 실제로 쌓임** |
| 7.4.5 | grace 보관 기간 만료 정리 | |
| 7.4.6 | sweep 메트릭 | |
| 7.4.7 | **`waiting` 표본 보정** (D-Q1 (a) 채택 시) | ETA 오차 유계 |
| **7.4.8** | **`dataStale` 중에는 쓸어내지 않는다** | 장애가 대량 이탈로 오인되지 않는다 |
| **7.4.9** | 회복 후 **생존 신호 수명 + 최대 폴링 간격**만큼 쉬고 재개 | 갱신이 밀린 `alive` 가 먼저 채워진다 |
| 7.4.10 | **신호가 통째로 없으면 아무것도 안 한다** | 저장소 유실이 전원 이탈로 안 읽힌다 |
| 7.4.11 | 입장 임계 이하는 안 걷는다 | 차례가 온 사람이 종료를 안 받는다 |
| 7.4.12 | **임계 위의 입장 표시는 이탈 기록으로 덮는다** | 표시만 남으면 다음 폴링이 입장으로 읽는다 |

**"한 틱" 은 틀렸다.** 생존 신호는 마지막 폴링에서 TTL(250초)만큼 살고 그 폴링은
최대 간격(60초)만큼 늦게 온다. 매진이 그보다 길면 그 사이 전원의 신호가
만료되고, 재입고 다음 틱에 임계 위 K명이 통째로 걷힌다.

**유예만으로는 부족하다.** 그 셈은 리더 메모리라 승계에서 사라지고, 쿠폰이 활성
목록을 드나들어도 사라진다. 그래서 스크립트에 마지막 방벽을 둔다 — 줄에 사람이
있는데 신호가 **하나도 없으면** 그것은 전원 이탈이 아니라 저장소 유실이다.

**이 방벽을 검사 창 안으로 좁히면 안 된다.** 좁히면 지키려던 판을 못 지키면서
정상 판을 막는다. 회복 구간은 정의상 누군가 먼저 돌아오는 판이라 창 안에 살아난
한 명이 생기고, 그 한 명이 나머지를 걷는다 — 좁혀도 결과가 같다. 반대로 창 안이
전부 진짜 이탈자면 아무도 못 걷어 그 창이 영영 안 열리고, 크레딧이 0 이면 임계가
안 움직여 그 상태가 굳는다. 회복 구간을 지키는 것은 재개 유예이고, 그것이 리더
메모리라 승계에서 사라지는 것이 진짜 구멍이다 — 레디스로 내려야 풀린다.

### G7.5 를 왜 구간으로 한정하는가

이탈자는 **생존 신호가 만료되어야** 걷힌다. 그 전에 차례가 오면 크레딧이 나가고,
그것은 어떤 구현으로도 못 막는다 — 그 사람이 떠났다는 것을 알 방법이 아직 없기
때문이다. 그래서 판 전체로 재면 낭비율이 이렇게 수렴한다.

```
낭비율 ≈ 이탈률 × (생존 신호 수명 + 청소 재개 유예) / 판 길이
```

이 값은 기구의 성능이 아니라 **판을 얼마나 길게 잡았는지**를 잰다. 이탈 30%·수명
250초·유예 60초를 넣으면 5% 미만은 판이 31분을 넘어야 나오고, 판을 두 배로 늘리면
아무것도 안 고쳐도 절반이 된다. 기준이 구현을 안 가른다.

**기구가 책임지는 구간은 그 뒤다.** 대기 시간이 수명을 넘은 사람에 대해서는
스위퍼가 손 쓸 시간이 있었고, 거기서 낭비가 남으면 그것은 기구의 결함이다.
하네스는 크레딧을 그 시간만큼 0 으로 붙잡아 모든 입장을 그 구간에 넣는다.

**워밍업 구간의 손실은 따로 적는다.** 없어지는 것이 아니라 수명과 유예에서
직접 나오는 값이라, 줄이려면 그 둘을 줄여야 한다 — 그리고 둘 다 줄이면 성실히
줄 선 사람이 걷힐 위험이 커진다. 맞바꿈이지 결함이 아니다.

  상수 하나가 판정을 뒤집고 있었다. 하네스 자체도 아직 판정 도구가 아니다
  (실측 대 모델, 과잉 청소 미검출, 새 지표 미사용, CI 미배선).

  배선이 끊겨 있다. 판단만 돌려 지표로 관찰한다.
- G7.10 은 D-Q1 (a) 를 안 채택했으므로 해당 없음.

**문턱은 하나도 안 내렸다.** 둘이 닫히기 전에는 Phase 8 을 시작하지 않는다.
