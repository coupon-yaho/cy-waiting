# 메모리 상한에서 후임이 리더를 못 잡았다

## 무엇을

레디스는 `noeviction` 이라 한도에 닿으면 메모리를 늘리는 명령만 거부한다. 리더 스크립트에서 연장은
만료만 고치는 `PEXPIRE` 라 거부되지 않고, 신규 획득은 `SET NX` 와 세는 값의 `INCR` 이라 거부된다.

그래서 쓰기가 막힌 동안 리더가 죽거나 배포로 내려가면 아무도 락을 못 잡는다. 쓰기가 풀려도 선거를 다시
거쳐야 배분이 돈다.

## 재현

통합 시험에서 `maxmemory` 를 사용량 아래로 내리고 비어 있는 락을 잡게 했다. 신규 획득이
`OOM command not allowed when used memory > 'maxmemory'. script: ...` 로 실패했고 연장은 통과했다.
시험은 컨테이너를 나눠 쓰므로 원래 한도를 반드시 되돌린다.

## 고친 것

리더 스크립트 첫 줄에 `#!lua flags=allow-oom` 을 붙였다. 레디스 7 의 스크립트 플래그로, 그 스크립트 안의
쓰기만 한도를 무시한다. 쓰는 것은 리더 키와 세는 값 둘이라 넘치는 양이 몇십 바이트다. 리더가 없는
배분 정지가 그보다 훨씬 무겁다.

다른 스크립트에는 안 붙였다. 줄 등록이나 배분 적용이 한도를 무시하면 메모리가 계속 는다.

## 어떻게 검증했나

- 신규 획득 시험이 고치기 전 빨갛고 고친 뒤 초록, 연장 시험은 전후 초록
- 리더 선출 시험 27건, 클러스터 모드 스크립트 시험 통과

## 로컬 리뷰가 고친 것

- **해제 조건을 만든 것처럼 적었다.** 새 리더의 봉인·적용·발행과, 메모리를 줄일 매진 큐 삭제·이탈자 청소가 모두 첫
  쓰기에서 같이 거부된다. 이번 수정은 후임이 서서 쓰기가 풀리는 순간 선거 공백 없이 재개하는 것까지다
- **셔뱅이 스크립트 머리 주석 검사를 깨뜨렸다.** 머리를 첫 줄부터 읽어 셔뱅에서 멈췄다. 리더·클러스터 시험만 돌려
  놓쳤다. 첫 줄의 셔뱅을 건너뛰게 고치고 단위·통합 시험 전체를 돌렸다
- 연장 시험이 한도 전제를 안 봤고, 공유 컨테이너의 한도 복구를 확인하지 않았다. 전제를 공용 헬퍼로 옮기고 복구 뒤
  다시 읽어 확인한다

## 남은 것

- 한도에서의 해제 조건 — 순감소 청소 스크립트의 `allow-oom` 검토, 쓰기 복구 뒤 재봉인, 쓰기가 막힌 채 리더가
  내려가는 시나리오 (CY-932)
