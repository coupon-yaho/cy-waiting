# 인증을 걷어내고 헤더 식별자로, 그리고 앞단 LB 가 계획에 없다는 것

## 무엇을

검토에서 결함 넷을 찾아 고쳤다.

1. **Phase 5 가 존재하지 않는 JWT 를 전제**하고 있었다 → 헤더 식별자로 재작성
2. **리더 락의 연장·해제에 소유권 확인이 없었다** → Lua CAS 요구 추가 (`G4.11`)
3. **틱·락 수명 값이 없어 `G4.2` 를 판정할 수 없었다** → 타이밍 표로 명시
4. **앞단 LB 가 계획 어디에도 없다** → readiness 조건과 LB 기준선 측정을 세움

배포 형태(스케줄러가 게이트웨이와 같은 프로세스인가)도 세 문서가 갈려 있어 통일했다.

## 왜 (근거)

**1. JWT.** `00-requirements` 가 상위 PRD 12절을 근거로 사전 발급 HS256 JWT 를
제약에 넣었고 `D-A1` 이 그걸로 해소돼 있었다. 그런데 발급 계층 API 명세 v2.0 에
`Authorization` 헤더가 없고 `X-Member-Id` 가 필수다. 게이트웨이만 JWT 를 요구하면
계약이 갈린다. **구현된 계약을 정본으로 삼았다.**

서명이 없으면 위조 판별이 불가능하므로 `G5.3`(위조 → 401)은 판정 자체가
성립하지 않는 게이트였다. 방어선을 **"헤더를 믿을지"에서 "게이트웨이가 발급한
것만 믿는다"로 옮겼다** — `queueToken`·입장 토큰은 HMAC 서명이라 위조가 안 되고,
남의 자리를 건드리려면 그 토큰이 필요하다.

**2. 락.** 펜싱 토큰을 안 쓰는 근거는 다섯 줄에 걸쳐 적혀 있는데, 그보다 기본적인
소유권 확인이 빠져 있었다. STW 로 A 의 lease 가 만료되고 B 가 잡았을 때, 깨어난
A 가 그냥 `PEXPIRE` 를 걸면 **B 의 락을 A 가 연장**하고 그냥 `DEL` 하면 **B 가
리더인 채로 락만 사라진다.** 펜싱과는 다른 층위의 문제다.

**3. 타이밍.** `lease = 2틱`, `G4.2` 상한 `3틱` 으로 1틱을 여유로 뒀다. 상한에 딱
맞추면 측정 오차 한 번에 게이트가 깨진다. `C10`(STW 3초) > `lease`(2초)라 리더
교체가 확정적이다 — 경계가 겹치면 같은 시나리오가 실행마다 다른 결과를 낸다.

**4. LB.** `fetchStale` 대응 전체가 *"LB 가 이 노드만 뺀다"* 에 위임돼 있는데
(`04:97` · `06:289` · `08:170` · `90:353`) 그 LB 가 무엇인지 없었다. readiness 에
**의존성 상태를 넣으면 안 된다**는 것이 핵심이다 — Redis 나 뒷단 서킷을 넣는
순간 공유 장애가 전 노드 동시 이탈로 번져 `G4.6` 이 깨진다.

## 고려했으나 택하지 않은 것

- **JWT 를 게이트웨이만 도입** — 상위 PRD 를 따르는 길이지만 발급 계층과 계약이
  갈린다. 헤더를 지우고 검증된 subject 를 주입하는 원래 설계는, 인증이 없으면
  **회원 식별자를 통째로 없애는** 동작이 된다.
- **매진 판정을 백엔드 응답 캐싱으로** — 네거티브 캐시는 노드마다 최초 1건이
  뒷단에 닿아야 채워지고, 그 순간이 하필 트래픽이 가장 몰린 때다. 재입고 시
  캐시를 깰 신호도 없어 TTL 만료를 기다려야 한다. 스냅샷 push 는 다음 틱에 전
  노드가 동시에 알고 `stock>0` 이 자동으로 되돌린다.
- **앞단을 L4(TCP 모드)로** — 오버헤드는 작지만 **기본 TCP 체크가 503 을 못 본다.**
  `fetchStale` 노드도 포트는 열려 있어 안 빠진다. `mode http` + `option httpchk`
  라야 계획이 요구하는 동작이 된다. `X-Forwarded-For` 를 자동으로 붙여 줘서
  IP 리미터(`5.7.3`) 배선도 같이 풀린다.
- **VIP + keepalived 로 LB 이중화** — 시험 환경은 같은 NAT 안 PC 8대다. LB
  이중화는 측정 대상이 아니고, 8대 중 한 대를 더 쓰는 값이 아깝다.
- **노드별 수요 비례 크레딧 배분** — `credit / N` 균등 분할은 게이트웨이 간 유입
  편차만큼 예산을 흘린다. 스케줄러가 하트비트로 수요를 알고 있으니 비례 배분이
  가능하지만, 사용자 판단으로 **감안하기로 했다.** `G10.1`(노드 ops 편차 ±20%)이
  깨지면 재검토한다.

## 확신이 낮은 부분

- **`lease` 2초와 `tick` 1초는 유도값이지 실측이 아니다.** `G4.3`(틱 지연 p99
  <100ms)이 실제로 얼마나 나오는지 모른 채 정했다. 틱이 밀리면 `lease` 도 같이
  올려야 한다.
- **앞단 LB 가 1GbE 에서 100K 를 감당하는지 모른다.** 대역폭은 계산상 76% 라
  들어가지만 **PPS 가 먼저 막힐 가능성**이 크다. `10.7.5` 기준선을 먼저 재기
  전에는 `G10.10` 을 판정할 수 없다고 봐야 한다.
- **`queueToken` 은 발급 계층 명세에서 가져온 것**이라 게이트웨이가 그것을 만든다는
  합의가 실제로 있는지 확인하지 못했다. 명세상 `/entry` 202 응답에 실리고
  게이트웨이가 그 응답을 직접 만드니 게이트웨이 몫이 맞을 텐데, 계약표(8절)에
  항목이 없다.
- **IP 리미터가 시험 환경에서 부하 생성기를 막는다.** NAT 안이라 출발지 IP 가
  많아야 8개다. 시험 프로파일을 따로 두어야 하는데 아직 정하지 않았다.

## 검증

- 깨진 링크 0 · 게이트 번호 중복 0 (전 페이즈 전수)
- `G9.10` 을 신설하려다 **이미 쓰이는 번호**여서 `G9.12` 로 옮김 — 번호 중복
  검사를 자동화하지 않으면 또 난다
- 카오스 시나리오 수가 본문 13개인데 요약 다섯 곳이 12로 적혀 있어 정정

## 다음 사람에게

**값을 새로 넣기 전에 그 값이 이미 유도되어 쓰이는 곳을 먼저 찾아라.**
이 세션에서 `tick-interval 500ms` 를 넣었다가, `07:55` 가 이미 *"스케줄러 1s +
갱신 500ms = 1.5초"* 로 유도해 세 문서의 안전 근거로 쓰고 있는 것을 나중에 발견해
되돌렸다. 발행 주기와 갱신 주기는 다른 값인데 하나로 뭉갰던 것이다.

같은 이유로 **스스로 만든 결함을 다음 검토에서 세 번 잡았다** — 근거 없는
`queueToken` 인용, 게이트 번호 충돌, 틱 값 충돌. 새로 쓴 문장은 기존 문서와
부딪힐 확률이 높다.
