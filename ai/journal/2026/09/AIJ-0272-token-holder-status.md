# 같은 사람이 같은 장애에서 다른 코드를 받았다

## 무엇을

차례가 온 사람이 막히는 자리가 **넷**이다. 사다리의 상한, 보호 차단(격벽 포화·
시한), 낡은 재료의 fail-open 상한, 서킷 폴백이다. **첫째만 429 를 주고 나머지
셋이 503 을 줬다.**

F8 이 이미 정한 것이다 ([02-domain-core](../../../../plan/02-domain-core.md) 3.4).

> 토큰 통과에도 tier 2를 적용하되, 초과 시 큐가 아니라 **짧은 `Retry-After` + 429**를
> 준다 — 이미 차례가 온 사람을 큐 뒤로 보내면 안 된다.

[[AIJ-0263]] 이 두 출구를 짚고 "CY-903 으로 뺐다" 고 남긴 그 항목이다.

## 셋으로 셌다가 넷이 됐다

처음에는 사다리·보호 차단·fail-open 셋으로 세고 앞의 둘만 고쳤다. 리뷰가 **서킷
폴백**을 찾았다. 그쪽은 `admitted` 로 차례가 온 사람을 이미 가려내 문구와 다시 올
시각을 따로 주면서 상태만 503 으로 박혀 있었다 — 그리고 **뒷단 장애에서 가장 자주
도는 출구**다. 나머지만 고치면 이 회차의 논거가 절반만 적용된다.

이름도 틀렸다. 셋째는 "등록 실패" 가 아니라 **낡은 재료의 fail-open 상한**이다.
등록 실패 쪽은 사다리 2번이 유효 토큰을 먼저 잡으므로 토큰 보유자가 도달할 수 없다.

## 판정에서 뽑는다

네 출구 다 판정값이나 그에 준하는 것으로 차례가 온 사람을 **이미 가르고 있었고
코드만 손으로 박고** 있었다. 보호 차단 쪽 주석은 "덮어쓴 판정으로 코드를 뽑으면
차례가 온 사람도 과부하 거절로 나간다" 며 매핑을 피했다 — 걱정은 맞고 답이
반대였다. 덮어쓰기 **전** 값으로 뽑으면 된다.

리뷰가 하나 더 짚었다. 보호 차단은 코드만 고치고 **기록하는 판정은 과부하 거절로
남겨** 두 출구가 오히려 갈렸다. 나간 응답과 적는 판정을 맞춘다 ([[AIJ-0265]] 가
fail-open 쪽에 세운 원칙이다).

## 시험 아홉이 옛 값을 못 박고 있었다

`토큰_요청` 으로 보호 차단과 fail-open 에 걸리는 시험 아홉이 503 을 단언했다.
이름은 대부분 "차례가 온 사람은 가까이 부른다" 라 `Retry-After` 가 주제이고 상태는
곁가지였는데, **그 곁가지가 계약을 반대로 고정**하고 있었다.

하나는 성격이 달랐다. `동시_건수가_배분된_몫의_세_배를_넘으면_막는다` 는 "리미터가
아니라 격벽이 막았는지" 를 판정값으로 갈랐는데, 이제 차례가 온 사람은 어느
출구에서든 같은 값을 받는다 — 그것이 이 회차가 맞춘 것이다. 출구를 세는 자로 바꿨다.

**줄에 안 선 사람의 503 은 그대로다.** 폴백과 보호 차단 양쪽에 그 사례가 있다.

## 이득이 아직 0 이다

원격 리뷰가 프런트엔드를 열어 확인했고 나도 따라 읽었다.
`coupon-magic-96` 의 `runIssue` 는 이렇게 끝난다.

```
} catch (error) {
  clearQueue();
  setPhase({ kind: "error", error });
}
```

**오류 종류를 안 가린다.** 429 도 `clearQueue()` 를 부르고 error 단계로 간다 —
게이트웨이가 코드를 바꿔도 그 사람은 여전히 입장 단계를 잃는다. 저장소 안의 모델
클라이언트(`test/load/circuit-recovery.js`)도 둘을 안 가른다.

즉 전제("503 이면 토큰을 버린다")는 맞는데 **429 여도 버린다**는 것이 이번에
드러났다. 이 회차만으로는 사용자에게 닿는 변화가 없다.

그래도 바꾼 이유는 전제와 무관하다 — F8 이 이미 정한 것을 세 출구가 안 지키고
있었고, 같은 사람이 같은 장애에서 출구에 따라 다른 코드를 받는 것 자체가 계약이
아니다. 되돌리는 조건까지 90-decisions 2.22 에 적었다.

## 어떻게 검증했나

- 네 출구 각각에서 차례가 온 사람이 429 를, 줄에 안 선 사람이 503 을 받는지
- `build` · `integrationTest` · `contextTest` 전 계층 통과
- 상태를 세는 자리를 전부 훑었다. 부하 시나리오 대부분은 429 와 503 을 같은
  바구니에 넣어 안 갈리는데, **종료 유출 판정만 갈린다** — 격벽 시한이 끊은
  차례가 온 사람이 `leaked` 에서 `turned_back` 으로 옮겨 간다. 지금 회차는 표를 든
  VU 가 없어 안 섞이지만 그 사실을 판정기 주석에 남겼다

## 남은 위험

**프런트엔드가 429 를 가려야 값이 생긴다.** 지금은 안 가린다(위 절). 게이트웨이가
옳은 코드를 내는 것과 그쪽이 그것을 옳게 읽는 것은 다르다 — CY-903 의 나머지
절반이고, 그것이 닫히기 전에는 이 회차의 이득이 0 이다.

**G6.1 의 문장을 좁혔다.** "서킷 강제 오픈 → 503" 에서 "404 아님. 줄에 선 사람 503 ·
차례가 온 사람 429" 로 바꿨다. 게이트의 뜻(폴백이 404 로 보이면 안 된다)은 그대로다.
