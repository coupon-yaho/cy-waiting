# 하한을 램프가 깎은 만큼까지 되돌린다

## 무엇을

`CapacityCollector.collect` 의 하한 조건을 바꿨다. 전에는 신선한 보고가 하나도
없거나 램프가 합을 정확히 0 으로 접었을 때만 하한을 썼다. 이제는 램프가 깎기
전 합(`reported`)을 같이 세어, 뒷단이 가진 것과 하한 중 작은 쪽까지 되돌린다.

```java
long credit = fresh == 0 ? minimum : Math.max(total, Math.min(minimum, reported));
```

`anyPositive` 는 `reported > 0` 에 포함되므로 없앴다.

## 왜 (근거)

하한이 0 에만 걸려 **0 과 하한 사이가 통째로 비어 있었다.** 램프는 합을 0 으로만
접는 것이 아니라 그 사이 어디로든 접는다.

게이트웨이 8노드, 뒷단 1대가 1000 을 보고, 램프 1초 경과를 넣어 봤다.

| | 값 |
|---|---|
| 램프 적용 후 합 | 16 |
| 하한 (`nodes × IDLE_DIVISOR`) | 40 |
| 노드당 몫 | 16 / 8 = 2 |
| 한산 통과 상한 `(long)(2 × 0.2)` | **0** |

`SecondWindowLimiter` 는 상한 0 을 무조건 거절로 처리한다. 아무도 안 몰리는
쿠폰의 요청이 여덟 노드 전부에서 `ENQUEUE_RATE_COUPON` 을 받는다 — R1 이
닫힌다. 경계는 `perNode >= IDLE_DIVISOR`, 즉 노드당 5 다.

**되돌리는 폭에 천장을 둔 이유.** 뒷단이 정직하게 낮게 보고한 것은 백프레셔다.
거기에 하한을 얹으면 없는 여유를 만들어 내는 셈이라, `reported` 를 천장으로
둔다. 뒷단이 3 을 가졌으면 하한이 10 이어도 3 이다. "여유 0" 보고가 0 으로
남는 것도 같은 규칙이 낸다 — 전에는 별도 분기(`total == 0 && anyPositive`)가
하던 일이다.

## 고려했으나 택하지 않은 것

- **하한을 무조건 `minimum` 으로** — 뒷단이 못 받겠다고 말한 뒤에도 밀게 된다.
  C-7 을 되돌리며 정한 원칙과 정면으로 어긋난다.
- **램프 창을 줄인다** — 부족 구간이 짧아질 뿐 없어지지 않는다. 램프를 두는
  이유(콜드 인스턴스의 과대 보고, C-5)도 함께 약해진다.
- **`idleCap` 산출에 `max(1, ...)` 를 넣는다** — PK-A5 가 금지한다. 상한 1 을
  보장하는 것은 분모가 아니라 하한이 할 일이다.

## 확신이 낮은 부분 / 남은 위험

- `reported` 는 신선한 보고만 센다. 신선도 창이 짧고 보고 주기가 흔들리면
  `fresh == 0` 으로 떨어져 이 경로를 안 탄다. 그때는 하한을 그대로 쓴다.
- 램프 중 하한을 되돌리면 콜드 인스턴스가 노드당 5 만큼은 받는다. 뒷단이 그것도
  못 받는 상태라면 이 되돌림이 첫 부하가 된다. 노드당 5 는 유휴 통과 한 건에
  해당하는 값이라 그 크기를 감수한다.

## 어떻게 검증했는가

`램프가_깎은_만큼에_하한이_걸리는지` 로 8노드 · 램프 1초 구간을 RED 로 잡고
값으로 못 박았다. `하한은_뒷단이_가진_것을_못_넘는다` 가 반대 방향을 잠근다.
기존 `보고한_0_에는_하한을_안_쓴다`·`램프가_만든_0_에는_하한을_쓴다` 는 그대로
통과한다 — 새 식이 옛 분기를 포함한다.

`./gradlew build integrationTest contextTest chaosTest` 통과.
