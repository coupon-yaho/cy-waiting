# 작업 흐름 규칙 (WF)

---

## WF-1 · MUST · Conventional Commits

```
<type>(<scope>): <제목>

<본문 — 코드만 봐서는 알 수 없는 "왜". 없으면 생략>

Refs: CY-145
```

```
feat(admission): 전역 크레딧 기반 통과 상한 산출
test(queue): 매진 쿠폰의 폴링 예산 잠식 검증
fix(redis): 시계 역행 시 순서 뒤바뀜
```

- **type 과 scope 는 영문**, 제목과 본문은 **한글**
- **제목은 명사형으로 끝낸다.** 요약이지 문장이 아니다 —
  `~했다` · `~한다` · `~된다` 같은 종결어미를 쓰지 않는다.
  무엇을 한 커밋인지가 목적어에 있으면 서술어는 군더더기다
- **제목 50칸 이내, 마침표 없음** — 글자 수가 아니라 **표시 폭**이다.
  한글은 터미널에서 두 칸을 차지하므로 한글 제목은 대략 25자가 상한이다
- 상세 설명은 Jira/Confluence에. 커밋 본문은 한두 줄
- `Refs:` — Jira 이슈 키. **제목에 넣지 않는다** (폭을 잡아먹는다).
  푸터는 이것 하나뿐이다 — 계획서 태스크 ID 를 커밋에 남기지 않는다 (3절)

type·scope 를 영문으로 두는 이유는 Conventional Commits 도구가 그걸 파싱하기
때문이다. 제목은 사람이 읽는 것이라 한글이 정확하다.

### type

| type | 용도 |
|---|---|
| `feat` | 기능 추가 |
| `fix` | 버그 수정 |
| `test` | 테스트 추가·수정 (RED 커밋 포함) |
| `refactor` | 동작 변경 없는 구조 개선 |
| `perf` | 성능 개선 |
| `docs` | 문서 |
| `build` | 빌드 스크립트, 의존성 |
| `ci` | CI 설정 |
| `chore` | 그 외 (게이트 통과 표시 포함) |

### scope

패키지명을 그대로 쓴다. 페이즈가 아니라 **코드 위치**를 가리킨다.

```
domain  admission  allocation  snapshot  queue  capacity  token
redis   routing    config      health    chaos  plan      rules
```

여러 패키지에 걸치면 생략한다.

## WF-2 · MUST · TDD 사이클을 커밋으로 남긴다

```
test(admission): 한산한 쿠폰의 무대기 통과 검증          [red]
feat(admission): 전역 크레딧 기반 통과 상한 산출
refactor(admission): 리미터 계층 선택 분리          (선택)
```

RED 커밋 바디 첫 줄에 `[red]`를 남긴다. CI가 이걸 보고 실패를 허용한다.

## WF-3 · MUST · git flow + Jira 티켓 ID 브랜치

**Phase 1 착수 시점부터 적용한다.** 그 전(base 작업)은 `main` 직접 커밋 + amend.

| 브랜치 | 용도 | 분기원 → 병합처 |
|---|---|---|
| `main` | 항상 배포 가능. 태그가 붙는다 | — |
| `develop` | 통합. 페이즈 작업이 모인다 | `main` → `main` |
| `feature/CY-123-<slug>` | 태스크 단위. **TDD 사이클 커밋이 여기 쌓인다** | `develop` → `develop` |
| `bugfix/CY-124-<slug>` | `develop` 의 결함 수정 | `develop` → `develop` |
| `release/<version>` | 릴리스 준비 (게이트 판정·문서 정리) | `develop` → `main` + `develop` |
| `hotfix/CY-125-<slug>` | 운영 장애 긴급 수정 | `main` → `main` + `develop` |

### 브랜치 이름 규칙

```
feature/CY-231-idle-cap-from-global-credit
        └──┬─┘ └──────────┬──────────────┘
     Jira 키          영문 kebab-case 슬러그 (3~6단어)
```

- **Jira 키가 반드시 앞에 온다.** CI 가 브랜치명에서 키를 뽑아 이슈 상태 전이·
  PR 링크·Confluence 리포트를 연결한다 → [`.github/README.md`](../../.github/README.md)
- 키가 없으면 **CI 가 PR 을 차단**한다
- **기본은 태스크 단위다.** 페이즈는 Jira Epic 이고 브랜치는 그 아래 태스크를 딴다

**예외 — 스캐폴딩 페이즈는 에픽 단위로 딴다.** Phase 1 처럼 태스크가 서로 얹혀 있어
따로 PR 을 열 수 없는 경우다 (그래들 없이는 스모크도 품질 임계도 성립하지 않는다).
그때는 `feature/CY-<에픽번호>-<슬러그>` 로 하나만 따고 태스크를 커밋으로 쌓는다.

| | 브랜치 | 왜 |
|---|---|---|
| Phase 1 | **에픽 단위** | 태스크가 전부 그래들 위에 얹힌다. 판정 단위도 페이즈다 |
| Phase 2~ | 태스크 단위 | 기능 티켓이 독립적으로 리뷰 가능하다 |

**Phase 2 부터 에픽 단위로 하지 않는다.** 35태스크·기능 티켓 8개를 한 브랜치에
담으면 리뷰가 불가능한 PR 이 된다.

### 병합 규칙

| 대상 | 방식 | 이유 |
|---|---|---|
| `feature/*` → `develop` | **merge commit** (squash 금지) | TDD 사이클 커밋이 이력의 목적이다 |
| `release/*` → `main` | merge commit + 태그 | 릴리스 경계를 이력에 남긴다 |
| `hotfix/*` → `main`·`develop` | merge commit 양쪽 | 한쪽만 하면 다음 릴리스에서 되돌아간다 |

**squash 는 어떤 경우에도 하지 않는다.** RED→GREEN→REFACTOR 커밋이 사라지면
TDD 준수의 증거가 없어진다 (WF-2).

## WF-4 · MUST · 게이트 커밋에 실측치를 남긴다

```
chore(gate): Phase 2 게이트 통과

분기 커버리지 100% / 뮤테이션 생존 4.2%
R1 · F1 · F4 · F8 시나리오 통과
속성 테스트: 배분 10만회 크레딧 초과 배분 0, 순위 10만 시퀀스 역행 0

Refs: CY-201
```

"통과했다"가 아니라 **숫자**를 남긴다. 나중에 회귀를 판단하는 기준선이 된다.

## WF-6 · MUST · 동작을 바꾼 세션은 작업 로그를 남긴다

무엇을 왜 했는지, 무엇을 고려했다가 버렸는지를
[ai/journal/](../journal/README.md)에 기록한다. 이유는 그 문서에 있다.

### 대상

| 필요 | 불필요 |
|---|---|
| `src/**` · `*.lua` | `plan/**` · `ai/**` · `.claude/**` |
| 빌드 스크립트 (`*.gradle`) | `*.md` 전반 |
| **`.github/workflows/**` · `.github/actions/**`** | `.github/README.md` · 템플릿 |
| | 봇 PR (dependabot 등) |

**CI 도 동작이다.** 파이프라인 구조를 바꾸는 것은 무엇을 언제 검증할지를 바꾸는
일이라 근거가 남아야 한다. 반면 계획·규칙 문서는 **그 자체가 근거 문서**이므로
따로 로그를 요구하지 않는다.

봇 PR 을 제외하는 이유: 의존성 범프에 근거 문서를 요구하면 규칙이 조롱거리가 된다.

## WF-7 · MUST · 문서는 늘릴 때 함께 줄인다

설계가 바뀌면 `plan/`과 `ai/rules/`를 **같은 변경에서** 고친다.
갈라지면 문서가 거짓말을 시작하고, 그때부터 아무도 읽지 않는다.

**같은 내용이 두 곳에 있으면 그 자체가 결함이다.** 한쪽만 고쳐지는 순간
어느 쪽이 맞는지 알 수 없게 된다. 내용을 추가할 때 이걸 먼저 본다.

| 상황 | 조치 |
|---|---|
| 다른 문서에 이미 있다 | 링크한다. 요약도 복사다 |
| 설명이 길어진다 | 근거는 `ai/journal/`, 문서에는 결론만 |
| 더 이상 사실이 아니다 | 지운다. "예전에는" 을 남기지 않는다 |

문서가 늘기만 하고 줄지 않으면 읽히지 않는다. 읽히지 않는 문서는 없는 것과 같다.

## 3. 계획서 태스크 ID가 안정적인 키다

**Jira 번호를 계획 문서에 하드코딩하지 않는다.**

| ID 종류 | 소유자 | 안정성 |
|---|---|---|
| 계획서 태스크 ID (`2.3.9`, `G2.1`, `F1`, `D-P1`) | 우리 | 안정적 |
| Jira 이슈 키 (`CY-231`) | Jira | 발번 시점에 정해짐 |

- 계획 문서(`plan/`)는 **계획서 ID만** 쓴다
- 둘의 대응은 [plan/91-jira-map.md](../../plan/91-jira-map.md)에서만 관리한다
- **커밋 푸터는 `Refs:` 하나만 남긴다.** 계획서 ID 를 커밋에 박지 않는다

계획서 ID 는 문서를 개편하면 바뀐다 — 실제로 Phase 5 를 쪼개면서 `5.9`→`6.5`,
`7.0`→`8.0` 처럼 대량으로 밀렸다. **커밋 이력은 못 고친다.** 박아두면 이력에
죽은 참조만 남는다. Jira 키는 이슈를 옮겨도 따라오므로 그쪽만 남긴다.

### 커밋에서 되짚기

```bash
git log --grep='Refs: CY-145'          # 특정 Jira 이슈의 모든 커밋
```

## 4. 문서 갱신 책임

| 문서 | 언제 고치는가 |
|---|---|
| `plan/0N-*.md` | 설계가 바뀔 때. 코드와 같은 PR |
| `plan/90-decisions.md` | 결정이 확정되거나 재검토 트리거가 발동할 때 |
| `plan/91-jira-map.md` | 이슈가 발번될 때 |
| `ai/rules/` | 규칙 합의가 바뀔 때. 별도 PR |
| `ai/journal/` | 작업할 때마다 |
| `CLAUDE.md` | 구조·진입점이 바뀔 때 |

### 결정 하나를 바꾸면 넷이 따라온다

**표를 하나만 고치고 끝내는 것이 이 저장소에서 가장 잦은 실수다.** 결정을 넣거나
바꾸면 아래를 **같은 커밋에서** 훑는다.

| 따라와야 하는 곳 | 무엇 |
|---|---|
| `plan/90-decisions.md` | 결정 본문 |
| 해당 **페이즈 문서** | 태스크·게이트·절 제목에 근거 ID |
| `plan/00-requirements.md` | 요구사항 추적표·가정·계약 표 |
| `plan/README.md` | 0절 차단 목록 · 2절 통과 수치 · 4절 의존 |
| `plan/91-jira-map.md` | 결정 상태(🔴🟡✅) · 티켓 대응 |
| `ai/rules/` | **같은 주제를 다루는 규칙이 있는지** |
| `ai/journal/index.md` | 그 결정이 해소한 가정 |

**`ai/rules/` 를 특히 놓친다.** 규칙은 원칙만 담고 수치는 계획서가 갖는 구조라
수치 충돌은 안 나지만, **정책이 겹칠 때 정면으로 갈린다** — 알람 대상을 규칙과
계획서가 각각 정의해 한 사고에 두 번 호출되게 만든 적이 있다.

```bash
# 결정 ID 가 인용된 곳을 먼저 센다. 0곳이면 구현부와 연결이 끊긴 것이다
rg -l '\bB-15\b' plan/ ai/ .claude/
```
