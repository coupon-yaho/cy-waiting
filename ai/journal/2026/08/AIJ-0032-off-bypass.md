# 대기열을 끄면 줄 선 사람이 추월당한다

## 무엇이 잘못돼 있었나

판정 사다리의 `mode == OFF` 우회가 **모든 큐 검사보다 앞**에 있었다.

```
 3. mode == OFF  → PASS_BYPASS      ← 여기
 5. waiting >= queueCapacity → REJECT_QUEUE_FULL
 6. dataStale && waiting > 0 → ENQUEUE_STALE   (F1)
```

`mode` 는 사람이 고른 값이고 `waiting` 은 기계가 관측한 값이라 **서로 독립**인데,
생성자가 그 조합을 막지 않는다 — `mode` 는 불변식 I1~I4 어디에도 등장하지 않는다.

재현했다. `(OFF, QUEUEING, credit=500, stock=10000, waiting=20000)` 을 만들어
토큰 없는 신규 요청을 넣으면 **`PASS_BYPASS`** 가 나온다. 줄에 선 2만 명을
신규 유입이 통째로 추월하고 재고까지 먼저 먹는다.

**불변식 4 다.** 6번이 낡은 스냅샷에서 막은 것(F1)을 3번이 그대로 뚫는다.

## 왜 안 잡혔나

시험 이름이 `대기열이_꺼져_있으면_붐벼도_통과한다` 인데 픽스처는
`CouponStates.off(500)` — `IDLE`·`waiting=0` 이다. **"붐빌 때" 를 전혀
시험하지 않으면서 이름이 그렇게 주장하고 있었다.**

그리고 팩토리가 `off(stock)` 뿐이라 **"OFF 인데 줄이 있다" 를 만들 방법이
없었다.** 도달 가능한 상태인데 픽스처로는 표현이 안 됐다 — TS-3 의 반대
방향이고, 결과는 더 나쁘다. 상태공간의 일부가 통째로 측정 밖이라 브랜치
커버리지·뮤테이션 수치가 그 위에서 나온 값이 된다.

## 고친 것

줄의 존재를 정책보다 **먼저** 본다.

```java
boolean hasQueue = s.waiting() > 0 || req.justEnqueued();
if (s.mode() == QueueMode.OFF && !hasQueue) {
    return AdmissionDecision.PASS_BYPASS;
}
```

`justEnqueued` 를 포함하는 이유 — `waiting` 이 아직 0 인데 이 요청이 방금
줄에 들어갔으면, 우회시킬 때 **자기가 방금 선 줄을 자기가 추월한다.**

**교착은 없다.** `OFF` 는 배분에 관여하지 않으므로(스케줄러는 `waiting` 과
`credit` 만 본다) 남은 줄은 계속 빠지고, 비는 순간 우회가 다시 산다.

`CouponStates.offWithQueue(...)` 를 만들어 이 상태를 픽스처로 표현할 수 있게
했고, 계획서 3.5절 사다리 표도 같은 커밋에서 고쳤다 (PK-A4).

## 시험도 지적당했다

처음 쓴 시험이 정본 생성자를 직접 불렀고(TS-3), 부정 단언(`isNotEqualTo`)이라
**나머지 13개 판정값 아무거나 통과**했다. 정확한 값으로 고정하고 경계를 넣었다 —
크레딧이 말라 용량이 0 이면 `REJECT_QUEUE_FULL`, 여유가 있으면
`ENQUEUE_BACKLOG` 다. 줄이 빠진 뒤 우회가 되살아나는 것까지 잇는다.

## 확신이 낮은 부분

- **`ALWAYS` 는 아직 안 봤다.** `OFF` 와 대칭인 정책인데 낡은 스냅샷 구간에서
  무시된다는 지적이 따로 있다 (CY-285).
- **`mode` 와 `runtime` 의 조합에 불변식이 없다.** 이번엔 판정 쪽에서 막았는데,
  상태 쪽에서 막을 것이 더 있는지는 3.6절이 다루지 않는다.
