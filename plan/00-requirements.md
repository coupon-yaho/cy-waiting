# 요구사항과 목표

**이 문서가 나머지 전부의 출처다.** 페이즈·게이트·설계 결정은 여기서 파생된다.
여기에 없는 것을 만들고 있다면 둘 중 하나다 — 요구사항이 누락됐거나, 범위를 벗어났다.

---

## 2. 배경

### 2.1 상위 프로젝트

`comprehensive-project` — **통신사 브랜드 데이, 대규모 트래픽 선착순 쿠폰 발급 시스템**.
발급 계층을 v1(비관적 락) / v2(Redis Lua) / v3(Kafka 비동기) 세 버전으로 구현해
동시성 처리 방식을 비교하는 것이 상위 과제의 서사다.

| 상위 문서 | 내용 |
|---|---|
| `../../PRD.md` | 제품 요구사항. 6절 도메인, 7절 버전 사다리, 10절 측정 지표, 12절 제약 |
| `../../ERD.md` · `ERD.sql` | 데이터 모델 |
| `../../SCALING.md` | 규모 산정 |
| `../../SECURITY.md` | 보안 요건 |

> 이 저장소는 상위 프로젝트의 **하위 프로젝트**다. 위 문서들은 이 git 저장소 밖에
> 있으므로 링크가 아니라 경로로 적는다. 상위 PRD 가 바뀌면 3절을 다시 확인한다.

### 2.2 이 게이트웨이의 위치

```
클라이언트 ──> [ 이 게이트웨이 ] ──> 쿠폰 서비스 N대 ──> MySQL / Redis / Kafka
               입장 판정 · 대기열       발급 · 재고 차감
```

**소유 경계**: 게이트웨이는 **입장(admission)** 을 소유하고, 쿠폰 서비스는
**발급과 재고** 를 소유한다. 게이트웨이는 재고를 읽되 차감하지 않는다.

### 2.3 왜 제로베이스로 다시 만드는가

이전 구현(2,524줄, `../../waiting-gateway/waiting-legacy/`)은 설계 문서화 수준이
높았으나 **핵심 기능이 반대로 동작**했다.

| 문제 | 근거 |
|---|---|
| R1 이 역전 — 부하 없는 쿠폰의 **모든** 요청이 큐로 갔다 | [AIJ-0001](../ai/journal/2026/08/AIJ-0001-analyze-legacy-admission-logic.md) |
| 그 버그를 덮은 테스트가 **도달 불가능한 상태**를 픽스처로 썼다 | 동 |
| 매진·이탈 대기자의 큐 종료 경로가 없어 영구 대기 발생 | 동 |
| fail-open 이 줄 선 사람을 추월시켜 **선착순의 공정성**을 깨뜨렸다 | [AIJ-0002](../ai/journal/2026/08/AIJ-0002-recovery-transition-findings.md) |

마지막 항목은 코드 수정으로 덮을 수 있는 성질이 아니다 — 판정 순서와 상태 모델이
근본에서 다시 잡혀야 한다.

## 3. 상위 PRD 와의 차이

**조용히 어긋나면 나중에 "왜 PRD 에 없는 걸 만들었냐"가 된다.** 명시적으로 기록한다.

| # | 항목 | 상위 PRD | 이 프로젝트 | 상태 |
|---|---|---|---|---|
| **X1** | 적응형 대기열 | 9절 Out of Scope — "AIMD 적응형 rate … **토큰버킷으로 충분**" | R1·R2 의 본체 | **의도적 확장** |
| **X2** | 실행 환경 | 12절 — "로컬 Docker Compose only" | **EC2 노드 여러 대**에 프로덕션 배포 | **의도적 확장** |
| **X3** | 프레임워크 | 12절 — "Spring Boot 3.x" | Spring Boot 4.1.0 / Spring Cloud 2025.1.2 | **이미 어긋남** |

### X1 — 가장 중요한 차이

PRD 9절은 적응형 rate 를 **명시적으로 제외**하고 "논의를 재개하려면 팀 합의가 필요"
하다고 적었다. 이 프로젝트는 그 합의를 전제로 진행한다.

- PRD 의 근거("토큰버킷으로 충분")는 **단일 쿠폰 기준**에서는 맞다
- 그러나 핫 쿠폰과 콜드 쿠폰이 **하나의 백엔드 용량을 나눠 쓰는** 상황에서
  전역 단일 토큰버킷은 핫 쿠폰 대기자가 콜드 쿠폰 대기자를 밀어낸다
- 그래서 공정 배분(fair-share)이 필요하고, 그것이 R1·R2 다

→ **팀 합의가 실제로 있었는지 확인이 필요하다** ([90-decisions.md](90-decisions.md) D-X1)

### X3 — 확인 필요

상위 PRD 는 Spring Boot 3.x 를 못박았는데 실제 구현은 4.1.0 을 쓰고 있었다.
게이트웨이만 다른 버전을 쓰면 쿠폰 서비스와의 라이브러리 호환 문제가 생길 수 있다.
→ [90-decisions.md](90-decisions.md) D-X2

## 4. 요구사항

각 요구사항은 **출처**(누가 왜 요청했는가)와 **성공 기준**(무엇으로 판정하는가)을 갖는다.
출처가 없는 요구사항은 만들지 않는다.

### R1 · 적응형 대기열

> **부하가 없는 쿠폰은 대기열을 거치지 않고 즉시 통과하고,
> 트래픽이 몰리는 쿠폰에만 대기열이 켜진다.**

| | |
|---|---|
| **출처** | 사용자 요청 (2026-08-13) — "부하가 없는 쿠폰이라면 대기열을 거치지 않고 바로 보내주고 대기열이 필요한 트래픽이 몰리는 서비스만 대기열을 넣어주고 싶어" |
| **왜** | 대기열은 백엔드를 지키는 장치이지 그 자체가 목적이 아니다. 여유가 있는데 줄을 세우면 사용자 경험만 나빠진다 |
| **함정** | 이전 구현이 **정반대로** 동작했다 — 한산한 쿠폰일수록 반드시 큐로 갔다 ([AIJ-0001](../ai/journal/2026/08/AIJ-0001-analyze-legacy-admission-logic.md)) |
| **성공 기준** | credit 0 인 IDLE 쿠폰이 큐 등록 없이 통과 · 전역 상한 초과 시점에 큐가 생김 |
| **실현** | Phase 2 (G2.1 도메인) · **Phase 6 (G6.12 실부하 실측)** |

### R2 · 가용량 기반 분산

> **뒷단 N대의 가용량 비율대로 트래픽이 흐른다.**
> 유휴 여유가 200/40/120이면 그 비율에 가깝게 간다.

| | |
|---|---|
| **출처** | 사용자 요청 — "뒷단 서비스들의 가용량에 따라 알맞게 분산 시켜서 트래픽을 돌려주는 거야… 유휴 커넥션 상태가 200, 40, 120 이라면 그거에 알맞게" |
| **왜** | 총량만 맞추고 라운드로빈으로 뿌리면 40짜리 인스턴스가 120을 받아 3배 과부하가 된다. 총량은 맞는데 분배가 틀린다 |
| **범위 정정** | 뒷단은 **단일 서비스 N대(동종)** 이다. 이종 서비스 A/B/C 가 아니다 → 보고된 `credits` 를 가중치로 쓰고 in-flight 로 실시간 보정한다 (가중 P2C, R-4) |
| **성공 기준** | 인스턴스 간 유입 비율이 `credits` 비율과 ±15% 이내 · 열화 시 5초 내 재분배 |
| **실현** | Phase 4 (총량) + Phase 9 (분배) |

### R3 · 매진 종결

> **매진된 쿠폰은 Redis 도 백엔드도 거치지 않고 게이트웨이가 종결한다.**

| | |
|---|---|
| **출처** | 사용자 요청 — "재고가 매진되어서 더 이상 발급하지 않게 될 수 있는데 이 때 redis 거치지 않고 서비스 인메모리에 저장해서 redis 의 부하도 줄이는 것을 희망" |
| **전제 정정** | 판정 경로는 **이미 Redis 왕복 0** 이다(로컬 스냅샷). 실제로 절감할 곳은 **백엔드 프록시**와 **갇힌 대기자의 폴링** 두 곳이다 |
| **안전 근거** | **재입고는 상시 발생한다**(B-11). 그래도 안전한 이유는 오판이 **한 방향뿐이고 스스로 낫기** 때문이다 — 재입고 직후 최대 1.5초 동안 `SOLD_OUT` 을 줄 수 있으나 다음 스냅샷이 `stock>0` 으로 되돌린다. **반대 방향(매진인데 통과)은 재고가 줄기만 하는 구간에서 불가능**하고, 그쪽이 초과 발급이라 위험한 방향이다 |
| **성공 기준** | 매진 후 1회 폴링 내 종료 신호 · 백엔드 도달 요청 ≤ 노드 수 · `SOLD_OUT` 응답 시 Redis 명령 0 |
| **실현** | Phase 7 |

### R4 · 규모

> **피크 100K RPS, 동시 대기 20,000명에서 무너지지 않는다.**

| | |
|---|---|
| **출처** | 사용자 요청 — "피크 트래픽은 100K 정도", "동시에 20000명이 몰린다면 그때가 문제가 되긴 하지만 그런 상황도 적절하게 해결" |
| **병목** | 오픈 순간의 `enqueue` 폭발. 한 쿠폰의 키가 해시태그로 한 노드에 몰려 그 노드의 ops 한계가 상한이 된다 |
| **완화** | Redis 클러스터 + 큐 샤딩. **단, 계산이 아니라 측정으로 착수를 판정한다** |
| **성공 기준** | **100K RPS 60초 지속에 5xx <0.1%** · 노드 증설 효율 ≥70% · 20,000 동시(200ms 램프)에서 노드별 ops 편차 ≤±20% |
| **실현** | Phase 10 (착수 게이트 1절) |

### R5 · 회복력

> **장애 진입·유지·회복 전 구간에서 정합성과 공정성이 유지된다.**
> 장애 대응으로 바뀐 상태가 장애가 걷힌 뒤 원래대로 돌아오고,
> 돌아오는 과정이 2차 장애를 만들지 않는다.

| | |
|---|---|
| **출처** | 사용자 요청 — "프로덕션으로 배포할 예정이라서 오차가 있어서는 안 되고 장애 대응이 완벽에 가까워야해. 물론 **장애 대응에 의한 상태 변경에 맞춰졌던 환경이 장애 회복하면서 돌아올 때도 문제가 없어야**해" |
| **왜 별도 요구사항인가** | 장애 대응은 시스템을 다른 모드로 전환한다(fail-open 상한, 낡은 스냅샷, 열린 서킷, 정지한 배분). **되돌아오는 순간이 가장 위험한데 유지 구간만 보는 테스트는 하나도 잡지 못한다** |
| **성공 기준** | 13+3 카오스 시나리오가 **진입·유지·회복** 3단계 판정 전부 통과 · 초과 발급 0 · 순위 역행 0 · 회복 버스트 ≤1.2배 |
| **실현** | Phase 8 — **프로덕션 배포의 실질적 승인선** |

> **"승인선"이지 배포 그 자체가 아니다.** 무중단 배포 절차·운영 롤백·런북은
> 이 계획의 비목표다 (5절). Phase 8 을 통과했다는 것은 **배포해도 되는 물건이
> 됐다**는 뜻이지 배포 준비가 끝났다는 뜻이 아니다.

### R6 · 대기 정보 제공

> **대기자에게 순위와 예상 대기시간을 알려준다. 정확할 필요는 없으나
> 순위가 뒤로 가서는 안 된다.**

| | |
|---|---|
| **출처** | 사용자 요청 — "내 순위와 내 뒤의 대기자 수의 계산은 내가 위치한 노드에서의 순번 × 노드의 개수 이러한 느낌으로 대략적인 계산을 거칠거야. **정확할 필요는 없어.** 또한 예상 대기시간도 알려주고 싶어" |
| **정확도 vs 단조성** | 근사는 허용되지만 **단조 비증가는 타협 불가**다. 순위가 뒤로 가면 사용자가 즉시 알아채고 신뢰가 깨진다 |
| **오차 특성** | 샤딩 추정기 `로컬순위 × S` 의 산포는 `√((R-1)(S-1))`. **상대 오차는 앞으로 갈수록 커지지만 절대 오차는 작아진다** — 체감하는 것은 절대값이므로 필요한 곳에서 정확하다 |
| **ETA 지배항** | 샤딩 오차(±1.5초)가 아니라 **credit 변동**이다. EWMA 가 훨씬 큰 기여를 한다 |
| **성공 기준** | 순위 단조성 위반 0 · ETA 는 EWMA credit 기반 · 거친 버킷으로 표시 |
| **실현** | Phase 2 (T2.7 표시) · **Phase 3 (G3.11 단조성 보장)** · Phase 10 (샤딩 반영) |

## 5. 비목표 — 하지 않기로 확정한 것

**여기 있는 것을 만들고 있다면 멈추고 이 문서를 먼저 고친다.**

| 분류 | 하지 않는 것 | 근거 |
|---|---|---|
| **재고** | 게이트웨이가 재고를 **차감**한다 | 발급 컨텍스트 소유. 원자 차감은 쿠폰 서비스 책임 (2.2절) |
| **발급** | 발급 비즈니스 로직(등급 검증, 중복 발급 판정) | 게이트웨이는 입장만 판정한다 |
| **인증** | 토큰 **발급**·회원가입·로그인 | 상위 PRD 9절 제외. 게이트웨이는 **검증만** 한다 |
| **정확도** | 순위·ETA 의 정확한 값 보장 | R6 — 근사 허용이 명시적 요구사항 |
| **라우팅** | 이종 서비스 간 라우팅 | 뒷단은 단일 서비스 N대 (R2 범위 정정) |
| **큐** | 오픈 전 사전 예약 대기열 | 상위 PRD 9절 제외 |
| **동기화** | 게이트웨이 노드 간 pub/sub 상태 동기화 | 공유 저장소가 이미 있는데 두 번째 진실 공급원을 만드는 셈 (PRD:817) |
| **일관성** | 애그리거트를 넘는 원자성 | Redis 슬롯 경계 = 트랜잭션 경계. 그 밖은 최종 일관성 |
| **확장** | 계획에 없는 확장 지점 | 두 번째 사례가 나올 때 도입 (DS-7) |
| **배포** | 무중단 배포 파이프라인·운영 롤백 절차 | 이 계획은 **게이트웨이를 만드는 것**까지다. 배포는 별도로 다룬다 |
| **운영** | 온콜 런북·알림 라우팅·대시보드 운영 | 위와 같다. Phase 6 이 관측 스택을 세우고 Phase 8 이 페이지 대상을 정하는 데까지만 한다 |

| 저장소 | Redis **7.x** (단일 → 클러스터) | 상위 PRD 12절 · **우리 설계도 독립적으로 요구** (E-9) |
| 시계 | Redis 노드는 **slew 보정만** 쓴다. step 보정(`makestep`) 금지 | E-9 — 큐 score 가 시계라 역행이 곧 추월이다 |
| 실행 환경 | **EC2 노드 여러 대. 쿠버네티스가 아니다.** Redis 도 자체 운영 | 사용자 확인 (2026-08-14) |
| 인증 | **없다.** 로그인·회원가입이 과제 범위 밖이라 mock 회원 100만 명을 쓴다. 회원 식별자와 등급은 `X-Member-Id`·`X-Member-Grade` 헤더로 받고, **위조 가능함을 전제한다** | 발급 계층 API 명세 v2.0 · 사용자 확인 (2026-08-18) |
| API 계약 | `X-Member-Id`·`X-Member-Grade` 필수. 누락·형식 오류는 `400 COMMON-001`. 에러 코드 체계는 PRD 11절을 따른다 | 상위 PRD 11절 · 명세 v2.0 |
| 측정 | 발급 계층 v1/v2/v3 는 **동시에 뜨지 않는다**. 메트릭에 버전 태그 필수 | 상위 PRD 7절 |
| 이슈 관리 | Jira 스페이스 프리픽스 **`CY`**. Epic=Phase, Story=태스크 절 | 사용자 지정 |
| 프로세스 | TDD · Conventional Commits · 커밋 단위 이력 | 사용자 지정 |

> **상위 PRD 12절과 어긋난다.** PRD 는 사전 발급 HS256 JWT 를 전제하지만 발급
> 계층은 그것 없이 구현됐다 — API 명세 v2.0 에 `Authorization` 헤더가 없고
> `X-Member-Id` 가 필수다. 게이트웨이만 JWT 를 요구하면 계약이 갈린다.
> **헤더 방식을 정본으로 삼는다** ([90-decisions.md](90-decisions.md) D-A1).
>
> 그래서 게이트웨이는 헤더를 신뢰하지 않고 **자기가 발급한 토큰만 신뢰한다**.
> 자리를 다루는 요청은 `queueToken`·입장 토큰으로 대상을 특정하므로, `X-Member-Id`
> 를 바꿔도 남의 자리를 건드릴 수 없다 → [05-data-plane.md](05-data-plane.md) 3절 · 5.5.7

## 7. 가정 — 아직 검증되지 않은 것

**틀리면 설계가 바뀌는 전제들이다.** 검증 전까지는 가정으로 다룬다.

| ID | 가정 | 틀리면 | 검증 |
|---|---|---|---|
| ~~A1~~ | ~~재고는 단조 감소한다 (재입고 없음)~~ | ✅ **재입고는 상시 발생한다** (B-11). 매진 종결은 여전히 안전하다 — 아래 R3 안전 근거 참조 |
| A2 | 쿠폰 서비스가 자기 여유(`credits`)를 정확히 보고한다 | R2 의 총량 산출이 틀린다 | A-11 (합의 완료) |
| A3 | 콜드 인스턴스가 여유를 과대 보고한다 (F6) | 램프업 대응이 불필요해진다 | A-12·A-13 · 카오스 C7 |
| A4 | 단일 Redis 가 20,000 동시 스파이크를 못 버틴다 | Phase 10 샤딩이 불필요해진다 | Phase 10 1절 착수 게이트 |
| A5 | 회복 버스트 허용치 1.2배가 적절하다 | RC4 기준을 재조정해야 한다 | 정상 시 변동폭 측정 |
| A6 | 적응형 대기열에 대한 팀 합의가 있다 (X1) | **프로젝트 범위 자체가 재검토 대상** | D-X1 |
| A7 | 쿠폰 서비스 인스턴스는 **10~20대** 규모다 | 3~5대면 가중 P2C 대신 가중치 비례 선택이 더 정확하고 단순하다. 50대 이상이면 전수 조회 비용을 다시 본다 | Phase 9 착수 시 실제 대수 확인 |

가정의 최신 상태는 [`ai/journal/index.md`](../ai/journal/index.md) 의
"검증하지 못한 가정" 표에서도 추적한다.

## 8. 외부 계약

쿠폰 서비스 팀과 합의가 필요한 항목. **우리 단독으로 결정할 수 없다.**

> 게이트웨이는 `cy-be` 와 **별도 저장소**다 ([90-decisions.md](90-decisions.md) O-1).
> 따라서 이 표는 계속 외부 계약이다. 키 소유는 O-3 을 따른다.

| 계약 | 내용 | 필요 페이즈 | 결정 |
|---|---|---|---|
| 가용량 보고 | `capacity:coupon-svc:{version}` 해시에 **`{instanceId, addr, credits, ts}`** 자기보고. 주소가 들어가면서 **이 보고가 곧 인스턴스 레지스트리**가 된다 (R-1) | Phase 4 · **Phase 9** | A-11 ✅ |
| 워밍업 램프 | 기동 후 60초 `credits × min(1, 경과/60s)` | Phase 4 | A-12 ✅ |
| 매진 신호 | `409` + `application/problem+json` 의 `type` | Phase 7 | B-10 ✅ |
| 정책 형식 | `coupon:policy` 를 JSON 으로 | Phase 10 | E-12 ✅ |
| 활성 쿠폰 | `coupons:active` 집합 갱신 주체와 시점 | Phase 4 | — |
| 에러 규격 | 게이트웨이 409 가 앱 409 와 **구별되지 않아야** 한다 | Phase 5 | — |
