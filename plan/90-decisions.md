#### D-C4 — 나이를 재는 두 벽시계

보고의 나이는 `레디스 TIME − 뒷단이 찍은 ts` 다. **두 값의 출처가 다르다.**
레디스 시계가 복제본 승격으로 뒤로 가면 분자만 뒤로 가고 분모는 그대로라, 모든
보고가 "앞섬" 으로 걸려 크레딧이 하한에 박힌다 — 역행 폭만큼 전면 억제다.

단조 바닥값으로 막아 보고 안 되는 것을 확인했다 (CY-875). 바닥값은 분자를
얼리는데 분모는 계속 앞으로 가므로, 허용치 1 초를 **두 틱 만에** 다시 넘는다.
어느 한쪽만 만져서 닫히는 문제가 아니다.

| 안 | 무엇 | 대가 |
|---|---|---|
| **뒷단이 레디스 시각을 찍는다** | 분자와 분모를 한 시계로 맞춘다. 하트비트가 이미 그 방식이다 | 뒷단 계약 변경(A-11 개정). 보고마다 `TIME` 왕복이 는다 |
| **허용치를 관측된 스큐만큼 연다** | 우리 쪽에서 끝난다 | **유령이 그만큼 오래 산다.** 죽은 인스턴스의 마지막 보고가 창 + 허용치까지 세어지는데, 그 허용치가 역행 폭만큼 벌어진다 (C17 이 재는 바로 그 위험) |

**둘 다 대가가 크다.** 앞엣것은 팀 밖의 합의가 필요하고, 뒤엣것은 이 페이즈가
막으려는 다른 사고를 키운다. 그래서 값을 고르지 않고 결정으로 올린다.

**D-B1 은 만료일이 있는 보류다.** v5 에 남는 것은 패치를 기다리는 것이 아니라
그 의존성들에 무기한 동결하는 것이다 — 근거는
[AIJ-0162](../ai/journal/2026/08/AIJ-0162-action-bumps.md). 만료일까지 고르지
않으면 동결을 고른 것이 된다. 만료 없는 보류는 잊힌다.

### 1.3 D-P1 은 어떻게 사라졌는가

원래 문제는 **`INCR seq` 가 되감겨 중복 순번이 나오는 것**이었다.
2.7절에서 순번 자체를 없애기로 하면서 이 형태의 F2 는 성립하지 않게 됐다.

남은 것은 성격이 다르다 — `kill -9` 로 **ZSET 이 통째로 날아가 대기자가 증발**하는 것.
결론과 근거는 2.7절 A-9·E-6 에 있다.

### 1.4 D-Q1 선택지 (결론은 2.4절 D-9)

| 안 | 내용 | 비용 |
|---|---|---|
| a | 표본 100명의 alive 존재율로 `ZCARD` 보정 | 거의 없음. 오차 통계적으로 유계 |
| b | 큐 전체를 순회하는 저속 배경 스위퍼 | Redis 부하 증가 |
| c | 보정 없이 ETA를 보수적(길게) 표시 | 0. 사용자 신뢰 저하 |

**(a) 로 확정.** Phase 10 의 순위 추정과 같은 성격의 근사이며 오차 특성도 유사하다.

## 2. 확정된 결정

### 2.1 아키텍처

| ID | 결정 | 근거 |
|---|---|---|
| A-1 | 판정 재료는 **로컬 스냅샷**에서만 읽는다 (요청 경로 Redis 왕복 0) | 상태 조회 ops가 RPS에 비례하면 게이트웨이의 존재 이유가 사라진다 |
| A-2 | 스냅샷은 **폴링**으로 갱신한다 (pub/sub 아님) | pub/sub은 at-most-once. 재연결 노드는 놓친 것을 모른다. `HGETALL`은 언제 붙어도 전체 복구 |
| A-3 | 스냅샷은 **통째 교체**한다 (키별 캐시 아님) | miss 시 Redis 쇄도. 쿠폰별로 낡음 시점이 다르면 낡음을 측정할 수 없다 |
| A-4 | 낡음을 **두 종류로 구분**한다 (`fetchStale` / `dataStale`) | 섞으면 스케줄러 장애가 전 노드 동시 이탈로 번진다 |
| A-5 | readiness 는 **어느 낡음도 안 본다.** `fetchStale` 은 liveness 로 간다 (CY-304) | `dataStale` 로 503 을 내면 전 노드가 동시에 빠져 100% 장애다. `fetchStale` 도 **"받아왔는가" 로 재면 같은 결과**라 "루프가 도는가" 로 재고, 그건 재기동이 고치는 결함이라 liveness 다 |
| A-6 | 배분은 **리더 하나만** 수행 | 게이트웨이는 무상태로 수평 확장, 스케줄러만 단일화 |
| A-7 | **펜싱 토큰을 쓰지 않는다** | 크레딧은 재고를 예약하지 않으므로 2배 발행이 초과 발급으로 번지지 않는다. **크레딧이 재고를 예약하는 구조가 되면 즉시 재검토** — 검증은 카오스 C5 |
| A-8 | `admitted` 임계는 **스냅샷에 넣지 않고** 폴링마다 직접 읽는다 | 복제본마다 값이 다르면 순위 역행으로 보인다. Phase 10 샤딩에서 이 결정이 단조성을 지탱한다 |
| **A-9** | **큐 순서는 `INCR` 순번이 아니라 Redis 시계 timestamp 다** (2026-08-14 전환) | 아래 2.7절 |
| A-10 | 입장 토큰 **재사용 방지는 발급 계층의 멱등성**에 맡긴다 (D-T1) | 게이트웨이는 재고를 차감하지 않는다. 토큰을 1회용으로 관리하면 통과 경로에 Redis 쓰기가 생기고, 그래도 결국 발급 계층 멱등성이 필요하다 |

### 2.2 판정

| ID | 결정 | 근거 |
|---|---|---|
| B-1 | **2계층 리미터** — 한산한 쿠폰은 `globalCredit/N`, 경합 쿠폰은 `credit/N` | `credit`이 "공정 몫"과 "통과 허가량"을 겸하면 R1이 역전된다 |
| B-2 | `max(1, ...)`을 **쓰지 않는다** | `credit=10`, 노드 20대면 각자 1명씩 통과시켜 크레딧의 2배가 지나간다 |
| B-3 | **매진 판정이 `dataStale`보다 앞선다** | 낡아도 오판이 **안전한 방향뿐**이고 스냅샷이 되돌린다 (B-11). 뒤에 두면 fail-open 상한을 갉아먹는다 |
| B-4 | **`waiting > 0`이면 fail-open하지 않는다** (F1) | 상태를 모른다는 것이 추월을 정당화하지 않는다. 선착순에서 공정성은 제품의 존재 이유 |
| B-5 | 리미터 카운터를 **경로 전환 시 이월**한다 (F4) | 독립 카운터면 전이 순간 1.5× 버스트 |
| B-6 | **`PASS_TOKEN`도 상한을 거친다** (F8) | 허가 시점과 사용 시점이 TTL만큼 벌어질 수 있다 |
| B-7 | **서킷 상태가 판정의 입력**이다 (F3). 서킷이 인스턴스별이므로(R-10) 판정이 보는 것은 **살아 있는 인스턴스 비율**이다 | 모르면 half-open 시험 시점에 트래픽 전량이 도달해 회복이 반복 실패. 비율을 안 보면 3대가 죽었을 때 남은 7대에 10대분이 몰린다 |
| B-8 | 스냅샷 미등재 쿠폰은 **404** | Redis 키 무한 생성 차단. 쿠폰별 리미터·격벽 맵이 클라이언트 입력으로 증식하는 것도 이것이 막는다 |
| **B-9** | **격벽을 인스턴스별·쿠폰별 둘 다** 둔다 | 레이트 리밋은 초당 건수를 세고 격벽은 동시 건수를 센다 — **초당 100건이어도 각각 10초 걸리면 동시 1,000건**이다. 인스턴스별은 느린 한 대가 커넥션을 독식하는 것을, 쿠폰별은 핫 쿠폰이 콜드 쿠폰의 통로를 막는 것을 막는다. 쿠폰 2,000개여도 **리미터가 이미 쿠폰별 카운터와 축출을 갖고 있어** 기계가 새로 필요하지 않다 |

| D-3 | 입장 토큰은 **지연 발급**한다 | 미리 만들면 이탈자 몫이 버려지고 크레딧 보정 로직이 필요해진다 |
| D-4 | 순번은 **서버만** 쓴다 | 클라이언트가 보관하면 고칠 수 있는 값이 된다 |
| D-5 | 이탈자 청소는 **틱 폴링**으로 (키스페이스 알림 아님) | `expired` 이벤트는 배달 보장이 없고, 놓쳤다는 사실도 모른다 |
| D-6 | sweeper는 **앞부분 K명만** 검사한다 | 전수는 20,000명에서 불가. 한계는 D-Q1로 별도 처리 |
| D-7 | 순번 조회는 **게이트웨이가 직접 응답**한다 | 폴링 4,000 RPS를 앱에 흘리면 대기열의 존재 이유가 없다 |
| **D-8** | 입장 임계는 개수가 아니라 **score 값**이다. N명 입장은 `ZRANGEBYSCORE ... LIMIT N-1 1` 로 N번째 구성원의 score 를 읽어 임계로 삼는다 | 개수 기반 `INCRBY` 는 **떠난 사람의 자리까지 소모**한다. score 기반은 실제 구성원 N명을 집으므로 이탈 구간의 크레딧 낭비가 줄어든다 |
| **D-9** | 유령 대기자는 **표본 alive 존재율로 보정**한다 (D-Q1) | 전수 스위핑은 20,000명에서 불가. 오차가 통계적으로 유계이고 Phase 10 순위 추정과 성격이 같다 |
| **D-10** | 크레딧이 큐 크기보다 클 때 임계는 **큐의 최대 score** 로 둔다. **`+inf` 를 쓰지 않는다** | `+inf` 면 이후 도착자까지 임계 아래로 들어와 **줄을 서지 않고 통과**한다 |
| **D-11** | 유예 재입장은 **새 score 로 재등록**한다. 원래 자리를 복원하지 않는다 | 원래 score 로 되돌리면 그 사람 뒤에 있던 사람들의 순위가 1 늘어난다 — **순위 역행 0(타협 불가)이 깨진다.** grace 는 자리 보관이 아니라 재방문자 식별이다. 대신 `alive` TTL 을 넉넉히 잡아 **grace 로 떨어지는 일 자체를 드물게** 만든다 |

#### O-1 — `cy-be` 와 분리

`cy-be` 는 v1(비관적 락) · v2(Redis Lua) · v3(Kafka)를 **따로 측정해 비교하는**
저장소다. 성격이 실험이고, 게이트웨이는 그 셋 앞에 공통으로 서는 운영 컴포넌트다.
섞으면 무엇을 측정하는 저장소인지 흐려진다.

| 이유 | |
|---|---|
| **배포 독립성** | 장애 대응 중 fail-open 상한이나 서킷 임계만 바꿔 게이트웨이만 올리는 상황이 실제로 생긴다. 백엔드를 지키는 장치가 백엔드 배포에 묶이면 안 된다 |
| **CI 성격** | 카오스 40분 + 뮤테이션 40분. 백엔드 PR 이 이 값을 치를 이유가 없고, 반대로 게이트웨이 CI 가 빨개도 백엔드가 막히면 안 된다 |
| **규범 불일치** | `ai/rules/` 는 WebFlux·리액티브·도메인 순수성 전제로 쓰였다. JPA 를 쓰는 발급 계층에 맞지 않는다 |
| **바운디드 컨텍스트** | 게이트웨이는 입장을 소유하고 재고는 소유하지 않는다 ([00-requirements.md](00-requirements.md) 2.2절) |

**포기하는 것**: 계약 변경이 두 저장소에 걸친다 (D-C1·D-C2·D-C3).
다만 이건 저장소를 합친다고 저절로 해결되지 않는다 — 같은 저장소 안에서도
키 이름은 갈라진다. O-3 과 계약 테스트로 따로 막는다.

#### O-2 — 게이트웨이는 더 쪼개지 않는다

배분 스케줄러를 별도 프로세스로 뺄 수 있게 설계했지만
(`waiting.scheduler.enabled` 토글), 그건 **배포 단위 분리이지 저장소 분리가 아니다.**

**지금은 붙여 둔다** — 게이트웨이 전 노드가 토글을 켜고 리더 한 대만 배분을 돈다.
아래는 **떼어낸 뒤의 모습**이고, 뗄 시점은 틱 지연으로 판단한다
([04-control-plane.md](04-control-plane.md) 배포 형태).

```
저장소 하나
 ├─ 게이트웨이     scheduler.enabled=false
 └─ 배분 스케줄러  scheduler.enabled=true, gateway.enabled=false
```

**저장소 경계는 배포 단위가 아니라 불변식이 걸치는 범위를 따라야 한다.**

게이트웨이와 스케줄러는 도메인 전체를 공유한다 — `CouponState`, `FairShareAllocator`,
`SnapshotMeta`, `RedisKeys`, Lua 스크립트. 특히 `IDLE ⟹ credit == 0`(I1)과 판정
순서는 두 쪽이 함께 지켜야 성립한다. 저장소를 나누면 `CouponState` 하나를 고치는 데
저장소 간 PR 이 필요해지고, 그건 우리가 `cy-be` 와 분리하면서 감수하기로 한 비용을
**내부에서 다시 만드는 것**이다.

Phase 4 의 게이트는 붙여 둔 상태에서 잰다 — "10노드에서 배분은 1대만" 은
게이트웨이 10대를 띄우면 그대로 판정된다. 떼어낸 뒤에는 스케줄러 노드를 여러 대
띄워 같은 게이트를 다시 잰다. **어느 형태든 같은 게이트가 성립한다.**

### 2.7 A-9 — 큐 순서를 timestamp 로 (2026-08-14)

**바꾸기 전**

```
enqueue    INCR seq:{cid}  →  ZADD queue:{cid} <seq> <member>
순위       my_seq - admitted_seq            뺄셈 하나
입장       INCRBY admitted_seq N            임계를 N 올린다
```

순위가 산술로 나오는 게 이 설계의 값이었다. 대가는 두 곳에서 같은 모양으로 나왔다.

| 어디 | 무엇 |
|---|---|
| F2 (D-P1) | 카운터가 되감기면 **중복 순번**. 두 사람이 같이 입장하고 순위가 역행한다 |
| Phase 10 | `INCR seq` 가 **유일한 직렬화 지점**. 샤딩의 1차 목적이 이 카운터를 쪼개는 것이었다 |

**바꾼 뒤**

```lua
local now = redis.call('TIME')                      -- {sec, usec}
local t   = now[1] * 1000000 + now[2]
local last = redis.call('ZRANGE', KEYS[1], -1, -1, 'WITHSCORES')
if last[2] and tonumber(last[2]) >= t then
  t = tonumber(last[2]) + 1                         -- 뒤로 못 간다
end
redis.call('ZADD', KEYS[1], t, ARGV[1])
```

- **`seq:{cid}` 키가 사라진다.** 되감길 카운터가 없다
- **직렬화 지점이 사라진다.** ZADD 는 O(log N) 이라도 노드 안에서 병렬로 돈다
- μs epoch 는 약 1.7×10¹⁵. ZSET score(float64) 의 정수 정확도 2⁵³≈9×10¹⁵ 안에 들어간다

**단조 가드는 선택이 아니다.** `TIME` 은 벽시계라 NTP 보정이나 복제본 승격으로
뒤로 갈 수 있고, 그러면 **줄 선 사람을 추월**한다 (불변식 4). 큐가 빈 동안 시계가
되돌아가는 경우까지 막으려면 큐 최대 score 를 별도 키로도 남겨야 한다.
원래 D-P1 의 C안(점프)이 하던 일이고, 대상이 카운터에서 시계로 바뀌었을 뿐이다.

**무엇을 잃는가**

| | 바뀐 것 |
|---|---|
| 순위 | 뺄셈 → `ZCOUNT queue (admitted (my_score`. **폴링 경로**에 O(log N) 하나가 붙는다. 판정 경로가 아니므로 A-1 은 그대로다 |
| 입장 임계 | `INCRBY` → `ZRANGEBYSCORE ... LIMIT N-1 1` 로 N번째 score 를 읽는다. 스케줄러 틱에 읽기 하나 |
| 동점 | 같은 μs 는 ZSET 이 member 사전순으로 가른다. 결정적·안정적이지만 도착순은 아니다 — μs 안쪽 도착순은 의미가 없다고 본다 |

**따라오는 이득 둘**

- **크레딧 낭비가 준다.** 개수 기반 `INCRBY` 는 떠난 사람의 자리까지 소모했다.
  `ZRANGEBYSCORE` 는 실제 구성원 N명을 집는다 (D-8). Phase 7 의 "이탈 30%에서
  크레딧 낭비 <5%" 가 쉬워진다
- **샤딩 후 순위가 정확해질 수 있다.** 샤드가 갈려도 시계가 하나라 score 가 서로
  비교 가능하다. `로컬 순위 × S` 추정 대신 샤드별 `ZCOUNT` 합산이 가능하다
  (Phase 10 5절)

**순위 단조성은 도메인이 아니라 어댑터가 책임진다.** 도메인은 주입받은
`localRank` 가 단조라는 전제 위에서만 동작하므로, **그 전제를 Phase 3 이 지켜야
한다** (G3.11).

**A-7(펜싱 불필요)이 강해졌다.** `INCRBY admitted N` 은 리더 교체 중 두 번
적용되면 2N 을 입장시켰다. 임계를 계산해 덮어쓰는 방식은 두 번 적용돼도 값이
같거나 유계라, 펜싱을 안 쓰는 근거가 하나 더 생겼다.

**남은 위험**: ZSET 자체가 유실되면 대기자가 증발한다. E-6 이 이걸 다룬다.

### 2.8 R-* — 라우팅과 인스턴스 목록 (D-R1 해소)

운영 환경은 **k8s 가 아니라 EC2 노드 여러 대**다. 클러스터 DNS 도 Endpoints API 도
없고 **IP 가 언제 바뀔지 모른다.** 정적 목록은 그래서 못 쓴다.

| ID | 결정 | 근거 |
|---|---|---|
| **R-1** | 인스턴스 목록과 가중치를 **가용량 보고 하나에서** 받는다. 별도 레지스트리를 두지 않는다 | 가용량은 R2 때문에 어차피 매초 Redis 를 지난다. 주소를 얹는 비용이 0 이고 컴포넌트가 늘지 않는다 |
| **R-2** | 살아있음은 **보고의 신선도**로 판단한다 — **보고 주기 1초, 낡음 임계 3초**(3회 연속 누락) | 일반 헬스체크는 "살아있지만 포화" 를 정상이라 한다. `credits: 0` 은 "지금은 보내지 마라" 를 정확히 말한다. 임계는 이 한 곳에서만 정하고 다른 문서는 참조만 한다 |
| **R-3** | `instanceId` 는 **기동 시 생성한 UUID** | EC2 인스턴스 ID 로 두면 한 노드의 두 프로세스가 충돌한다. 재시작하면 in-flight 가 초기화되므로 다른 인스턴스로 보는 게 맞다 |
| **R-4** | 선택은 **가중 라운드로빈** — 여유 비율대로 결정적으로 돈다. 가중 P2C 는 설정으로 남긴다 (R-9·R-11) | 원래는 P2C 였다. **뽑은 이유가 실측에서 안 나타났다** — 게이트웨이 M 대가 같은 인스턴스로 몰린다는 것이었는데, 두 대를 띄워 재니 라운드로빈은 안 몰렸고 P2C 가 오히려 비율에서 밀렸다. 뽑은 근거가 사라지고 대가만 남았다. 값과 조건은 [09-routing.md](09-routing.md) 의 G9.9 행에 있다 (CY-916 · AIJ-0225) |
| **R-5** | Redis 가 낡으면 **목록을 비우지 않는다** (fail-static) | 전 인스턴스 배제는 100% 장애다. A-5 와 같은 논리 |
| **R-6** | 인스턴스별 전송량을 **집계하지 않는다** | 전역 카운트는 요청마다 Redis 를 요구한다 (A-1 위반). 보낸 결과는 다음 초의 가용량 보고에 나타난다 — 장부가 아니라 되먹임이다 |
| **R-7** | 보고의 만료를 **Redis TTL 로 하지 않는다.** 페이로드의 `ts` 를 읽는 쪽이 걸러낸다 | **해시 필드에는 개별 TTL 이 없다** (`HEXPIRE` 는 7.4+). 키 전체에 TTL 을 걸면 살아있는 인스턴스까지 사라진다. 읽는 쪽 필터는 버전에 안 묶이고 `SCAN` 도 필요 없다. 리더가 틱마다 오래된 필드를 `HDEL` 하지만 정합성이 거기 달려 있지는 않다 |
| **R-8** | in-flight 는 **요청 타임아웃을 넘긴 항목을 만료**시킨다. 보고 수신 시 리셋하지 **않는다** | in-flight 는 게이트웨이가 자기가 내보낸 요청 수라 백엔드 보고가 덮어쓸 값이 아니다. 리셋하면 3초짜리 요청이 살아있는데 0 이 되고, 끝날 때 감소가 걸려 **음수로 간다.** 마감을 달면 살아있는 요청을 안 버리면서 누수가 유계가 된다 |
| **R-9** | 라우팅 전략은 **설정으로 교체**한다 (재시작). **자동 전환하지 않는다** | 인스턴스 수로 자동 전환하면 ① 임계 근처에서 진동하고 — **롤링 배포가 정확히 그 구간을 지난다** ② 대시보드에 어느 구간이 무슨 모드였는지 안 남아 장애 분석이 막히고 ③ 카오스·부하를 두 전략 다 돌려야 하며 ④ 애초에 그 규모에서 두 전략의 차이가 실측으로 드러나는지가 미검증이다. 가정(A7)을 벗어나면 **경고 로그**로 알리고 판단은 사람이 한다 |
| **R-10** | 서킷은 **인스턴스별**로 연다. 백엔드 전체를 하나로 묶지 않는다 | 하나로 묶으면 한 대가 죽어도 전 트래픽이 막힌다. 인스턴스별이어야 로드밸런서가 그 한 대만 뺀다. **판정이 보는 값도 바뀐다** — "서킷이 열렸는가"가 아니라 **살아 있는 인스턴스 비율**이다. 10대 중 3대가 열렸는데 상한이 그대로면 남은 7대에 10대분이 몰린다 |
| **R-11** | **가중 P2C 와 가중 라운드로빈을 둘 다 구현**한다 | 인스턴스가 3~5대면 라운드로빈이 더 정확하다 — 무작위 둘을 뽑는 이득이 그 규모에서는 없다. 어느 쪽이 나은지는 실측으로 정할 문제고, 하나만 만들면 그 측정을 할 수 없다. **쟀더니 P2C 가 ±15% 를 못 넘겼다** (R-4) — 그래서 G9.9 는 미달로 남고 P2C 는 설정으로만 남는다. 둘 다 통과해야 한다는 원래 요구는 인스턴스가 쉰 대를 넘어 P2C 를 다시 볼 때 살아난다 |
| **G-1** | 페이즈를 **부분 충족으로 닫을 수 있다.** 조건은 셋이다 — ① 미달인 게이트마다 무엇이 왜 미달인지가 그 페이즈 표에 행으로 있고 ② 미달의 성격이 "안 한 것" 이 아니며 ③ 닫는 커밋이 실측치를 든다. 셋 중 하나라도 안 서면 안 닫는다 | 6-2 는 "하나라도 미달이면 다음을 시작하지 않는다" 인데, 그대로 읽으면 **밖의 선행을 기다리는 미달** 하나로 페이즈가 영영 안 닫힌다. Phase 8·9 가 연달아 그 자리에 걸렸고, 두 번 다 산문으로 다시 읽어 넘어갔다 — 규칙을 두 번 구부렸으면 규칙을 고치는 것이 맞다. **낮추는 것이 아니다**: 미달을 통과로 적는 것을 금지하고, 성격을 적을 것을 요구한다. "안 한 것" 은 여전히 못 닫는다 |

```
HSET capacity:coupon-svc:{version} <uuid> {"addr":"10.0.3.17:8080","credits":180,"ts":...}
                                 매 1초 갱신
읽을 때   now - ts > 3초  →  없는 것으로 취급 (R-2·R-7)
```

**구현은 라우터를 만드는 게 아니다.** Spring Cloud LoadBalancer 의 확장점 둘을
구현한다 — `ServiceInstanceListSupplier`(스냅샷에서 목록) 와
`ReactorServiceInstanceLoadBalancer`(credits 비례 선택). 라우트를 `lb://` 로 두면
`ReactiveLoadBalancerClientFilter` 가 URI 를 고른 인스턴스의 IP 로 갈아끼운다.

**in-flight 는 보고 지연만 메운다.** 최대 1초 동안 낡은 비율로 밀어넣는 구간이
있어 로컬 관측치로 가중치를 깎는다. 노드가 M 대면 각자 자기 몫만 아는 로컬 값이고,
전역을 알려면 요청마다 Redis 를 쳐야 한다 — 리미터의 `credit/N` 과 같은 처리다.

**계약 변경이 필요하다.** `credits` 만 올리던 것을 `{instanceId, addr, credits}` 로.
D-C1 에 합쳐 협의한다.

`D-C1`·`D-C2`·`D-C3` 해소, 그리고 검토에서 드러난 롤백 구멍(`P-1`)과 알람 부재(`P-2`).

| **B-16** | **개인화 응답 코얼레싱을 회귀 테스트로 막는다.** 상한 초과 응답은 버퍼링하지 않는다 | 지금은 개인화가 없지만 필드 하나가 붙는 순간 **남의 응답을 받는다.** 사람 리뷰로 막을 수 없다. 바디 버퍼링은 판정 경로 금지 규칙의 의도적 예외이므로 **크기 상한 밖에서는 포기하고 흘린다** — 보호 장치가 메모리 사고의 원인이 되면 안 된다 |

| **S-2** | **IP 상한이 실질 방어, `memberId` 상한은 폭주 감지** | 로그인·회원가입이 없어 `X-Member-Id` 를 바꾸는 비용이 0 이다. `memberId` 상한만으로는 우회되고, IP 는 NAT 공유 때문에 좁게 잡을 수 없다 — **역할이 달라서 둘 다** 둔다 |

| **P-2** | **알람은 증상 기반 + 다중 창 소진율** (Google SRE). 불변식 2 는 **게이트웨이 쪽 선행 지표**(틱 배분 합계 > `globalCredit`)로 감시한다 | 원인마다 걸면 장애 하나가 열 개를 울려 아무도 안 본다. 그리고 **초과 발급 자체는 게이트웨이가 볼 수 없다** — 재고는 발급 계층이 갖는다 (비목표) |

#### P-1 이 없으면 롤백 절이 자기를 부정한다

Phase 6 은 "보호 장치는 설정으로 끌 수 있게 둔다 — **되돌리기가 배포 없이

### 2.11 C-7 — 여유 평활을 대칭으로 두는 이유 (2026-08-26)

한 번 비대칭으로 바꿨다가 되돌렸다. 하강만 즉시 반영하면 뒷단이 "여유가
줄었다" 고 말한 순간 바로 조인다는 것이 착안이었는데, 따져 보니 잃는 것이 더
컸다. 실측과 계산은 [AIJ-0089](../ai/journal/2026/08/AIJ-0089-asymmetric-smoothing.md).

**비대칭 EWMA 는 평활기가 아니라 최솟값 추종기다.** 진동하는 관측에서 값이
평균이 아니라 최솟값 쪽으로 굳어 가용량을 절반 가까이 과소평가한다. 그만큼
`idleCap` 과 큐 상한이 좁아지고, 그것이 곧 R1 위반이다.

**모든 하강이 뒷단의 신호인 것도 아니다.** 리더가 바뀌면 새 수집기의 램프
기록이 비어 전 인스턴스가 램프를 처음부터 다시 탄다 (C-5). 그 하강은 뒷단이
아니라 우리가 만든 값인데, 비대칭이면 그대로 실린다. 이월 장치(C-6)는 첫
관측이 더 높을 때만 살아남으므로 이 구간에서 구조적으로 무효가 된다 — F9 를
만든 이유가 사라진다. 표시 ETA 를 나누는 분모도 이 값이라, 없앤 하강 평활이
하필 ETA 가 튀는 방향이었다 (R6).

애초의 동기도 약했다. 운영 계수 α=0.3 에 틱 1초면 반감이 1.94틱이다. 뒷단이
조이라고 말한 뒤 2초 늦게 따라가는 것이 문제라면 그 2초에 무엇이 깨지는지부터
적어야 하는데 적을 것이 없었다.

**분모(노드 수)의 비대칭과는 다른 값이다.** C-4 가 노드 수 감소를 늦추는 것은
분모가 작아지면 노드당 몫이 커져 초과가 되기 때문이다. 여기는 분자이고,
작아지는 방향이 안전한 쪽이라 같은 논리가 안 걸린다.

되돌린 자리에 남은 것은 하나다. 수집기는 램프가 만든 값과 뒷단이 보고한 값을
이미 가르고 있는데(`anyPositive`), 그 구분을 하한 판정에만 쓰고 크레딧 하나로
접어 버린다. 그 구분을 평활기까지 실어 보내는 일이 CY-569 다.

### 2.12 C-8 — `ALWAYS` 를 낡음보다 앞에 두는 이유 (2026-08-26)

운영자가 "무조건 줄을 세운다" 를 거는 순간은 오픈 직후다. 그리고 그때가 리더가
가장 흔들리는 순간이라 `dataStale` 이 잘 뜬다. 사다리에서 낡음 우회가 앞에 있으면
**그 설정이 정확히 필요한 구간에서만 무시된다.**

더 나쁜 것은 그 상태가 스스로 유지된다는 점이다. 아무도 큐에 안 들어가니
`hasQueue` 가 영영 거짓이고, 낡음이 풀릴 때까지 전원이 우회한다. 노드 열 대면
초당 1,000건이 대기열 없이 뒷단으로 직행한다.

**가용성을 맞바꾸지 않는다.** 낡음 우회가 있는 이유는 큐를 못 쓸 때 요청을
버리지 않기 위해서인데, 그 안전망은 그대로다 — 등록이 실패하면 부르는 쪽이 상한
있는 fail-open 으로 받는다. 순서를 바꾸는 것은 "먼저 줄을 세워 보고, 안 되면
우회한다" 이지 "우회를 없앤다" 가 아니다.

`OFF` 는 반대다. 그건 여전히 낡음 우회보다 뒤에 있어야 한다 — 앞에 두면 꺼진
쿠폰만 무제한으로 뒷단에 꽂혀 상한이 있으나 마나가 된다.

이 조합은 CY-517 로 운영자 모드가 발행에 실리기 전까지 **도달 불가였다.** 그래서
지금까지 근거가 필요 없었다.

### 2.13 C-9 — `OFF` 우회에 상한을 안 거는 이유 (2026-08-26)

`PASS_BYPASS` 는 리미터를 안 탄다. 다른 통과 경로가 전부 노드 예산을 쓰는 것과
다르고, 그래서 "꺼진 쿠폰만 무제한으로 뒷단에 꽂힌다" 는 지적이 나온다.

**상한을 걸면 그 모드가 하는 일이 없어진다.** 운영자가 대기열을 끄는 것은 그
쿠폰을 게이트웨이의 조절 대상에서 빼겠다는 뜻이다. 노드 예산을 쓰게 하면 다른
쿠폰과 같은 통에서 경쟁하므로, 예산이 빠듯한 순간에는 껐는데도 조여진다.

**안전을 떠받치는 것은 상한이 아니다.** 우회가 서려면 셋이 동시에 참이어야 한다 —
스냅샷이 신선하고, 줄이 안 보이고, 이 노드가 방금 안 세웠다. 그 조합에서는
**어느 노드도 줄을 세우지 않는다.** 사다리에서 등록으로 가는 줄은 전부 낡음이나
`hasQueue` 를 요구하기 때문이다. 추월당할 사람이 아예 없다.

**남는 창은 하나다.** 운영자가 켜 뒀다 끈 뒤 줄이 다 빠지는 그 구간이다. 마지막
한 명을 넣은 노드는 자기 래치로 막지만, 다른 노드는 그 사람을 모른 채 우회한다.
**상한은 이 창을 안 닫는다** — 넘는 사람 수를 줄일 뿐이다. 닫으려면 래치가 노드
로컬이 아니어야 하고, 그건 요청 경로에 공유 상태를 하나 더 놓는 일이라 불변식 1
과 맞바꾼다. 지금은 안 바꾼다.

낡은 구간은 다르다. 거기서는 `OFF` 도 상한 안에서만 통과한다 (사다리 4번이 5번
앞이다) — 상태를 모르는 구간에는 상한이 있어야 하고, 꺼진 쿠폰만 그것을
비켜 가면 그 상한이 있으나 마나가 된다.

### 2.17 O-5 — 오버헤드 게이트를 nightly 로만 두는 이유 (2026-08-27)

**정한 것.** G6.11(게이트웨이 오버헤드 p99 < 5ms)의 부하 잡을 `main` 의 필수
게이트에 안 넣고 nightly 에서만 돈다. **문턱은 안 내린다.**

**왜.** 갓 뜬 JVM 에서 이 값이 안 잡힌다. 같은 콜드 게이트웨이에 같은 부하를
넣고 예열만 바꿔 잰 값이다.

| 예열 | 오버헤드 p99 |
|---|---|
| 12초 | 9.82ms |
| 60초 | 5.44ms |
| 150초 | 5.58ms |

60초 위로는 안 내려간다. 남는 것은 JIT 가 아니라 실행 자체의 잡음이다. 이미 돌던
컨테이너에서는 같은 실행이 2.27ms 로 나왔으니, 문턱을 넘기는 것은 게이트웨이가
아니라 **기동 직후라는 조건**이다.

CI 는 매번 컨테이너를 새로 띄운다. 그러니 이 잡을 `main` 의 필수 게이트로 두면
**게이트웨이가 느려서가 아니라 방금 떴다는 이유로 병합이 막힌다.** 그 상태가
이어지면 결국 문턱을 올리자는 압력이 생기고, 그때 잃는 것은 이 게이트가 원래
지키려던 값이다.

**문턱을 안 내리는 이유.** 5ms 는 R4(피크 100K/초)에서 온 값이지 측정 편의에서
온 값이 아니다. 재기 어렵다는 것은 기준을 고칠 이유가 아니라 재는 법을 고칠
이유다.

**되돌리는 조건.** 예열이 끝난 상태를 CI 에서 재현할 수 있게 되면 `main` 으로
올린다 ([`CY-675`](https://shseol.atlassian.net/browse/CY-675)). 후보는 AppCDS·AOT 캐시로 기동 자체를 데우는 것, 그리고 compose 의
readiness 를 "떴다" 가 아니라 "데워졌다" 로 바꾸는 것이다. 지금 예열 문턱은
Redis 의 `gw:snapshot` 을 보는데, 그 값은 게이트웨이를 재시작해도 남아 있어
**콜드 JVM 을 데워졌다고 말한다** — 실제로 이번 측정이 그렇게 시작됐다.

**고려했으나 택하지 않은 것.**

*문턱을 8ms 로 올리는 것.* 콜드 실행을 통과시키는 값인데, 그러면 워밍된 상태에서
게이트웨이가 세 배 느려져도 안 걸린다. 재기 쉬운 기준은 지킬 것이 없다.

*예열을 더 늘리는 것.* 150초까지 넣어 봤고 안 내려간다. 실행 하나가 4분을 넘기고,
그 값을 주고 사는 것이 없다.

### 2.18 O-6 — 인스턴스별 게이트를 Phase 9 로 옮기는 이유 (2026-08-27)

**정한 것.** Phase 6 의 G6.2(한 인스턴스의 서킷이 열려도 나머지로 흐른다)와
G6.5(느린 인스턴스가 커넥션을 독식하지 못한다)를 **Phase 9 의 게이트로 옮긴다.**
기준은 그대로 두고 판정 시점만 옮긴다.

**왜.** **지금은 인스턴스가 하나뿐이라 그 문장을 만들 수 없다.** 발급 라우트의
`uri` 는 뒷단 주소 하나이고, 인스턴스 목록도 선택기도 Phase 9 의 9.1.1·9.1.3 에서
만든다 (R-1). 그 전까지 "인스턴스 한 대" 라는 말이 가리킬 대상이 없다.

그래서 이 두 게이트는 Phase 6 안에서 **통과도 미달도 판정할 수 없다.** 판정할 수
없는 기준을 게이트에 두면 둘 중 하나가 된다 — 통과로 세거나(측정 안 한 초록),
페이즈를 영원히 못 닫거나.

**G6.2 는 이미 Phase 9 에 같은 문장이 있다.** G9.10 이 "두 전략 모두 열린 서킷
인스턴스로 트래픽을 보내지 않는다" 이고, 이쪽이 더 세다 — 전략 둘을 다 본다.
G6.2 를 옮기는 것이 아니라 **G9.10 에 흡수시킨다.**

**G6.5 는 갈 자리가 없어 새로 만든다.** Phase 9 에 인스턴스별 동시 상한을 재는
게이트가 없다. G9.13 으로 단다.

**Phase 6 에서 하는 것.** 서킷 자체는 이미 붙어 있고(6.1.1~6.1.9) 느린 호출 집계도
있다. 격벽도 쿠폰별로 돌고 메모리 유계까지 못 박았다. **인스턴스라는 축만 없다.**

**되돌리는 조건.** 없다. 인스턴스 축이 생기는 시점이 Phase 9 이고, 그때 두 기준을
같이 판정한다.

**고려했으나 택하지 않은 것.**

*스텁을 두 대 띄워 Phase 6 에서 판정하는 것.* 하네스는 두 대를 띄울 수 있지만
게이트웨이가 그중 하나를 고를 수 없다. 하네스만 고치면 판정 대상이 없는 판을 또
하나 만드는 것이고, 이 저장소가 이번 페이즈에서 여러 번 밟은 자리다.

*Phase 9 의 라우팅을 Phase 6 으로 당기는 것.* 인스턴스 목록·선택 전략·in-flight
카운터가 한 덩어리라 페이즈 하나가 통째로 앞으로 온다. 순서를 정한 이유(보호가
먼저, 분배가 나중)를 뒤집는 값은 없다.

### 2.19 O-7 — 게이트웨이의 SLI 를 성공 응답이 아니라 판정으로 잡는 이유 (2026-08-28)

**정한 것.** 게이트웨이의 SLI 는 **"재료를 갖고 판정한 요청의 비율"** 이다. 목표는
30일 창에서 **99.9%**. 소진율은 5분·1시간과 30분·6시간의 이중 창으로 본다.

**왜 성공 응답 비율이 아닌가.** 이 제품은 **끊는 것도 줄 세우는 것도 정상 동작**이다.
격벽이 막은 503 과 큐 등록 202 는 게이트웨이가 자기 일을 한 결과이지 실패가 아니다.
2xx 비율로 SLI 를 잡으면 **보호 장치가 동작할수록 SLO 가 나빠진다** — 그 지표를 보고
할 수 있는 유일한 개선은 보호를 끄는 것이다.

**무엇을 실패로 세는가.** 게이트웨이가 자기 일을 못 한 것만 센다.

| 사유 | 왜 실패인가 |
|---|---|
| `PASS_FAIL_OPEN` | 낡은 재료로 열어 줬다 |
| `ENQUEUE_STALE` | 낡은 재료로 줄 세웠다 |
| `REJECT_OVERLOAD` | 낡은 재료로 상한을 물렸다 |
| 재료 없음 | 상한을 못 걸고 흘렸다 |
| 재료 낡음 | 같은 상태로 흘렸다 |
| 등록 실패 후 개방 | 줄을 못 세워 열어 줬다 — 줄 선 사람을 추월시킨 것이다 |
| 경로변수 없음 | 배선이 어긋나 판정이 통째로 없었다 |

**세는 것은 카운터 하나다.** 위 사유들을 운영 카운터에서 더해 만들지 않는다. 한
요청이 여러 사유를 지날 수 있어 — 재료가 낡아 열어 준 뒤 격벽 시한까지 걸리는
식으로 — 더하면 **실패율이 100% 를 넘는다.** 사유를 만나면 요청에 표시만 남기고,
요청이 끝날 때 `waiting.judgement{quality}` 를 한 번 센다. 라벨을 리네임해도 항이
조용히 빠지지 않는다.

**앞의 셋이 이 SLI 의 핵심이다.** `deferred-*` 는 **스냅샷에 없는 쿠폰에만** 붙는다.
실트래픽은 전부 스냅샷에 있는 쿠폰이라, 재료가 낡아도 `deferred-*` 는 안 오른다 —
사다리 4번과 7번으로 내려가 `PASS_FAIL_OPEN`·`ENQUEUE_STALE`·`REJECT_OVERLOAD` 가
된다. 이것을 빼면 **스냅샷 발행이 멎은 구간이 100% 성공으로 잡힌다.**

**무엇을 실패로 안 세는가.** 매진 종결, 정상 큐 등록, 격벽이 찬 503, 모르는 쿠폰
404, 회원 식별자 없음 400, **격벽 시한 초과**, 그리고 **`enqueue-error`**.

격벽 시한을 넘긴 요청도 **판정은 신선한 재료로 했다.** 그것까지 세면 뒷단 지연만으로
판정 예산이 타고, 그때 볼 것은 이 지표가 아니라 서킷과 보호 차단 알람이다. 마지막 것이 미묘한데, 줄을
못 세운 뒤 무엇을 했는지는 그 다음이 가른다 — 끊었으면(`enqueue-failed-shed`)
설계대로이고, 열어 줬으면(`enqueue-failed-open`) 추월이다. 등록 오류 자체를 세면
끊기도 같이 세게 되고, 열어 준 것은 두 번 세게 된다.

**분모.** 같은 카운터의 전부다. 요청 하나가 정확히 하나를 올린다.

**왜 이중 창인가.** 한 창만 보면 둘 중 하나가 된다 — 짧으면 순간 스파이크로 울리고,
길면 느린 소진이 몇 시간 동안 조용하다. 짧은 창과 긴 창이 **동시에** 넘을 때만
울린다. 배수와 등급 모두 구글 SRE 워크북을 따른다.

| 창 | 배수 | 소진 | 예산 소진까지 | 등급 |
|---|---|---|---|---|
| 1시간·5분 | 14.4 | 2% | 2.1일 | 호출 |
| 6시간·30분 | 6 | 5% | 5일 | 호출 |
| 3일·6시간 | 1 | 10% | 30일 | 티켓 |

**세 번째가 없으면 조용히 사라지는 구간이 남는다.** 6배는 닷새면 예산이 없어지니
느린 소진이 아니다. 배수 2(15일 소진)는 위 둘 어디에도 안 걸린다.

**저트래픽에는 실패 건수 바닥을 같이 건다.** 비율만 보면 한 시간에 69건 미만일 때
실패 한 건이 호출 임계를 넘는다. 새벽에 실패 하나로 사람을 깨우게 된다.

**바닥을 요청률로 걸면 안 된다.** 초당 0.5 는 시간당 1,800건이라, 그 아래에서
**전부 실패해도 알람이 안 뜬다** — 우발적 실패를 거르려다 진짜 장애를 통째로
덮는다. 실패가 다섯 건 이상일 것을 요구하면 둘 다 된다. `clamp_min` 은 `0/0` 을
막는 가드일 뿐 이 일과 무관하다.

**되돌리는 조건.** 99.9% 는 실측 없이 정한 값이다. 실부하에서 `deferred-*` 가 그
예산을 상시로 먹으면, **목표를 낮추기 전에 재료 신선도를 먼저 본다** — 그쪽이
원인이면 SLO 를 고칠 일이 아니다.

**고려했으나 택하지 않은 것.**

*HTTP 상태로 잡는 것.* 위와 같은 이유다. 게다가 게이트웨이의 503 과 뒷단의 503 이
같은 코드라 상태만으로는 누구 잘못인지 안 갈린다.

*지연을 SLI 에 넣는 것.* 오버헤드는 G6.11 이 잰다. 그 값은 뒷단을 뺀 것이라
스크레이프로는 못 만들고, 넣으면 SLO 가 하네스에 묶인다 (O-5).

### 3.1 디스커버리로 갈아탈 때 (R-1 재검토)

**지금 안 쓰는 이유는 못 써서가 아니라 중복이어서다.** 가용량이 어차피 매초
Redis 를 지나가니 목록만 받자고 컴포넌트를 세울 이유가 없었다.

갈아탄다면 **`ServiceInstanceListSupplier` 하나만 교체**한다. 로드밸런서도 판정도
in-flight 도 목록의 출처를 모른다. 지금 설계의 값이 여기 있다.

```
쿠폰 서비스 ──▶ Consul/Eureka   등록: addr + 헬스체크
            └─▶ Redis          보고: {credits}   ← 여전히 필요

게이트웨이  ──▶ DiscoveryClient  목록 ┐
            └─▶ HGETALL capacity 가중치┴─▶ 조인해서 ServiceInstance 완성
```

**가용량까지 디스커버리에 넣지는 않는다.** Consul 은 Raft 기반 CP 스토어라
인스턴스마다 초당 쓰기를 밀어넣는 건 합의 프로토콜을 지표 수집기로 쓰는 것이다.
Eureka 메타데이터는 하트비트에 실려 기본 30초다 — 초 단위 신호에 안 맞는다.

| 신호 | 주기 | 중요한 것 | 맞는 저장소 |
|---|---|---|---|
| 멤버십 | 배포·스케일 때 | 일관성 | Consul 같은 CP 스토어 |
| 가용량 | 초당 | 최신성 (근사 가능) | Redis 같은 빠른 캐시 |

**얻는 것**: 실패 도메인이 갈린다. 지금은 Redis 가 흔들리면 목록과 가중치가 동시에
낡지만, 갈라두면 Redis 가 죽어도 목록은 살아 가중치를 균등으로 낮춰 계속 돌릴 수 있다.

**치르는 것**: 운영할 컴포넌트가 늘고, 진실의 출처가 둘이 되어 어긋나는 구간이
생긴다 — "디스커버리엔 있는데 보고가 아직 없다", "보고는 오는데 디스커버리에서
빠졌다". 조합마다 정책이 필요하다. 출처가 하나면 안 생기는 질문들이다.

### 2.14 C-10 — 노드 몫이 있으면 한산 상한을 0 으로 안 내리는 이유 (2026-08-26)

`idleCap` 은 노드 몫에 한산 비율을 곱한다. 몫이 1 이면 `1 × 0.7 = 0.7` 이 정수로
잘려 **0** 이 되고, `hasRoom` 이 `cap > 0` 을 먼저 보므로 그 쿠폰은 첫 요청부터
`ENQUEUE_RATE_COUPON` 이다. 노드 예산은 한 명을 받을 수 있는데 쿠폰별 상한이
먼저 막는 것이라, **아무도 안 몰리는 쿠폰이 전 노드에서 줄을 선다** — R1 역전이다.
진단도 거짓말을 한다. 이름은 "그 쿠폰을 조였다" 인데 실제로 조여진 것은 반올림이다.

`CapacityCollector` 의 하한은 이 자리를 안 덮는다. 그 하한은 관측이 비었거나 램프에
깎였을 때만 답이 되고, 뒷단이 신선하게 `노드 수 × 2` 미만을 보고하면 그 값이 그대로
나간다. 게이트웨이 20대에 뒷단 합계 30 — 회복 구간의 전형적인 모습이다.

**B-2 가 막는 자리와 다르다.** 거기는 크레딧이 노드 수보다 적어 노드 몫이 0 인
경우이고, 각자 하나씩 통과시키면 총합이 크레딧을 넘는다. 여기서 1 을 보장하는 것은
몫이 1 이상일 때뿐이고, 그때 총합은 노드 수 이하이며 `globalCredit >= 노드 수` 이므로
넘지 않는다. 노드 총량은 tier2 가 따로 막는다.

**비율 0 은 예외로 둔다.** 그건 절삭이 아니라 한산 통과를 끄는 설정이라, 여기서 1 을
얹으면 운영자가 끈 것이 안 꺼진다.

### 2.15 O-4 — `gradle/actions` 를 v5 에서 멈추는 이유 (2026-08-26)

액션 핀 검사를 붙이면서 이 액션이 v4.4.3(2025-09)에 묶여 있는 것을 봤다. 주석이
`# v4` 라 Dependabot 이 그것을 의도로 읽고 그 메이저 안에서만 올렸기 때문이다.
지금 최신은 v6.3.0 이다.

**v6 은 코드 변경이 아니라 라이선스 변경이다.** 캐싱 기능이
`gradle-actions-caching` 이라는 별도 컴포넌트로 빠지면서 MIT 를 벗어나 Gradle 의
상용 약관 아래로 갔다. 릴리스 노트가 "v6 으로 올리는 것은 그 약관에 동의하는
것" 이라고 명시한다. 그건 도구 버전을 올리는 일이 아니라 계약이고, 봇도 리뷰어도 아닌
사람이 정할 일이다.

**v5 까지는 올린다.** v5 의 변경은 노드 24 로의 이동뿐이고, GitHub 호스티드
러너는 한참 전에 그 버전을 넘었다. 우리가 쓰는 것은 캐싱과 의존성 제출인데 v5
에서는 둘 다 MIT 그대로다.

**되돌아볼 조건.** 캐싱이 실제로 병목이 되어 v6 의 새 구현이 필요해지거나,
Gradle 이 약관을 바꾸면 다시 본다. 그전까지는 검사가 `v5.x` 를 정확한 버전으로
요구하므로 조용히 넘어갈 수 없다.

### 2.16 C-11 — 멱등 키의 시도를 클라이언트가 가르는 이유 (2026-08-26)

타임아웃을 켜면 **게이트웨이가 끊어도 뒷단은 처리했을 수 있다.** 사용자가 다시
시도하면 같은 사람이 두 번 발급되므로, 뒷단의 멱등성(A-10)이 작동할 근거를
게이트웨이가 줘야 한다. 문제는 **무엇을 한 번의 시도로 볼 것인가**다.

**입장 토큰을 재료로 쓰려 했는데 틀렸다.** 토큰 문자열은 30초 창마다 바뀐다
(`SignedToken` 이 만료를 창 단위로 끊는다). 09:00:29 에 받은 토큰으로 발급을
시도해 끊기고, 09:00:33 에 상태를 다시 물으면 새 문자열이 나온다. 재시도는 다른
키로 가고 뒷단은 새 시도로 처리한다 — **타임아웃 재시도가 몇 초 안에 안 끝나는
것이 보통이라, 이 창을 밟는 것이 예외가 아니라 기본값이다.**

**통과 경로가 바뀌어도 갈린다.** 한산할 때 토큰 없이 통과한 사람이 재시도할
때는 쿠폰이 몰려 줄로 갈 수 있고, 그러면 토큰을 들고 통과한다. 타임아웃이 나는
이유가 곧 부하이므로 이 순서는 자연스럽다.

**`(쿠폰, 회원)` 만으로 줄이면 정상 발급이 사라진다.** 두 번 줄 서서 두 번 차례가
온 사람의 두 번째가 재생으로 버려진다. 게이트웨이는 그 사람이 두 장을 받아도
되는지 모른다 — 발급 정책은 뒷단 것이고, 계획서 5절이 "게이트웨이는 발급 로직을
갖지 않는다" 를 비목표로 못 박았다.

**그래서 시도는 클라이언트가 가른다.** 사용자 행동 하나에 값을 하나 만들고
재시도에는 같은 값을 쓴다 — 결제 API 들이 쓰는 형태다. 게이트웨이는 그 값을
**검증된 회원에 묶어** 서명한다. 그러면 뒷단 로그에서 주운 키를 실어 남의 진짜
시도를 재생으로 버리게 만드는 길이 막힌다.

**값을 안 주면 `(쿠폰, 회원)` 으로 떨어진다.** 그때는 두 번째 정상 발급을 잃을 수
있지만, 초과 발급은 타협 불가이고(불변식 2) 잃는 쪽은 아니다. 안전한 방향으로
치우친다.

**모든 통과 경로가 덮는다.** 한 갈래만 덮으면 나머지에서 클라이언트가 준 값이
그대로 뒷단에 닿는다. fail-open 은 레디스가 흔들리는 구간이고 뒷단 지연이 가장
큰 구간이라, 거기서 안 막히면 이 장치가 있으나 마나다.
