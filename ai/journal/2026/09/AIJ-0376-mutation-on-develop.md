# 뮤테이션 회귀를 develop 에서 먼저 본다

## 무엇을

야간이 develop 도 뮤테이션을 따로 잰다. 가드는 실패할 때와 끝날 때 살아남은 뮤턴트와 판정 안 선 뮤턴트를
클래스·메서드·줄로 로그와 잡 요약에 쓴다. 뮤테이션 리포트는 7일 보관하고, main 의 뮤테이션 잡 제한을
40분에서 60분으로 올렸다.

## 왜 (근거)

**main 의 야간이 아홉 번 빨갰던 까닭을 분석하니 셋이 겹쳐 있었다.** 첫째, 스케줄은 기본 브랜치에서만 돈다. develop 에 쌓인
회귀는 릴리스 PR 을 main 으로 열 때에야 처음 재어졌고, 그 뒤 매일 밤 같은 실패가 났다. 둘째, 가드는 "몇 개 모자라다"
한 줄만 남겼다. 보관 2일이 지나면 어느 뮤턴트인지 찾을 길이 없었다. 셋째, main 의 잡은 40분 제한에 38분을 써 시간
초과와 점수 미달이 섞일 수 있었다.

**위치는 통과해도 남긴다.** 점수가 임계 근처(최근 89.9%)에서 흔들려, 초록인 밤에도 어느 뮤턴트가 경계인지가 다음
작업의 재료다. 요약이 실패해도 판정은 안 바뀐다.

**develop 실행은 판정과 리포트에 넣었다.** 밖에 두면 빨개져도 아침 리포트가 "이상 없음" 으로 나간다.

## 고려했으나 택하지 않은 것

- **PR 마다 증분 뮤테이션** — 바뀐 클래스만 재도 시험 전체를 도는 비용이 커, PR 을 여는 속도를 떨어뜨린다. 야간 develop
  실행이 하루 안에 같은 회귀를 잡는다
- **임계를 낮춘다** — 기준을 못 지킬 때 기준을 고치는 것은 재는 것이 아니다

## 확신이 낮은 부분 / 남은 위험

- develop 실행은 이 변경이 main 에 릴리스된 뒤부터 스케줄로 돈다. 그 전에는 `workflow_dispatch` 로 부를 수 있다
- 시험 워크플로 본문은 부른 쪽(main)의 것이고 스크립트는 develop 의 것이다. 요약 스크립트가 없는 옛 커밋을 재면
  요약을 건너뛴다

## 어떻게 검증했는가

요약 스크립트의 자기검증(판정 안 선 것·살아남은 것의 위치, 죽인 것과 시간 초과 제외, 클래스별 수, 목록 상한, 리포트
없음과 깨짐, 잡 요약)을 규범 검사에 넣었다. 마지막 야간 실행의 실제 리포트로 돌려 2948개 중 살아남은 299개가 클래스별
수와 줄 순서로 나오는 것을 봤다. 워크플로는 YAML 파싱과 판정 배선 검사로 봤다.

## 다음 사람이 알아야 할 것

- 뮤테이션이 빨개지면 잡 요약의 "뮤턴트 위치" 부터 본다. 클래스별 수가 몰린 곳이 시험이 약한 곳이다
- 마지막 야간(main)은 임계 90% 에 5개 모자랐다. v0.9.0 전에 develop 실행 결과로 다시 본다
