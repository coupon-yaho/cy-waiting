# 매달림을 없앴더니 그 자리에 서킷이 드러났다

## 무엇이 잘못돼 있었나

뒷단 HTTP 연결에 상한이 안 정해져 있었다. 프레임워크 기본값은 **30초**다
(`HttpClientProperties.connectTimeout` — "the default is 30s").

`application.yml` 에 `connect-timeout: 1s` 가 있긴 한데 그건 **레디스** 것이다.
같은 이름이 다른 계층에 있어서, 있는 줄 알고 지나가기 쉬운 자리였다.

죽은 컨테이너의 주소로 보낸 SYN 은 거절도 안 오고 그냥 답이 없다. 그러면
연결이 30초까지 매달리고, 그 전에 응답 상한 12초가 먼저 걸린다. **어느 쪽도
"연결 실패" 가 아니다.** 그래서 연결 실패에만 무는 재시도(9.3.11)가 볼 것이
없었다 — 배선은 맞는데 걸릴 사건이 안 생긴 것이다.

## 어떻게 드러났나

한 대를 죽이고 응답을 세는 실측(9.4.3)이다. 죽인 뒤 뒷단까지 간 64 건 중
**36 건이 응답 없이** 끝났다. 게이트웨이 로그에 재시도가 한 줄도 없었다.

5xx 는 0 이었다. **그것만 보면 통과다** — 게이트가 "5xx 유출 0" 이라고만
적혀 있었기 때문이다. 사용자에게는 오류를 받는 것보다 나쁘다. 몇 초를
기다린 뒤 아무것도 못 받는다. 판정에 "응답 없음" 을 유출로 세는 갈래를
넣은 뒤에야 미달로 나왔다.

## 무엇을 했나

라우트가 이미 메타데이터로 응답 상한을 건다. 프레임워크가 같은 자리에서
`connect-timeout` 도 읽으므로(`RouteMetadataUtils.CONNECT_TIMEOUT_ATTR`)
거기 붙였다. 값은 **500ms** 다 — 같은 데이터센터 안의 연결은 밀리초 단위라
넉넉하고, 응답 상한 12초보다는 한참 짧다.

**응답 상한보다 길면 기동을 막는다.** 길면 응답 상한이 먼저 끊어 연결 실패가
영영 안 드러나고, 그 요청은 재시도 없이 그대로 실패한다 — 연결 상한을 둔
이유가 사라진다. 시험으로만 두면 배포 설정 한 줄이 이 순서를 뒤집고, 그
사실은 장애 때만 드러난다. 응답 상한과 격벽 시한 사이에 이미 같은 모양의
검증이 있어 그 옆에 나란히 뒀다.

## 새 검증이 곧바로 시험 셋을 막았다

응답 상한을 300ms 로 줄여 쓰는 카오스 시험이 셋 있다. 연결 상한 기본값 500ms
가 그보다 길어서 기동이 막혔다 — **검증이 의도대로 문 것이다.** 그 시험들에
짧은 연결 상한(100ms)을 같이 줬다.

이게 검증을 기동에 둔 이유이기도 하다. 시험으로만 뒀으면 이 조합이 조용히
지나가고, 그 판에서는 연결 실패가 응답 상한에 가려진 채 무엇을 재는지 모르게
됐을 것이다.

## 고려했으나 택하지 않은 것

- **`spring.cloud.gateway.server.webflux.httpclient.connect-timeout` 으로 전역
  설정한다** — 라우트마다 다르게 줄 수 없다. 조회와 발급은 성격이 다르므로
  라우트별로 둘 자리를 남긴다. 지금은 같은 값을 쓴다
- **응답 상한에서 유도한다** (예: 응답 상한의 1/20) — 두 값의 이유가 다르다.
  연결은 망 왕복이고 응답은 뒷단 처리 시간이라, 한쪽이 바뀔 때 다른 쪽이
  따라 움직이면 안 된다

## 게이트 문구는 여기서 안 고친다

G9.4 행은 실측을 담은 브랜치(CY-903)가 들고 있다. 두 브랜치가 같은 줄을 고치면
병합에서 부딪히고, 그때 한쪽 문장이 조용히 사라진다. **고친 사실은 그 행에서
합친다.**

## 고친 뒤 다시 쟀다 — 매달림은 사라졌다

같은 하네스로 다시 쟀다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 응답 없음 | **36 건** | **0 건** |
| 5xx | 0 건 | 202 건 |
| 뒷단까지 간 것 | 64 건 | 364 건 |

**연결이 500ms 에 실패한다.** 매달리지 않으니 같은 12초에 표본이 다섯 배 이상
쌓였고, 사용자가 몇 초를 기다린 뒤 아무것도 못 받는 일이 없어졌다.

## 그 자리에 서킷이 드러났다

5xx 202 건의 출처는 서킷이다. 로그가 그대로 말한다.

> 서킷 열림(OPEN) — backend 로 가는 발급을 막는다

연결 실패가 빠르게 쌓이자 서킷이 열렸고, **서킷이 뒷단 전체에 하나뿐이라**
멀쩡한 두 대로 갈 요청까지 막혔다. 죽은 대 하나가 전체를 끈 것이다.

**이건 새 결함이 아니라 이미 아는 것이다.** G9.10 이 "인스턴스별 서킷이 없어
배제하면 전부 빠진다" 로 막혀 있고, 같은 뿌리가 여기서도 나온다. 연결 상한은
**매달림을 실패로 바꾸는 데까지**가 제 몫이고, 그 실패를 한 대에 가두는 것은
인스턴스별 서킷의 몫이다.

그래서 G9.4 는 **아직 미충족**이다. 다만 미충족의 이유가 바뀌었다 — "연결이
실패하지 않는다" 에서 "실패가 한 대에 안 갇힌다" 로.

## 고친 것을 확인하려다 두 번 헛돌았다

**첫 재측정이 고치기 전과 똑같은 값을 냈다.** 36/64 그대로였다. 진단이 틀린
줄 알았는데, 게이트웨이 이미지가 낡아 **새 설정이 안 들어가 있었다.** compose
는 JAR 이 바뀌어도 이미 있는 이미지를 그대로 쓴다. 고친 코드가 아니라 옛
바이너리를 재고 그 값을 실측으로 적을 뻔했다.

하네스 넷 모두 **JAR 이 있는지 보고 이미지를 다시 짓게** 했다. 이 함정에는
전에도 한 번 걸렸다 (AIJ-0208 의 "이미지가 나흘 전 것이었다").

**두 번째는 내가 도는 스크립트를 편집해서 깨졌다.** 배시는 스크립트를 조금씩
읽으므로, 실행 중에 파일이 바뀌면 읽는 위치가 어긋나 엉뚱한 줄을 실행한다.
`deadline: 바인딩 해제한 변수` 가 그 증상이었다.

## 리뷰가 둘 다 실제 결함으로 확인했다

아래 "확신이 낮은 부분" 에 적어 둔 둘이 의심으로 끝나지 않았다. 장애 경로
리뷰가 각각 배선상의 확정 결함임을 짚었고, 라이브러리 소스를 열어 확인했다.

### 재시도는 안 걸린 게 아니라 걸릴 수 없었다

추정("서킷이 먼저 열려서")이 틀렸다. 진짜 이유는 **필터 순서와 폴백의 조합**이다.

`ROUTE_RETRY(1)` 가 `ROUTE_CIRCUIT(2)` 보다 작아 재시도가 서킷을 감쌌다. 그런데
서킷 필터에 폴백 주소가 걸려 있고, Spring Cloud Gateway 의
`SpringCloudCircuitBreakerFilterFactory` 는 폴백이 있으면 **하류의 모든 오류**를
그리로 넘기고 정상 완료를 내보낸다.

```java
return cb.run(chain.filter(exchange)..., t -> {
    if (config.getFallbackUri() == null) {
        return Mono.error(t);      // 폴백이 있으면 여기 안 온다
    }
    ...
    return handle(getDispatcherHandler(), ...);   // 성공 Mono
});
```

바깥의 재시도는 볼 오류가 없고, 상태 기반 재시도는 우리가 껐다. **두 갈래가 다
막혀 있었다.** 그래서 이 엔트리가 "인스턴스별 서킷이 붙은 뒤에 다시 보자" 로
남긴 처방은 틀렸다 — 각 서킷이 폴백을 들고 있는 한 그것만으로는 안 풀린다.

**순서를 뒤집었다.** 재시도를 서킷 안쪽(`ROUTE_CIRCUIT + 1`)으로 옮겼다. 원래
바깥에 둔 근거는 "안쪽이면 서킷이 요청 하나에 결과 하나만 본다" 였는데, 그편이
오히려 맞다 — 서킷이 재야 할 것은 "이 요청이 끝내 실패했는가" 이지 "TCP 시도가
몇 번 실패했는가" 가 아니다. 바깥에 두면 한 대의 연결 실패가 전역 서킷 창을 두 배
속도로 밀어 멀쩡한 나머지까지 끊는다.

### 값 검사만 있어서 못 잡았다

시험이 재시도 횟수와 필터 순서라는 **값**만 봤다. 연결이 실제로 실패했을 때 두
번째 시도가 나가는지를 보는 시험이 없었다. 그래서 배선이 한 번도 안 도는 채로
전건 초록이었다.

`ConnectRetryTest` 를 넣었다. 죽은 포트와 산 스텁을 같은 여유로 실어 라운드로빈이
번갈아 고르게 하고, 여섯 건이 다 200 으로 끝나며 **산 대가 여섯 건을 다 받는지**
본다. 상태만 보면 폴백이 200 을 낼 때 못 가르므로 뒷단이 센 수를 같이 본다.
고치기 전에는 이 시험이 503 으로 떨어졌다.

### 500ms 는 왕복 시간이 아니라 SYN 재전송으로 잡을 값이었다

근거가 얇은 정도가 아니라 하한을 잘못 잡고 있었다. 연결 상한이 걸리는 순간은
정상일 때가 아니다 — 뒷단의 accept 큐가 넘치면 커널이 SYN 을 조용히 버리고,
리눅스의 첫 재전송은 **1초 뒤**다. 500ms 는 그 전에 포기하므로 **멀쩡한
인스턴스를 실패로 접는다.**

그리고 accept 큐가 넘치는 순간이 하필 서킷이 닫히며 억눌린 것이 풀리는 회복
구간이다. 커넥션 풀이 탄력적이라 그때 새 커넥션을 그만큼 연다. 즉 **회복이
2차 장애를 만드는 경로**이고, 그건 이 변경이 새로 연 것이다 — 30초였을 때는
재전송이 결국 붙었다.

**2초로 올렸다.** 첫 재전송 뒤로 여유를 두고, 재시도가 한 번 더 붙어도 4초라
응답 예산(12초) 안이다.

배포 파일의 값을 시험이 안 보고 있던 것도 같이 고쳤다 — 리뷰가 11초로 바꿔
보니 스위트가 전건 초록이었다. `BackendTimeoutBudgetTest` 가 배포 파일에서
직접 읽어 부등호로 건다. 실측 전이라 등호로는 못 박는다.

## 라우팅을 끄면 재시도를 안 건다

재시도가 실제로 돌기 시작하면서 하나가 따라왔다. 단일 주소로 되돌린 판에는
고를 다음 대가 없어, 재시도가 **같은 죽은 주소로 두 번** 간다 — 연결 시도와
사용자 대기가 그냥 두 배다. 그 스위치를 당기는 순간이 하필 뒷단이 아플 때라
(Phase 9 5절), 부하를 줄이려고 당긴 것이 부하를 늘린다.

`lb://` 일 때만 재시도 필터를 건다. 라우트를 짓는 자리가 이미 그 분기를 알고
있어 한 줄이다.

## 확신이 낮은 부분 / 남은 위험

- **2초도 실측이 아니다.** 하한의 근거(SYN 재전송)는 분명해졌지만, 상한 쪽은
  여전히 "매달림으로 돌아가지 않을 만큼" 이라는 감이다. accept 백로그를 실제로
  넘치게 해 재는 것이 남았다
- **응답 상한을 낮추면 노드가 기동에 실패한다.** 두 값이 짝으로 움직여야 하는데
  검증이 하드 실패라, 장애 중에 응답 상한만 낮추면 전 노드가 크래시 루프에
  든다. 클램프 + 경고로 바꾸는 것이 맞아 보이나 이 브랜치의 범위 밖이다
- **폴백 지표에 인스턴스 차원이 없다.** 어느 대가 안 붙는지를 게이트웨이
  지표로는 못 가른다. 경보도 `state` 라벨을 뭉갠다

## 다음 사람이 알아야 할 것

**게이트 표는 여기서 안 고쳤다.** `plan/09-routing.md` 의 G9.4·G9.11 행이 이
브랜치가 사실로 만든 것과 어긋나는데, 같은 파일을 CY-903 이 크게 고치고 있어
두 곳에서 만지면 충돌한다. CY-903 이 머지된 뒤 이 브랜치를 갱신하면서 같이
고친다.

**연결 단계를 덮는 카오스 시나리오가 없다.** C7 은 가용량 쪽만 보고, C18 은
제목부터 "TCP 는 받고" 다. "SYN 을 보냈는데 답이 없다" 는 자극을 만드는
시나리오가 필요하다 — 컨테이너를 죽이면 RST 가 와서 블랙홀이 안 된다.
패킷을 DROP 해야 한다. 진입(연결 상한 안에 실패하고 다음 대로 넘어간다),
유지(한 대의 실패가 전역 서킷을 안 연다), 회복(복귀 뒤 램프)의 3단계로 쓴다.
