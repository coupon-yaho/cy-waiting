# 같은 값 조합이 두 상태를 다 가질 수 있었다

## 무엇이 잘못돼 있었나

I3 이 한쪽만 봤다. `DRAINING` 이면 `credit >= waiting` 을 요구했지만, 반대인
`QUEUEING` 이면서 `credit >= waiting` 인 조합은 안 막았다. 그래서 `(credit=500,
waiting=100)` 이 `DRAINING` 으로도 `QUEUEING` 으로도 만들어졌다.

`offWithQueue` 가 `runtime` 을 `QUEUEING` 으로 못 박고 있어서 실제로 그 조합을
만들었다.

## 판정은 하나도 안 바뀐다 — 근거를 정정한다

**처음에 "다 뺄 수 있는 줄인데 계속 줄을 세운다" 를 버그로 적었다. 틀렸다.**

`runtime` 을 읽는 곳은 `AdmissionDecider` 의 사다리 8번 한 줄이고 조건은
`!= IDLE` 이다. `DRAINING` 과 `QUEUEING` 이 같은 칸이라 고치기 전에도 후에도
`ENQUEUE_BACKLOG` 다. `OffModeQueueTest` 가 diff 에 없는데 그대로 통과하는 것이
그 증거다.

게다가 **"다 뺄 수 있는 줄에 계속 줄을 세우는 것" 자체가 요구 동작이다.**
`waiting > 0` 이면 신규 유입은 뒤에 서야 한다 — 불변식 4 다. 배수 중이라고
통과시키면 그게 추월이다.

그러니 이 변경이 얻는 것은 **표현의 유일성** 하나다. 같은 사실을 두 이름으로 적을
수 있으면 두 발행자가 다르게 적고, 그때부터 상태가 사실을 안 말한다. 판정 결과의
변화가 아니라 모델의 정합성이다.

## 경계

`credit == waiting` 은 다 뺄 수 있으므로 `DRAINING` 한쪽에만 속한다. 두 방향이
같은 자리를 써서 `waiting > 0 && stock > 0` 구간을 정확히 이분한다 — 어느 쪽도
아닌 틈도, 둘 다인 겹침도 없다.

**`stock == 0` 에서는 유일성이 안 선다.** I2 가 `CLOSED ⟹ stock == 0` 한쪽만
걸어서 `CLOSED` 와 `DRAINING` 이 같은 값 조합을 공유한다. 이 변경이 파는 성질의
**한계**이므로 계획서 표에도 같이 적었다.

배분기 쪽에서도 `==` 가 맞다. `CouponDemand.want() = min(waiting, stock)` 이고
`FairShareAllocator` 가 grant 를 `want()` 로 막으므로 배분 직후엔 항상
`credit <= waiting` 이고, `credit == waiting` 은 "요구를 다 채웠다" 는 뜻이다.

`I3'` 은 `I4` **뒤에** 둔다. 앞에 두면 줄이 빈 `QUEUEING` 이 여기서 먼저 걸려
"줄이 비었다" 대신 "다 뺄 수 있다" 고 답한다 — 원인을 잘못 말한다.

## 고려했으나 버린 것

- **`runtime` 을 저장하지 않고 매번 `(credit, waiting)` 에서 유도한다.** 모순이
  구조적으로 불가능해지고 아래 "남긴 위험" 도 사라진다. 다만 wire 형식(`FIELDS = 6`)
  을 바꿔야 하고, 배분기가 히스테리시스 같은 **판단**을 실을 자리가 없어진다.
  Phase 4 배분기 착수 직전이라 지금 결정할 문제로 분리했다 (CY-323).
- **`CLOSED ⟹ credit == 0` 과 `stock == 0 ⟹ CLOSED` 도 함께 넣기.** 지금 자유형
  생성자가 `(CLOSED, credit=500, stock=0)` 을 통과시키고, 그 때문에 위에 적은
  유일성이 `stock == 0` 에서 깨진다. 사다리 1번이 `stock <= 0` 을 먼저 걷어내
  판정에는 해가 없고, 넣으면 코덱이 떨구는 축만 한 개 더 는다. **유일성 주장의
  한계로 문서에 적고** 판단은 CY-323 과 함께 한다.
- **팩토리를 `offWhileQueueing` / `offWhileDraining` 으로 쪼개기.** "팩토리 하나 =
  상태 하나" 계약에는 맞지만, 부르는 쪽이 경계를 다시 계산해야 해서 갈릴 자리를
  오히려 늘린다. 유도를 유지하되 **경계를 시험으로 못박는 쪽**을 골랐다.

## 파장 — 픽스처 8곳이 도달 불가 상태를 만들고 있었다

다섯 곳은 **`credit` 만 쓰는 시험**인데 `waiting` 을 아무 값이나 넣어 둔 것이었다
— `queueing(100, 500, 10)` 처럼. `contendedCap` 과 `queueCapacity` 는 `waiting` 을
안 읽으므로 단언은 그대로 두고 `waiting` 만 정합하게 고쳤다. 무작위 시험 둘은
`waiting = credit + 1` 로 묶어 어떤 `credit` 이 나와도 성립하게 했다.

여섯 번째(`QueueDerivedTest`)는 **단언 인자까지 바꿨다.** I3' 가 "credit 이 크면
waiting 은 더 커야 한다" 를 강제하는 바람에, 원래 픽스처를 그대로 살리려면
`waiting` 이 R4(동시 대기 20,000)의 수천억 배가 된다. 그래서 오버플로를 `credit`
이 아니라 `maxEtaSec` 으로 내게 바꿨다 — 곱이 `credit * maxEtaSec` 이라 같은
분기를 치고, 쿠폰 상태는 도달 가능한 값으로 남는다. 극단값을 없앤 것이 아니라
**상태에서 인자로 옮긴 것**이다.

나머지 두 곳(`OffModeQueueTest`)은 **고친 것이 아니라 조용히 재분류된 것**이다.
`offWithQueue(500, 10_000, 100)` 이 `QUEUEING` 에서 `DRAINING` 으로 바뀌었는데
단언(`ENQUEUE_BACKLOG`)은 8번이 `!= IDLE` 이라 양쪽 다 통과한다. 시험의 목적
(불변식 4)은 살아 있고, `OFF + QUEUEING` 커버리지는 `waiting = 20_000` 쪽에 남아
있다.

## 어떻게 검증했는가

뮤턴트를 만들어 되돌려 봤다.

| 뮤턴트 | 죽는 시험 |
|---|---|
| I3' 제거 | I3 시험 2개 + 코덱 격리 1개 |
| 생성자 경계를 `>` 로 | 경계 시험 |
| **팩토리 경계만 `>` 로 (두 경계가 갈림)** | **offWithQueue_는_경계에서_DRAINING을_고른다** (단독) |
| 팩토리 경계를 `credit + 1 >= waiting` 으로 | offWithQueue_는_경계_바로_아래에서_QUEUEING을_고른다 (단독) |
| `waiting <= 0` 를 `< 0` 으로 | offWithQueue_는_줄이_비었으면_거부한다 (단독) |
| **`I3'` 를 `I4` 앞으로 옮기기** | **대기자가_0인데_QUEUEING이면_생성에_실패한다** |

**세 번째가 처음엔 살아남았다.** 코드 주석과 계획서가 둘 다 "경계가 갈리면
팩토리가 생성자에 막히는 조합을 만든다" 고 경고해 놓고, `credit == waiting` 으로
팩토리를 부르는 시험이 하나도 없었다. 생성자 쪽 단언은 `runtime` 을 인자로 받으니
동어반복이라 경계를 못 지킨다 — 경계를 참으로 만드는 유일한 주체는 **유도하는
팩토리**다. 거기에 대고 결과 상태를 재는 시험을 넣어 잡았다.

갈렸다면 `credit` 이 대기자와 정확히 같아지는 순간 — 줄이 다 빠지기 직전, 가장
흔한 정상 전이 — 에 팩토리가 예외를 던졌을 것이다.

**순서 주장이 2차 검토 전까지 미검증이었다.** "I3' 는 I4 뒤에 둔다" 를 코드 주석·
저널·커밋 본문 세 곳에 적어 놓고, 실제로 앞으로 옮겨 보니 295개가 전부 초록이었다.
강화한 두 단언이 서로의 알리바이가 됐기 때문이다 — I4 메시지는 `runtime=QUEUEING`
을 담아 `"QUEUEING"` 단언을 만족시키고, I3' 메시지는 `waiting=` 을 담아 `"waiting"`
단언을 만족시킨다. **하필 두 불변식이 공유하는 토큰을 골랐다.**

메시지에 `[I1]`·`[I3']` 같은 **불변식 ID** 를 박고 단언을 거기 묶었다. 산문이나
공유 토큰이 아니라 안정된 자리에 닻을 내린다. 이제 순서를 뒤집으면 죽는다.

**`waiting <= 0` 가드는 상태를 막지 않는다.** 지우고 실제로 불러 보니 I4 가 먼저
던진다. 가드가 바꾸는 것은 **메시지**다 — 부른 쪽에게 "off 를 써라" 를 그 자리에서
말해 준다. 2차 검토에서 잡혔다. 처음엔 주석에 "빈 줄에 ENQUEUE_BACKLOG 를 낸다"
고 적었는데 그런 일은 일어나지 않는다.

## 확신이 낮은 부분 · 남긴 위험

**안전한 기본값이 사라졌다.** 전에는 `waiting > 0` 이면 `QUEUEING` 으로 발행하는
것이 `credit` 과 무관하게 안전했다. 이제 `(credit, waiting)` 평면에 정답이 하나뿐
이라, 배분기가 두 값을 다른 시점에 재면 모순 조합이 나온다.

떨어지면 조용하다. 코덱은 그 쿠폰만 `null` 로 떨구고, `isAcceptable` 은 **전멸만**
막으므로 1000개 중 999개가 떨어져도 스냅샷이 수용된다. 코덱에 로거도 카운터도
없다. 관측 수단은 CY-306, 떨구지 말고 정규화할지는 CY-323 으로 뗐다.

떨어진 쿠폰이 판정에서 어떻게 보이는지는 **아직 코드가 없다.** `CouponState` 의
Javadoc 은 "미지 쿠폰은 요청 경로에서 404 로 끊는다" 고 적혀 있다. 어느 쪽이든
전면 차단이라 위험의 크기는 같지만, 요청 경로를 만들 때 확인해야 한다.

**재분류된 픽스처가 정상 경로에서 나오는 상태가 아니다.** `offWithQueue(500,
10_000, 100)` 은 credit 이 대기자의 5배다. 위에 적은 "배분 직후엔 항상
`credit <= waiting`" 과 I3 을 합치면 배분기가 발행할 수 있는 `DRAINING` 은
`credit == waiting` 한 점뿐이다. 이 픽스처는 **시점 어긋남 경로에서만** 나오는
조합이다 — 지금은 판정이 같아 해가 없지만, 저 위의 "남긴 위험" 과 같은 뿌리다.

**히스테리시스가 갈 자리가 없어졌다.** `I1' + I4 + I3'` 을 합치면 `waiting > 0 &&
stock > 0` 구간에서 `runtime` 은 `(credit, waiting)` 의 순수 함수다. `QueueingHysteresis`
의 래치 신호를 스냅샷에 실을 자리가 없다. I3' 만의 잘못은 아니지만 배분기 착수
직전에 신호를 하나 더 지웠으므로 결정이 필요하다 (CY-324).

## 다음 사람이 알아야 할 것

- **불변식 위반 메시지에 `[I3']` 같은 ID 가 붙어 있다.** 시험 단언이 거기 묶여
  있으니 형식을 바꾸면 시험이 깨진다. 산문을 고치는 것은 자유다.
- **`offWithQueue` 는 팩토리 중 유일하게 상태를 둘 만든다.** 경계를 고칠 일이
  있으면 생성자와 팩토리 **양쪽**을 같이 고쳐야 한다. 한쪽만 고치면 줄이 다
  빠지기 직전에 예외가 난다.
- **떼어 둔 결정 셋.** 코덱이 모순 레코드를 떨구지 말고 정규화할지(CY-323),
  드롭 관측 수단(CY-306), 히스테리시스 래치를 어디에 실을지(CY-324).
  셋 다 배분기(Phase 4) 착수 전에 답이 필요하다.
