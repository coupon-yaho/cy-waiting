## 2. F2 — 유실이 순서를 깨뜨린다

순번이 카운터가 아니라 시계이므로(A-9), 유실이 순서를 깨뜨리는 경로는 둘이다.

### 2.1 시계가 뒤로 가면 추월당한다 (치명)

score 를 `redis.call('TIME')` 에서 얻는데 이건 **벽시계다.** NTP 보정이나
복제본 승격으로 뒤로 갈 수 있다.

```
12:00:00.000000 에 A 등록   →  score = 1755...000000
NTP 가 시계를 300ms 되돌림
12:00:00.000000 에 B 등록   →  score ≤ A 의 score
                               B 가 A 앞에 선다
```

**불변식 4(줄 선 사람을 추월시키지 않는다)가 깨진다.** 복제본 승격이면 그 구간
전체가 한꺼번에 추월당한다.

**대응 — Lua 안에서 단조를 강제한다.**

```lua
local now  = redis.call('TIME')
local t    = now[1] * 1000000 + now[2]
local floor = tonumber(redis.call('GET', KEYS[2]) or 0)   -- maxscore:{cid}
if floor >= t then t = floor + 1 end
redis.call('ZADD', KEYS[1], t, ARGV[1])
redis.call('SET', KEYS[2], t, 'EX', 86400)
```

**바닥값은 `maxscore:{cid}` 하나면 된다.** ZSET 의 마지막 원소를 따로 읽을 필요가
없다 — Lua 는 효과 기반으로 원자 복제되므로 `ZADD` 와 `SET maxscore` 는 **같이
남거나 같이 사라진다.** `maxscore` 가 ZSET 보다 뒤처지는 상태가 존재하지 않는다.

큐가 빈 동안 시계가 되돌아가도 이 키가 남아 있으면 막힌다. 그게 이 키의 존재
이유고, ZSET 만으로는 안 되는 이유다.

**수명은 enqueue 마다 갱신되는 24시간이다.** 오픈 중에는 계속 밀려나므로 사라지지
않고, 끝난 쿠폰은 하루 뒤 자연 소멸한다. 쿠폰 일정을 몰라도 성립한다.

**승격 후 복원 절차는 없다.** 둘 다 유실됐다면 큐가 빈 것이고, 빈 큐에는 추월할
대상이 없다. ZSET 만 살아남는 경우가 없으므로(위 원자성) 별도 복원이 불필요하다.

### 2.2 ZSET 이 날아가면 대기자가 증발한다

`appendfsync everysec` 에서 `kill -9` 가 나면 최대 1초 분량의 등록이 사라진다.
그 사람들은 다음 폴링에서 `NOT_QUEUED` 를 받는다.

**허용한다.** 재등록하면 되고, 새 score 는 유실 구간보다 크므로 **이미 줄 선
사람을 추월하지 않는다.** `always` 의 쓰기 지연을 20,000 스파이크에서 치를 만한
이득이 아니다 (E-6).

`maxscore` 는 같은 Lua 안에서 갱신되므로 ZSET 과 함께 유실된다. 남은 대기자보다
작은 바닥값이 되는 상태는 생기지 않는다.

**검증**: 카오스 C12 (`kill -9` 후 복구) · **C13 (복제본 승격 + 시계 역행)** — G3.3

### 2.3 입장 임계의 경계값

| 상황 | 임계 |
|---|---|
| 아무도 입장 안 함 | `0` |
| N명 입장 | `ZRANGEBYSCORE queue (admitted +inf LIMIT N-1 1` 의 score |
| 큐에 N명이 안 됨 | **큐의 최대 score.** `+inf` 로 두지 않는다 |

**`+inf` 를 쓰면 안 된다.** 이후 도착하는 사람까지 임계 아래로 들어와 **줄을 서지
않고 통과**한다. 크레딧이 큐 크기보다 클 때는 지금 있는 사람 전원까지만 올린다.

### 2.4 운영 전제

| 항목 | 요구 |
|---|---|
| Redis 버전 | **7.x 이상.** Lua 의 `TIME` + 효과 기반 복제(5+), `ZRANDMEMBER`(6.2+) |
| 시계 동기화 | **slew 보정만.** step 보정(`makestep`)은 쓰지 않는다 |

시계가 크게 뒤로 가면 `maxscore` 가 순서는 지키지만 그 구간 전체가 `floor+1` 로
몰린다. 순서는 맞고 ETA 는 순위 기반이라 무사하지만, 애초에 그 상태를 만들지
않는 편이 낫다.

## 3. 키 스킴 — 샤딩까지 내다본 확정

```
S >  1:   queue:{cid:s}   maxscore:{cid:s}   admitted:{cid:s}   grace:{cid:s}   alive:{cid:s}:{member}
S == 1:   queue:{cid}     maxscore:{cid}     admitted:{cid}     grace:{cid}     alive:{cid}:{member}

전역:     gw:snapshot      gw:instances      scheduler:leader    gw:tunables
          coupons:active   coupon:policy     capacity:coupon-svc:{version}
쿠폰별:   stock:{cid}      (샤드 무관 — 발급 계층이 소유)

s = crc16(memberId) % S         ← 반드시 sticky (E-7)

queue      ZSET. score = Redis TIME 의 μs (A-9). seq 카운터는 없다
maxscore   시계 역행 방어용 바닥값 (2.1절)
admitted   입장 임계. 개수가 아니라 **score 값**이다 (D-8)
gw:tunables  운영자가 고치는 JSON. 리더가 읽어 스냅샷에 실어 퍼뜨린다 (P-1, Phase 6)
coupon:policy  JSON. `pcall(cjson.decode, …)` 로 읽고 실패는 기본값 (E-12)
```

> `gw:tunables` 와 `coupon:policy` 는 **사람 또는 다른 팀이 쓰는 유일한 키**다.
> 나머지는 게이트웨이가 소유한다. 밖에서 쓰는 키는 값이 깨져 들어올 수 있다고
> 가정하고 읽어야 한다 — 그래서 둘 다 파싱 실패 시 기본값 규칙이 붙어 있다.

### 3.1 S==1을 접미사 없는 형식으로 두는 이유

`{cid:0}`으로 통일하면 깔끔해 보이지만, **S를 1에서 올릴 때가 아니라 처음부터
샤딩 코드를 도입할 때** 콜드 쿠폰 전체의 키가 바뀐다. 제로베이스라 지금은 문제가
없지만, 운영 중 샤딩 도입은 불가능해진다. 접미사 없는 형식을 유지하면
**S=1인 쿠폰은 영원히 키가 안정적**이다.

부작용: S를 1에서 올리면 키 형식이 바뀌므로 **큐가 빈 상태에서만 가능**하다.
운영 규칙으로 못박는다 (→ Phase 10).

### 3.2 해시태그

쿠폰별 키는 모두 `{cid}` 또는 `{cid:s}` 태그를 포함한다. 같은 샤드의 키가 같은
슬롯에 모여야 하나의 Lua가 원자적으로 다룰 수 있다.

`stock:{cid}`은 발급 계층이 소유하며 샤드 무관이다. **Lua에서 접근하지 않는다** —
샤딩 시 슬롯이 갈리기 때문. 게이트웨이는 별도 `MGET`으로 읽는다.

## 4. Lua를 어디에 쓰는가

**원자성이 실제로 필요한 곳에만.** 클러스터에서 Lua는 KEYS에 선언되지 않은 키를
만질 수 없고, 서로 다른 슬롯의 키를 한 스크립트에 담을 수 없다.

| 스크립트 | 원자성이 필요한 이유 | 클러스터 호환 |
|---|---|---|
| `enqueue.lua` | 조회-후-등록을 나누면 새로고침 연타 시 항목 2개 등록. **시계 단조 가드도 여기서 원자적이어야 한다** (2.1절) | 단일 샤드 완결 ✓ |
| `queue_status.lua` | 유예 복원·하트비트·배수 판정이 원자적이어야 순번 역행 없음 | 단일 샤드 완결 ✓ |
| `leader_acquire.lua` | GET-후-SET 사이에 다른 노드가 잡을 수 있음 | 단일 키 ✓ |
| `sweep.lua` | 큐에서 제거와 grace 이동이 나뉘면 자리 유실 | 단일 샤드 완결 ✓ |
| ~~`collect_demand`~~ | **Lua 쓰지 않음** — 파이프라인 ZCARD로 | 슬롯 교차 불가 |
| ~~`apply_allocation`~~ | **Lua 쓰지 않음** — HSET + 샤드별 임계 SET | 슬롯 교차 불가 |

배분 반영의 원자성 상실이 잃는 것은 **정합성이 아니라 진단 편의**다
("크레딧은 늘었는데 배수는 안 된 중간 상태를 볼 수 있다"). 클러스터에서는
어차피 불가능하고 잃는 것도 그뿐이다.

## 7. 하지 않는 것

| 항목 | 이유 |
|---|---|
| 실제 샤딩 (S>1) 사용 | Phase 10. 키 스킴만 준비 |
| 스케줄러·스냅샷 루프 | Phase 4 |
| HTTP 계층 | Phase 5 |
| 전체 카오스 시나리오 | Phase 8. 여기서는 G3.3·G3.10 에 필요한 것만 |

> **여기서 만드는 것은 Redis 프로세스 조작뿐이다** — `kill -9` 후 재기동(3.3.5),
> 시계가 뒤처진 복제본 승격(3.3.6). 어댑터가 **순서 역행 0** 을 지키는지만 본다.
>
> Phase 8 의 `C12`·`C13` 은 같은 사건을 **진입·유지·회복 3단계로 판정**하고
> `RC1`~`RC6`(초과 발급 0 · 자리 유지 · 회복 버스트 ≤1.2배 …)을 얹는다.
> 게이트웨이 전체가 서 있어야 잴 수 있으므로 여기서는 불가능하다.
