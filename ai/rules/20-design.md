# 설계 규칙 (DS)

---

## 1. 계층

```
com.kafkick.waiting/          ← 루트는 조직 규칙 (PK-0)
├── domain/          순수. Spring·Redis·시계 없음. 판정·배분·폴링 규칙 전부
├── application/     오케스트레이션. 도메인을 호출하고 포트를 통해 밖과 이야기한다
├── adapter/
│   ├── redis/       Redis 접근. Lua, 키 스킴
│   ├── web/         필터, 핸들러, 라우트
│   └── metrics/     Micrometer
└── (각 계층의 *Config)  값이 필요한 빈과 프로퍼티 (DS-0)
```

**영속(entity·repository) 계층이 없다.** 재고를 차감하지 않으므로 필요 없다 —
`adapter/redis` 하나가 밖으로 나가는 유일한 통로다 (PK-0).

### DS-0 · MUST · 스스로 설 수 있는 것은 스스로 선다

빈을 설정에 손으로 박을지, 어노테이션으로 등록할지는 **셋 중 어디에 해당하는가**로
갈린다. 애매하면 설정에 두는 쪽이 아니라 이 표를 다시 본다.

| 어떻게 만들어지나 | 어디에 |
|---|---|
| 협력자만 주입받으면 선다 | **어노테이션** (`@Component`) |
| `domain` 패키지다 | 설정. 스프링을 참조할 수 없다 (DS-1) |
| 설정에서 온 값이 있어야 선다 | 설정 |
| 메서드 참조로 조립된다 | 설정. 어노테이션으로 옮기면 협력자를 통째로 문다 |

**팩토리의 검증을 잃지 않는다.** 생성 시점에 막는 것이 이 저장소가 지키는 것이라,
어노테이션 생성자도 그 검증을 지나가야 한다. 생성자가 둘이면 스프링이 못 고르므로
`@Autowired` 로 짚는다 (JS-4).

**이름이 쓰이는 빈은 이름을 못 박는다.** 헬스 그룹처럼 이름으로 지목하는 자리가
있으면 기본 이름에 맡기지 않는다 — 클래스 이름을 고치는 것만으로 조용히 빠진다.

### DS-1 · MUST · 도메인 순수성

`domain` 패키지는 아래를 **참조하지 않는다.**

| 금지 | 대신 |
|---|---|
| `org.springframework.*` | POJO. 배선은 `config`에서 |
| `org.springframework.data.redis.*` | 포트 인터페이스를 도메인이 정의 |
| `reactor.core.*` | 순수 함수는 `Mono`를 반환하지 않는다 |
| `Instant.now()`, `System.currentTimeMillis()` | `Clock` 주입 |
| `Math.random()`, `ThreadLocalRandom` 직접 호출 | 난수원 주입 |

ArchUnit이 검사하고 훅이 차단한다.

**왜 이렇게까지 하는가**: 이 계층의 오류가 곧 크레딧 초과 배분과 공정성 붕괴다.
순수해야 브랜치 100%와 뮤테이션 테스트가 가능하고, 그래야 그 두 가지를 보장할 수 있다.
순수성은 한 번 깨지면 조용히 번진다 — `import` 하나가 들어오는 순간
테스트 전략 전체가 무너진다.

### DS-2 · MUST · 도달 불가 상태를 만들 수 없게 한다

public 생성자가 불변식을 어긴 값을 만들 수 있으면 안 된다.
팩토리 메서드만 노출하고 컴팩트 생성자에서 검증한다.

```java
// 금지 — (IDLE, credit=1000)이라는 존재할 수 없는 상태를 만들 수 있다
public CouponState(QueueMode mode, RuntimeState runtime, int credit, ...)

// 올바름
public static CouponState idle(long stock)
public static CouponState queueing(int credit, long stock, long waiting)
public static CouponState closed(long waiting)
```

> 이전 구현에서 R1 버그가 3개월 살아남은 유일한 원인이 자유형 생성자였다.
> 테스트가 불가능한 상태를 픽스처로 만들어 버그를 덮었다.

## 2. DDD — 이 도메인에 실제로 맞는 만큼만

용어를 억지로 끼워 맞추지 않는다. 이 시스템에서 **실제로 성립하는 것**만 쓴다.

### 2.1 바운디드 컨텍스트

| 컨텍스트 | 소유하는 것 | 이 프로젝트의 위치 |
|---|---|---|
| **입장 관리** (게이트웨이) | 대기열, 순번, 입장 토큰, 크레딧 배분 | 여기 |
| **쿠폰 발급** (쿠폰 서비스) | 쿠폰, **재고**, 발급 이력 | 뒷단 |

**게이트웨이는 재고를 소유하지 않는다.** 읽기 전용 투영(projection)으로 다룬다.

이 구분이 실무에서 갖는 의미:

- 게이트웨이는 재고를 **차감하지 않는다.** 원자 차감은 발급 컨텍스트의 책임
- 그럼에도 게이트웨이가 "매진"을 종결할 수 있는 이유는 **오판이 안전한 방향뿐이고
  스냅샷이 되돌리기** 때문이다 (B-11). 재입고는 상시 발생한다.
  단조 감소하는 투영은 한 방향으로만 안전하게 낡을 수 있다
- 재입고(취소·환불)가 상시화되면 이 전제가 약해진다 → `plan/90-decisions.md` 재검토 트리거

### 2.2 애그리거트

| 애그리거트 | 루트 | 불변식 | 트랜잭션 경계 |
|---|---|---|---|
| **대기열** | `queue:{couponId[:shard]}` | 한 회원은 자리 하나<br>score 는 단조 증가 (시계가 뒤로 가도)<br>`admitted` 임계는 단조 증가 | **Lua 스크립트 1회** |

이 매핑이 이 프로젝트에서 가장 중요한 DDD 적용이다:

```
애그리거트 경계  =  Redis 해시태그 {couponId:shard}  =  하나의 슬롯  =  Lua의 원자 실행 범위
```

**애그리거트 하나를 넘는 원자성은 시도하지 않는다.** 그래서:

- `enqueue`, `queue_status`, `sweep`은 Lua다 (한 애그리거트 안에서 완결)
- 수요 수집·배분 반영은 Lua가 **아니다** (여러 애그리거트에 걸침 → 최종 일관성)
- 샤딩은 애그리거트를 쪼개는 일이다. 그래서 회원→샤드 매핑이 **sticky**여야 한다

### 2.3 애그리거트가 **아닌** 것

억지로 부르지 않는다.

| 타입 | 실제 성격 |
|---|---|
| `CouponState` | **값 객체**. 식별자 없음, 생명주기 없음, 매 틱 통째로 교체 |
| `GatewaySnapshot` | **읽기 모델**. 판정용 투영 |
| `FairShareAllocator` | **도메인 서비스**. 상태 없는 계산 |
| `AdmissionDecider` | **도메인 서비스** (정책) |
| `InstanceCapacity` | 다른 컨텍스트가 보낸 **메시지** |

### 2.4 유비쿼터스 언어

코드·문서·대화에서 같은 단어를 쓴다. 번역하지 않는다.

| 용어 | 뜻 | 아닌 것 |
|---|---|---|
| **credit** | 이번 1초에 추가로 받아 줄 수 있는 **인원** | 재고가 아니다 |
| **stock** | 남은 쿠폰 수량 | credit을 만들지 않고 **깎기만** 한다 |
| **admit** | 이번 틱에 배수할 인원 | 발급 확정이 아니다 |
| **입장(admission)** | 큐를 통과해 발급을 **시도**할 자격 | 발급 성공 보장이 아니다 |
| **waiting** | 큐에 있는 인원 | 유령 포함 가능 (sweeper 참조) |

## 3. SOLID — 구체적으로 어디에

원칙 나열이 아니라 **이 프로젝트의 어느 지점**에 적용되는지.

### DS-3 · SRP — 판정과 응답을 분리한다

`AdmissionDecider`는 **판정만** 한다. HTTP 응답 작성, 메트릭 기록, 큐 등록은
호출부의 일이다.

```
AdmissionDecider   →  AdmissionDecision (enum)      순수, 테스트 쉬움
AdmissionFilter    →  판정을 받아 응답으로 번역      WebFlux 의존
```

이렇게 나눠야 판정 분기 전수를 컨텍스트 없이 검증할 수 있다.

### DS-4 · OCP — 판정 단계 추가가 기존 분기를 건드리지 않게

판정은 **순서 있는 규칙 목록**이다. 새 규칙(예: 서킷 오픈 처리)을 넣을 때
기존 `if` 사슬을 뜯지 않도록 규칙을 값으로 표현한다.

**단, 규칙이 3개 이하일 때는 `if` 사슬이 더 낫다.** 추상화는 두 번째 사례가
나타났을 때 도입한다 (4절 참조).

### DS-5 · ISP — 필요한 것만 노출한다

`SnapshotHolder`가 데이터 플레인에 주는 것은 `stateOf(couponId)`와 메타뿐이다.
갱신 메서드(`replace`)는 컨트롤 플레인만 쓴다. 인터페이스를 나눠서
**데이터 플레인이 스냅샷을 바꿀 수 없게** 한다.

### DS-6 · DIP — 포트는 도메인이 정의한다

```java
// domain — 도메인이 필요를 선언한다
public interface QueueRepository {
    Ticket enqueue(long couponId, MemberId member, Duration aliveTtl);
}

// adapter/redis — 인프라가 구현한다
class RedisQueueRepository implements QueueRepository { ... }
```

방향이 반대가 되면(도메인이 Redis 타입을 참조하면) DS-1이 깨진다.

## 4. 디자인 패턴 — 두 번째 사례가 나올 때 도입한다

**패턴을 위한 패턴을 금지한다.** 사례가 하나뿐인데 전략 인터페이스를 만들면
간접 참조만 늘고 읽기가 어려워진다. 아래는 **이 프로젝트에서 실제로 두 번째
사례가 예정된** 지점들이다.

| 패턴 | 적용 지점 | 두 번째 사례 |
|---|---|---|
| **전략** | 로드밸런싱 정책 | P2C → peak-EWMA 격상 (Phase 9 G8.1 미달 시) |
| **전략** | `ShardSplitter` | 단일 샤드 → 인원 비례 분할 (Phase 10) |
| **전략** | 폴링 간격 정책 | 밴드 기반 → 예산 기반 |
| **책임 연쇄** | 판정 파이프라인 | 규칙이 10개를 넘으면 |
| **파사드** | `QueueService` | Lua 스크립트 묶음을 한 인터페이스 뒤로 |
| **팩토리** | `CouponState` 팩토리 메서드 | 상태 종류마다 (DS-2) |
| **팩토리** | `CouponStates` 테스트 픽스처 | 동 |
| **어댑터/포트** | Redis 접근 | DS-6 |
| **템플릿 메서드** | 카오스 3단계 판정 | 12개 시나리오가 같은 뼈대 |
| **널 오브젝트** | `CouponState.unknown()` | 스냅샷에 없는 쿠폰 |

### 쓰지 않는 것

| 패턴 | 이유 |
|---|---|
| **옵서버 / pub-sub** | at-most-once. 재연결 노드가 놓친 것을 모른다. 폴링을 쓴다 |
| **싱글턴 (수동 구현)** | Spring 빈이 이미 한다 |
| **DI 프레임워크 밖의 서비스 로케이터** | 의존이 숨는다 |

### DS-7 · SHOULD · 패턴 도입 시 근거를 남긴다

패턴을 도입하는 커밋은 journal에 **"어떤 두 번째 사례 때문인가"**를 적는다.
그것이 없으면 도입하지 않는다.

## 5. 확장 지점을 미리 만들지 않는다

"나중에 필요할 것 같아서" 인터페이스를 뚫지 않는다.
대신 **바꾸기 쉬운 구조**로 둔다 — 순수 함수, 작은 클래스, 명확한 경계.

예외: `plan/`에 **명시적으로 예정된** 확장(위 표의 "두 번째 사례")은
그 페이즈에서 도입한다. 계획에 없는 확장은 만들지 않는다.

## 6. 잘 만들어진 라이브러리를 먼저 본다

**DS-8 · MUST · 직접 만들기 전에 라이브러리부터 찾는다**

리트라이·서킷·격벽·타임아웃·리미터·재시도 백오프처럼 **이미 잘 풀린 문제**를
다시 구현하지 않는다. 우리가 쓴 것은 우리가 고쳐야 하고, 그 시간은 이 제품이
실제로 어려운 곳(공정성·정합성)에 쓰여야 한다.

**논블로킹이 전제다.** 이 게이트웨이는 WebFlux 위에 서 있으므로 고르는 기준에
**리액티브 지원**이 먼저 온다. 블로킹 API 하나가 이벤트 루프를 잡으면 전체
처리량이 무너진다 — 편의 하나 얻자고 그걸 치르지 않는다 (RX-1).

| 필요 | 먼저 볼 것 |
|---|---|
| 서킷·격벽·타임아웃·리트라이 | `resilience4j` (+ `resilience4j-reactor`) |
| 지표 | Micrometer |
| 컨테이너 기반 시험 | Testcontainers |
| 리액티브 조합·백프레셔 | Reactor 연산자. 직접 스레드를 만들지 않는다 |

**직접 만들려면 근거를 journal 에 남긴다.** 아래 셋 중 하나에 해당하고, 그
사실이 기록돼 있어야 한다.

1. **의미가 다르다** — 라이브러리가 못 하는 계약이 필요하다
2. **순수성을 깬다** — 도메인에 프레임워크·시계가 들어온다 (DS-1)
3. **버전이 안 맞는다** — 지원하는 런타임 버전이 우리와 다르다

> **버전은 실측해서 고른다.** 문서나 기억에 있는 버전을 적지 않는다 —
> Maven Central 을 조회해 그 시점의 최신을 확인하고, 우리 런타임과 맞는지까지
> 본다. Boot 4 처럼 새 버전에서는 **스타터가 아직 없어 코어 모듈만 쓸 수도** 있다.

### 실제 사례 — `SecondWindowLimiter`

`resilience4j-ratelimiter` 가 있는데 직접 만들었다. 위 1·2 둘 다에 해당한다.

- **두 예산을 전부-아니면-전무로** 차감해야 하는데 라이브러리에 그 계약이 없다.
  나눠 치면 통과하지 않은 요청이 예산을 깎고, 그 유실은 부하 시험 전까지 안
  보인다 (G2.12)
- **상한이 매 틱·쿠폰마다 바뀐다.** 인스턴스 설정이 아니라 **호출 인자**여야 한다
- **시각을 주입받아야 한다.** 라이브러리는 내부 시계를 쓰는데 그러면 초 경계
  동작을 시험할 수 없다 (DS-1 · TS-4)
