# 통째로 끄려다 아무것도 못 고칠 뻔했다

## 증상

의존성 갱신 봇이 연 PR 아홉 개가 전부 같은 자리에서 죽었다.

```
브랜치명이 규칙에 맞지 않는다: 'dependabot/github_actions/actions/checkout-7.0.1'
```

브랜치명에 티켓 번호를 요구하는 규칙은 사람이 지킬 규칙이다. 봇은 그 형식으로
브랜치를 안 만들고, 만들 수도 없다.

## 처음 한 것 — 그리고 왜 틀렸나

봇 PR 은 워크플로를 통째로 건너뛰게 했다. 리뷰가 세 가지를 짚었다.

**목표를 달성하지도 못한다.** 필수 체크 중 재사용 워크플로 안에 있는 것은
건너뛰면 그 이름으로 보고를 안 한다. 빨강 아홉이 **영구 대기 셋**으로 바뀔 뿐
병합은 여전히 막힌다.

**가장 필요한 검사를 껐다.** 의존성 검토는 의존성이 바뀌는 PR 을 보라고 있는
것인데, 정확히 그 PR 에서 꺼진다. 시크릿·취약점 스캔도 같이 나갔다.

**뒷받침한다고 적은 것이 사실이 아니었다.** "병합 뒤 main·nightly 가 잡는다" 고
썼는데, 봇은 기본 브랜치를 대상으로 PR 을 연다 — develop 을 거치지 않는다.
검증 없이 릴리스 브랜치로 바로 들어간다는 뜻이었다.

## 다시 한 것

**면제는 봇이 만들 수 없는 형식 셋만.** 브랜치명, 커밋 제목, 작업 로그.
빌드·테스트·시크릿·취약점·의존성 검토는 그대로 돈다.

저장소에 이미 그 패턴이 있었다 — 작업 로그 검사가 `[bot]` 접미사로 면제하고
있었다. 새 기준을 만들 이유가 없었고, 만들었으면 둘이 갈라졌을 것이다.

## 판정 게이트가 공허하게 통과했다

통째로 건너뛰면 집계 판정도 건너뛰는데, **건너뛴 잡은 성공으로 보고된다.**
파이프라인 전체가 그 하나로 수렴하게 만들어 뒀는데 그게 아무것도 안 보고
초록이 되는 상태였다.

## 규칙이 세 곳에 있었다

되돌리기 커밋이 규약에 걸리면서 드러났다.

git 훅에는 병합·되돌리기 예외가 있는데 **공유 라이브러리에는 없었다.** 그래서
도구 훅으로 커밋하면 걸리고 터미널로 커밋하면 안 걸렸다. 라이브러리 머리말이
"규칙을 양쪽에 복사하지 않는다" 고 적어 뒀는데 그 예외만 복사돼 있었다.

CI 는 더 나빴다 — **규칙 전체를 사본으로 갖고 있었다.** 제목 형식, 길이, 마침표,
종결어미, 한글 여부까지 전부 다시 적혀 있었다. 예외 하나를 맞추는 것으로는
같은 일이 또 난다.

라이브러리를 실제로 부르게 했다. CI 에 남는 것은 그쪽에서만 알 수 있는 둘뿐이다 —
부모 수로 병합을 가리는 것과 본문의 마커 검사.

**푸터 검사도 예외를 안 받고 있었다.** 제목은 통과시키고 푸터에서 막으니
되돌리기가 여전히 죽었다. 판단 함수 하나를 두고 둘이 같이 쓴다.

## 어떻게 검증했는가

| 확인한 것 | 결과 |
|---|---|
| 봇·사람 구분값 | 봇 `[bot]` 접미사, 사람은 없음 — 실측 |
| 빈 Jira 키를 쓰는 곳 | 리포트가 이미 빈 값을 건너뛴다 |
| YAML 유효성 | 두 파일 다 통과 |
| CI 로직을 실제 커밋으로 | 이 브랜치와 develop 최근 40개 전부 통과 |
| 도구 제목 예외 제거 | 판정 실패 |
| 제목 길이를 5칸으로 | 판정 실패 |

## 남은 것

**필수 체크 목록을 안 건드렸다.** 재사용 워크플로 안의 셋은 봇 PR 에서 이제
정상으로 돈다. 다만 그 이름으로 보고하는 구조 자체가 취약해서, 나중에 누가
그것들을 건너뛰게 만들면 검증 없는 병합 경로가 생긴다.

**코드 소유자 규칙이 비어 있다.** 필수 체크가 유일한 병합 관문이다.
