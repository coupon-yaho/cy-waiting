# Phase 8 — Resilience

> **이 계획의 무게중심.** 장애 중 동작만이 아니라 **회복 전이**를 검증한다.
> 장애 대응으로 바뀐 상태가 장애가 걷힌 뒤 원래대로 돌아오는지, 돌아오는
> 과정에서 2차 장애를 만들지 않는지가 판정 대상이다.
>
> **Phase 9·10 보다 앞선다.** 회복력이 검증되지 않은 시스템을 확장하면
> 장애 반경만 커진다.

**선행**: Phase 7 (닫힘) · **상세 수준**: **완전 명세** (CY-785 에서 승격)

---

## Goal

> **장애가 걷힌 뒤 스스로 정상으로 돌아온다 (R5).**
> 그리고 돌아오는 과정이 2차 장애를 만들지 않는다.

| 통과 수치 | |
|---|---|
| 카오스 시나리오 (21 단일 + 4 조합) | **전부 3단계 판정 통과** |
| 초과 발급 (전 시나리오·전 구간 합산) | **0건** — 타협 불가 |
| 순번 역행 (전 시나리오) | **0건** — 타협 불가 |
| 회복 순간 백엔드 유입 버스트 | **≤ 정상 1.2배** (RC4) |
| 회복 후 정상 지표 복귀 | **≤ 30초** (RC3) |
| 서킷 half-open 회복 시도 | **≤ 2회** (F3) |

**이 게이트가 프로덕션 배포의 실질적 승인선이다.**
Phase 9·10 은 이걸 통과한 뒤에만 시작한다 — 회복력이 검증되지 않은 시스템을
확장하면 장애 반경만 커진다.

---

## 2. 회복이 왜 별도 판정을 받아야 하는가

장애 대응은 시스템을 **다른 모드로 전환**한다. fail-open 상한, 낡은 스냅샷,
줄어든 노드 분모, 열린 서킷, 정지한 배분. 이 전환들은 각각 정상 모드로
되돌아와야 하는데, 되돌아오는 순간이 가장 위험하다.

| 회복 시 위험 | 원인 |
|---|---|
| **억눌린 트래픽 방출** | 장애 중 큐에 쌓인 사람 + 재시도가 동시에 |
| **상한 이중 개방** | 두 경로의 카운터가 같은 초에 모두 열림 (F4) |
| **분모 급변** | 노드가 한꺼번에 복귀해 각자 몫이 급변 (F5) |
| **콜드 인스턴스 과부하** | 재기동 인스턴스가 여유를 과대 보고 (F6) |
| **상태 리셋으로 인한 진동** | EWMA·히스테리시스가 초기화 (F9) |
| **동기화된 재시도** | 고정 `Retry-After` (F7) |
| **서킷 half-open 실패 반복** | 시험 요청 시점에 트래픽 전량 도달 (F3) |

전부 "장애는 견뎠는데 복구에서 무너지는" 형태다. 유지 구간만 보는 테스트는
하나도 잡지 못한다.

## 3. F3 — 서킷 상태가 판정에 반영되지 않으면 회복이 안 된다

서킷브레이커가 열려도 게이트웨이의 판정은 이를 모른다. 계속 `PASS` 판정을 내려
요청을 라우팅하려 하고, 서킷이 가로채 fallback으로 보낸다.

무엇이 일어나는가:

```
백엔드 열화 → 서킷 오픈
  → 게이트웨이는 여전히 통과 판정 → 전량이 fallback으로 (503)
  → half-open 전환 시점
  → 시험 요청이 아니라 "그 순간 도착한 모든 트래픽"이 백엔드로
  → 약한 백엔드가 즉시 재포화 → 서킷 재오픈
  → 회복이 지연되거나 영원히 안 됨
```

**결정**: 서킷 상태를 판정의 입력으로 삼는다.

| 서킷 상태 | 판정 처리 |
|---|---|
| CLOSED | 정상 |
| **OPEN** | 해당 라우트의 유효 credit을 **0으로 간주** → 신규 유입은 큐로 |
| **HALF_OPEN** | 유효 credit을 **소량**으로 제한 → 시험 트래픽만 통과 |

효과:

- 서킷이 열리면 트래픽이 fallback이 아니라 **큐**로 간다 — 사용자는 503 대신
  순번을 받고, 백엔드는 완전히 쉰다
- half-open 시점에 소량만 도달하므로 **회복 판정이 공정해진다**
- 회복 후 credit이 정상으로 돌아오면 큐가 자연히 배수된다

구현: resilience4j의 `CircuitBreakerRegistry`에서 상태를 읽어 `AdmissionDecider`에
전달한다. 로컬 조회이므로 Redis 왕복 0 원칙을 지킨다.

## 4. 회복 판정 공통 기준 (RC)

전 시나리오에 적용된다. 시나리오별 기준은 이것에 **추가**된다.

| ID | 기준 | 측정 방법 |
|---|---|---|
| **RC1** | 초과 발급 **0건** — 장애 전·중·후 전 구간 합산 | 발급 수 vs 재고 |
| **RC2** | 순번 역행 **0건** | 폴링 응답 시퀀스 전수 검사 |
| **RC3** | 회복 후 **30초 내** 판정 분포가 정상 범위로 복귀 | `waiting.admission.decision` |
| **RC4** | 회복 순간 백엔드 유입 버스트 **≤ 정상 1.2배** | 백엔드 스텁 수신 RPS |
| **RC5** | 장애 중 큐에 있던 사용자가 **자기 자리 유지** | 사용자별 score 추적 |
| **RC6** | 지표·내부 상태가 장애 이전 값으로 수렴 | EWMA·히스테리시스·노드 분모 |

**RC4가 가장 중요하다.** 나머지가 전부 통과해도 RC4가 깨지면 회복이 곧 2차 장애다.

## 5. 카오스 시나리오

각 시나리오는 **진입 → 유지 → 회복** 3단계로 판정한다.
회복 단계는 위 RC1~RC6에 시나리오별 기준을 더한다.

### C1 — Redis 완전 정지 → 복구

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 스냅샷 유지(지우지 않음), 큐 등록 실패 → fail-open 상한 | 전면 차단 0, 무제한 통과 0 |
| 유지 | 상한 안에서 통과. **어떤 노드도 빠지지 않는다** | 통과량 ≤ 상한, 갱신 루프 정지 0, 503 유출 0, `dataStale` 진입 |
| 회복 | 스냅샷 즉시 재적재, 큐 순번 전원 유지 | RC1~RC6 + 첫 스냅샷까지 5초 이내 |

> **fail-open이 큐를 추월하지 않는지**(F1)를 여기서 함께 본다.
> Redis가 죽으면 큐 등록 자체가 불가하므로 F1의 3번째 규칙(그때만 fail-open)이
> 적용되는 유일한 시나리오다.

### C2 — Redis 지연 주입 500ms → 해제

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 스냅샷 타임아웃 발생, 판정은 로컬이라 영향 없음 | 판정 p99 변화 없음 |
| 유지 | 폴링 응답 지연, 갱신 루프는 계속 돎 | 갱신 루프 정지 0 |
| 회복 | 지연 해제 후 정상 주기 복귀 | RC1~RC6 |

> **판정 경로가 Redis를 안 치므로 발급 지연이 변하지 않아야 한다.**
> 변한다면 어딘가에서 Redis를 치고 있다는 뜻이다 — G5.1의 실전 검증이다.

### C3 — Redis 클러스터 노드 failover

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | MOVED/ASK 리다이렉트 처리, 해당 슬롯만 일시 실패 | 다른 샤드 영향 0 |
| 유지 | 복제본 승격 대기 중 그 샤드만 fail-open | 영향 범위가 샤드에 국한 |
| 회복 | 토폴로지 갱신 후 정상 | RC1~RC6 + 승격된 복제본에서 순서 역행 0 (C13) |

> Phase 10 이후에만 실행 가능. 그 전에는 단일 노드이므로 C1으로 대체한다.

### C4 — 배분 리더 강제 종료 → 승계

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | `admitted` 임계 정지, 게이트웨이는 `dataStale` 전까지 정상 판정 | 판정 중단 0 |
| 유지 | `dataStale` 진입 → fail-open. **큐가 있으면 추월 금지**(F1) | 추월 0 |
| 회복 | 3틱 내 새 리더 승계, EWMA·히스테리시스 이월(F9) | RC1~RC6 + 승계 ≤ 3틱, 진동 0 |

### C5 — 리더 네트워크 분단 (스플릿 브레인) → 복구

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 구 리더가 락 만료를 모른 채 한 틱 더 수행 가능 | — |
| 유지 | 크레딧 최대 2배 발행. **재고 초과 발급은 0** | 초과 발급 0 (발급 계층 원자 차감) |
| 회복 | 분단 해소 후 구 리더가 락 상실을 인지하고 물러남 | RC1~RC6 + 틱 번호 역행 감지 |

> 펜싱 토큰을 쓰지 않는 근거의 실전 검증이다. **여기서 초과 발급이 1건이라도
> 나오면 근거가 무너진 것이므로 펜싱을 도입해야 한다.**

### C6 — 게이트웨이 노드 1대 종료 → 복귀

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 헬스체크 503 → LB 제외. 즉시 등록 해제 | 5xx 유출 0 |
| 유지 | 남은 노드가 큰 분모를 써서 과소 통과 (안전 방향) | 초과 0 |
| 회복 | 복귀 노드가 하트비트 → **분모 즉시 반영**(F5) | RC1~RC6 + 총 통과 ≤ globalCredit + **복귀 노드의 유입 비율 오차 ≤ ±15%** (G9.12) |

> F5의 비대칭 반영을 검증하는 시나리오. 분모 반영이 늦으면 여기서 초과가 나온다.
> **복귀 노드의 라우팅 품질도 같이 본다** — 로컬 관측이 0 이라 열화 인스턴스를
> 구별하지 못하는 구간이 여기서 드러난다 ([09-routing.md](09-routing.md#cold-start)).

### C7 — 백엔드 인스턴스 1대 종료 → 콜드 복귀

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 그 인스턴스 보고가 낡아 합산에서 제외 → globalCredit 감소 | 유입이 즉시 조정 |
| 유지 | 남은 인스턴스 여유에 맞춰 배분 | 남은 인스턴스 포화 0 |
| 회복 | **콜드 인스턴스가 램프업**(F6) | RC1~RC6 + 복귀 직후 그 인스턴스 유입이 램프 곡선을 따름 (`startedAt` 전에는 2차, 후에는 선형 — A-13) |

### C8 — 백엔드 전체 지연 → 서킷 오픈 → half-open 복구

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 서킷 오픈 → **유효 credit 0 → 신규 유입은 큐로**(F3) | 503 유출 최소, 큐 등록 정상 |
| 유지 | 백엔드 유입 ≈ 0. 대기자는 순번 유지 | 백엔드 부하 0 |
| 회복 | half-open에서 **소량만 통과** → 성공 시 CLOSED | RC1~RC6 + half-open 실패 반복 0, 회복 시도 ≤ 2회 |

> F3 미적용 시 half-open이 반복 실패하는 것을 **먼저 테스트로 확인**한 뒤
> 대응을 구현한다 (카오스도 TDD, [`ai/rules/40-testing.md`](../ai/rules/40-testing.md) TS-8).

### C9 — DB 커넥션 끊기 (PRD 필수 시나리오)

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 백엔드 5xx → 서킷 오픈 (C8과 동일 경로) | |
| 유지 | 대기열 순번이 Redis에 남아 유지됨 | 순번 유실 0 |
| 회복 | DB 복구 후 5초 내 정상화, 정합성 무손상 | RC1~RC6 + 초과 발급 0 |

### C10 — 게이트웨이 STW 정지 3초

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 그 노드의 갱신 루프·하트비트 정지 | |
| 유지 | 다른 노드가 그 노드를 죽은 것으로 셀 수 있음 | 분모 변화가 초과를 만들지 않음 |
| 회복 | 깨어난 노드가 낡은 스냅샷으로 한 번 판정할 수 있음 | RC1~RC6 + 낡은 판정이 상한을 넘지 않음 |

> 리더가 STW를 겪으면 C5로 이어진다. 두 시나리오를 조합해서도 실행한다.

### C16 — 가용량 읽기만 느리다

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 가용량 읽기만 예산(틱의 1/4)을 넘긴다. 수요·발행은 성공 | 유예 안에서는 크레딧이 직전 값 그대로 |
| 유지 | 유예 뒤로는 줄되 바닥이 노드를 받친다 | 노드당 몫 ≥ 유휴 역수 (R1) · 뒷단이 보고한 0 은 안 올라간다 |
| 회복 | 첫 성공 판에 실측으로 복귀 | 유예가 다시 차서 바로 다음 실패에 안 깎인다 |

> **감쇠가 실제로 도는 구간은 여기뿐이다.** 레디스가 통째로 죽으면 수요 읽기도
> 같이 죽어 판이 통째로 실패하고, 감쇠값이 배분에 닿지도 않는다. 읽기 예산이
> 틱의 1/4 이라 이 부분 장애가 가장 흔한 형태다.

### C18 — 뒷단 무응답 (TCP 는 받고 헤더를 안 보냄)

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 뒷단이 붙기는 하는데 응답을 안 보낸다 | 격벽 누수 0 · 서킷 창에 표본 > 0 · 상한 도달 후 서킷 OPEN |
| 유지 | OPEN 이면 유효 크레딧 0 으로 신규 유입을 큐로 (F3) | 뒷단 유입 ≈ 0 · `BACKEND_UNAVAILABLE` · 차례가 온 사람의 `Retry-After` 는 가까운 밴드 |
| 회복 | 뒷단 재기동. half-open 프로브가 설정한 수를 안 넘는다 | 실제 프로브 ≤ 설정값 · 회복 시도 ≤ 2회 (G8.12) · RC1~RC6 |

> **C8 은 지연, C9 는 5xx 를 전제한다.** 응답 자체가 안 오는 구간은 그 둘 사이로
> 빠지는데, 스레드풀이 마르거나 DB 커넥션이 끊기면 뒷단은 5xx 를 내는 것이 아니라
> **아무것도 안 낸다.** 그래서 C9 는 지금 존재하지 않는 진입 조건을 판정하고 있다.

> **끊는 자리가 서킷 안팎 중 어디인지가 이 시나리오의 핵심이다.** 밖에서 끊으면
> 서킷이 받는 것은 오류가 아니라 취소이고, 취소는 창에 안 쌓인다 — 표본이 0 이라
> 서킷이 영원히 안 열리고, 그동안 게이트웨이는 죽은 뒷단에 계속 밀어 넣는다.
> 초록불은 그대로다. 이 시나리오만이 그것을 잡는다.

> **회복 단계의 RC4 를 꼭 넣는다.** 재기동으로 회복하면 물려 있던 커넥션이 한
> 순간에 끊기고 격벽 자리가 같은 초에 통째로 풀린다. 초당 리미터가 잡아 준다는
> 가정이 실제로 성립하는지는 여기서만 확인된다.

### C17 — 시계 역행과 유령 인스턴스

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 승격한 복제본의 시각이 뒤로 간다 | 단조 가드가 걸린 횟수 > 0 · 역행 폭이 지표에 남는다 |
| 유지 | 보정한 시각으로 걷어 크레딧이 유지된다 | 승격 전 값과 같다. 보정 없으면 하한이다 |
| 회복 | 시계가 따라잡으면 바닥값을 놓는다 | 실측을 다시 따라간다 |
| 유령 | 시계가 앞선 뒷단이 죽는다 | 마지막 보고가 신선도 창 + 허용치까지만 세어진다 |

> **유령이 회복 첫 구간에 겹친다.** 죽은 인스턴스가 새 식별자로 돌아오면 그
> 몫이 콜드 램프값과 함께 실린다 — 뒷단이 가장 차가울 때 유입이 가장 높다
> (F6·RC4). 그래서 앞섬 허용치를 신선도 창과 따로 둔다.

> 조용히 fail-open 한다. `G4.1` 이 "정확히 1대" 라 0대를 이미 배제하므로, 이
> 시나리오는 그 게이트를 **지연 구간에서도** 재는 것이 목적이다.

### C19 — 전역 폴링 배수 하강 ★

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 큰 쿠폰 A 와 작은 쿠폰 B 를 함께 띄워 배수를 5 이상으로 올린다 | `waiting.poll.budget.overshoot.ticks` 가 오른다 |
| 유지 | 60초. B 의 대기자가 밴드×배수 간격을 받는다 | 실측 폴링 ≤ 노드당 예산 · RC5 |
| 회복 | A 의 재고를 0 으로 만들어 **한 틱에** 배수를 1.0 으로 떨군다 | **RC4 (≤1.2배)** · RC1 · RC3(아래 참조) |

> **배수에는 평활도 히스테리시스도 없다.** 매 틱 처음부터 다시 계산되고, 쿠폰
> 하나가 매진되는 한 틱에 20 에서 1.0 으로 떨어진다. 그동안 입장 토큰은 폴링해야
> 받으므로(지연 발급) 배수만큼 미청구 입장자가 쌓여 있고, 배수가 풀리는 순간
> 그것이 평시 유입에 얹혀 나간다 — **RC4 를 직접 겨눈다.**
>
> `CreditSmoother`·`QueueingHysteresis`·가용량 램프업이 다 붙어 있는 판에서
> 배수만 맨몸이다. 하강에만 램프를 걸면 적체가 서서히 풀린다 (CY-731).
>
> **RC3 의 기산점은 배수 하강이 아니라 하강 뒤 첫 폴링이다.** 발급 경로에
> 트래픽을 넣는 것은 폴링해서 차례를 확인한 사람인데, 배수가 걸린 동안 그들이
> 받은 간격이 40~60초다. 하강한 틱부터 30초를 재면 아직 아무도 안 돌아왔으므로
> 어떤 구현으로도 못 넘긴다 — 없는 결함을 찾게 되거나 기준을 임의로 낮추게 된다.
> **한 폴링 주기(≤60초) 안에 복귀**로 읽는다.

### 6.1 서킷 상태 연동 (F3)

**이 페이즈에서 유일하게 새로 만드는 동작이다.** 나머지는 이미 있는 것을
장애 구간에서 재는 일이다.

#### T8.1.1 · 서킷 상태를 판정의 입력으로

- **산출물** `domain/admission/CircuitState.java`, `AdmissionRequest` 의 새 자리
- **근거** 3절. 서킷이 열려도 판정이 모르면 전량이 fallback 으로 가 사용자는
  503 을 받고, half-open 순간 **그때 도착한 모든 트래픽**이 약한 뒷단에 꽂혀
  재포화한다 — 회복이 영영 안 된다
- **선행** 없음

**도메인이 resilience4j 를 모르게 한다.** 열거값 셋(`CLOSED`·`OPEN`·`HALF_OPEN`)만
받는다. 라이브러리 타입을 도메인에 들이면 그날 도메인이 그 라이브러리에 묶인다.

1. **RED** `서킷이_열리면_유효_크레딧이_0이다`
2. **GREEN** `AdmissionRequest.circuit()` 을 판정 사다리가 읽는다
3. **RED** `반쯤_열리면_소량만_통과한다`
4. **GREEN** half-open 상한
5. **완료** 세 상태가 각각 다른 유효 크레딧을 낸다

#### T8.1.2 · 판정 사다리의 자리

- **산출물** `AdmissionDecider` 의 분기
- **근거** **매진(1번)보다 뒤, 낡음(4번)보다 앞이다.** 매진은 서킷과 무관하게
  종결이고, 낡은 재료의 fail-open 이 서킷을 우회하면 안 된다
- **선행** 8.1.1

1. **RED** `매진은_서킷보다_먼저_끊는다`
2. **RED** `서킷이_열리면_낡아도_fail_open_하지_않는다`
3. **GREEN** 사다리에 자리를 잡는다
4. **완료** 사다리 순서 시험이 세 자리를 다 못 박는다

- **선행** 8.1.1

1. **RED** `판정이_서킷_상태를_받는다`
2. **GREEN** 필터가 레지스트리에서 읽어 요청에 싣는다

3. **완료** 같은 시나리오가 켜기 전후로 다른 결과를 낸다

#### T8.1.6 · 배분을 조이는 판단은 클러스터의 것이다 — **완료**

- **산출물** `control/ClusterCircuit.java`, 하트비트에 실린 노드별 서킷
- **근거** 8.1.4 까지 만들고 나면 배분 게이팅의 재료가 **리더 한 대의 로컬
  서킷**이다. 전역 크레딧은 클러스터가 나눠 쓰는 값이므로 한 대의 관측으로
  정하면 두 방향으로 틀린다 — 리더만 멀쩡하면 나머지가 다 열려 있어도 평소
  속도로 돌고(불변식 2 를 위협한다), 리더만 열려 있으면 멀쩡한 클러스터가
  통째로 멈춘다
- **선행** 8.1.3, CY-626 의 하트비트

**분모와 열린 수를 같은 왕복에서 받는다.** 나눠 읽으면 그 사이에 노드가
드나들어 서로 다른 판의 값으로 비율을 내고, 그 비율이 과반 경계에 걸리면
일어나지 않은 상태 전이가 만들어진다.

1. **RED** `노드별_서킷을_세어_돌려준다`
2. **GREEN** 하트비트 값이 `<seconds>|<STATE>` 가 되고 `notClosed` 를 돌려준다
3. **RED** `클러스터_판정을_등록부에_적는다`
4. **GREEN** 배분이 `registry::circuit` 을 읽는다
5. **완료** 과반 열림은 OPEN, 소수는 HALF_OPEN, 관측 없음은 CLOSED 다

> 회복 진동과 함께 C20·C21 에서 잰다 (CY-789).

### 6.2 회복 전이 처리

**대부분은 이미 구현된 것의 실전 검증이다.** 단위 시험은 있고, 장애 구간에서도
같은 성질이 서는지가 안 잡혔다.

**8.2.5 만 예외다.** F7 의 결정은 오류 경로에 **±50% 지터와 연속 실패 지수
백오프**를 요구하는데, 지금 오류 경로는 정상 경로와 같은 ±20% 를 쓰고 백오프가
없다. 검증만 걸어 두면 결정보다 약한 정책이 그대로 나간다.

**검증 태스크의 산출물은 시나리오 판정 한 줄이다.** 새 코드가 아니라, 그
시나리오의 회복 단계에 단언을 더하는 일이다. 완료 조건은 전부 **그 단언이
구현을 되돌렸을 때 빨개지는가**로 잰다 — 안 그러면 통과가 근거가 못 된다.

| ID | 산출물 (단언을 더할 자리) | 무엇을 재나 | 완료 조건 |
|---|---|---|---|
| 8.2.1 | C1·C2 회복 단계 | `dataStale` 해제 순간 리미터 카운터가 이월된다 (F4) | 이월을 끄면 같은 초 통과량이 2배가 되고 그 단언이 빨개진다 |
| 8.2.2 | C6 회복 단계 | 노드 분모의 비대칭이 유지된다 (F5) | 비대칭을 대칭으로 바꾸면 배분 총합이 전역 크레딧을 넘고 빨개진다 |
| 8.2.3 | C7 회복 단계 | 뒷단 인스턴스가 램프업으로 들어온다 (F6) | 램프업을 끄면 콜드 인스턴스 첫 초 유입이 상한을 넘고 빨개진다 |

#### T8.2.5 · 오류 경로의 지터와 백오프 (F7)

- **산출물** `domain/queue/ErrorBackoff.java`, 오류 경로의 `Retry-After` 계산
