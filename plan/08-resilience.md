# Phase 8 — Resilience

> **이 계획의 무게중심.** 장애 중 동작만이 아니라 **회복 전이**를 검증한다.
> 장애 대응으로 바뀐 상태가 장애가 걷힌 뒤 원래대로 돌아오는지, 돌아오는
> 과정에서 2차 장애를 만들지 않는지가 판정 대상이다.
>
> **Phase 9·10 보다 앞선다.** 회복력이 검증되지 않은 시스템을 확장하면
> 장애 반경만 커진다.

**선행**: Phase 7 (닫힘) · **상세 수준**: **완전 명세** (CY-785 에서 승격)

---

## Goal

> **장애가 걷힌 뒤 스스로 정상으로 돌아온다 (R5).**
> 그리고 돌아오는 과정이 2차 장애를 만들지 않는다.

| 통과 수치 | |
|---|---|
| 카오스 시나리오 (21 단일 + 4 조합) | **전부 3단계 판정 통과** |
| 초과 발급 (전 시나리오·전 구간 합산) | **0건** — 타협 불가 |
| 순번 역행 (전 시나리오) | **0건** — 타협 불가 |
| 회복 순간 백엔드 유입 버스트 | **≤ 정상 1.2배** (RC4) |
| 회복 후 정상 지표 복귀 | **≤ 30초** (RC3) |
| 서킷 half-open 회복 시도 | **≤ 2회** (F3) |

**이 게이트가 프로덕션 배포의 실질적 승인선이다.**

> **집계 잡이 실패해야 게이트다.** 브랜치 보호가 요구하는 검사는 `판정` 하나이고
> 개별 잡은 요구 목록에 없다. 그 잡이 출력만 내고 0 으로 끝나면 카오스가 빨개져도
> 병합이 열린다 — 한동안 그랬다 (CY-886). `verdict-selftest.sh` 가 그것을 지킨다.
Phase 9·10 은 이걸 통과한 뒤에만 시작한다 — 회복력이 검증되지 않은 시스템을
확장하면 장애 반경만 커진다.

## 2. 회복이 왜 별도 판정을 받아야 하는가

장애 대응은 시스템을 **다른 모드로 전환**한다. fail-open 상한, 낡은 스냅샷,
줄어든 노드 분모, 열린 서킷, 정지한 배분. 이 전환들은 각각 정상 모드로
되돌아와야 하는데, 되돌아오는 순간이 가장 위험하다.

| 회복 시 위험 | 원인 |
|---|---|
| **억눌린 트래픽 방출** | 장애 중 큐에 쌓인 사람 + 재시도가 동시에 |
| **상한 이중 개방** | 두 경로의 카운터가 같은 초에 모두 열림 (F4) |
| **분모 급변** | 노드가 한꺼번에 복귀해 각자 몫이 급변 (F5) |
| **콜드 인스턴스 과부하** | 재기동 인스턴스가 여유를 과대 보고 (F6) |
| **상태 리셋으로 인한 진동** | EWMA·히스테리시스가 초기화 (F9) |
| **동기화된 재시도** | 고정 `Retry-After` (F7) |
| **서킷 half-open 실패 반복** | 시험 요청 시점에 트래픽 전량 도달 (F3) |

전부 "장애는 견뎠는데 복구에서 무너지는" 형태다. 유지 구간만 보는 테스트는
하나도 잡지 못한다.

## 3. F3 — 서킷 상태가 판정에 반영되지 않으면 회복이 안 된다

서킷브레이커가 열려도 게이트웨이의 판정은 이를 모른다. 계속 `PASS` 판정을 내려
요청을 라우팅하려 하고, 서킷이 가로채 fallback으로 보낸다.

무엇이 일어나는가:

```
백엔드 열화 → 서킷 오픈
  → 게이트웨이는 여전히 통과 판정 → 전량이 fallback으로 (503)
  → half-open 전환 시점
  → 시험 요청이 아니라 "그 순간 도착한 모든 트래픽"이 백엔드로
  → 약한 백엔드가 즉시 재포화 → 서킷 재오픈
  → 회복이 지연되거나 영원히 안 됨
```

**결정**: 서킷 상태를 판정의 입력으로 삼는다.

| 서킷 상태 | 판정 처리 |
|---|---|
| CLOSED | 정상 |
| **OPEN** | 해당 라우트의 유효 credit을 **0으로 간주** → 신규 유입은 큐로 |
| **HALF_OPEN** | 유효 credit을 **소량**으로 제한 → 시험 트래픽만 통과 |

효과:

- 서킷이 열리면 트래픽이 fallback이 아니라 **큐**로 간다 — 사용자는 503 대신
  순번을 받고, 백엔드는 완전히 쉰다
- half-open 시점에 소량만 도달하므로 **회복 판정이 공정해진다**
- 회복 후 credit이 정상으로 돌아오면 큐가 자연히 배수된다

구현: resilience4j의 `CircuitBreakerRegistry`에서 상태를 읽어 `AdmissionDecider`에
전달한다. 로컬 조회이므로 Redis 왕복 0 원칙을 지킨다.

## 4. 회복 판정 공통 기준 (RC)

전 시나리오에 적용된다. 시나리오별 기준은 이것에 **추가**된다.

| ID | 기준 | 측정 방법 |
|---|---|---|
| **RC1** | 초과 발급 **0건** — 장애 전·중·후 전 구간 합산 | 발급 수 vs 재고 |
| **RC2** | 순번 역행 **0건** | 폴링 응답 시퀀스 전수 검사 |
| **RC3** | 회복 후 **30초 내** 판정 분포가 정상 범위로 복귀 | `waiting.admission.decision` |
| **RC4** | 회복 순간 백엔드 유입 버스트 **≤ 정상 1.2배** · 중복 발신 **0건** | 백엔드 스텁 수신 수 — 확인 뒤 창의 봉우리, 회복 대기 구간의 도착/발신 비 |
| **RC5** | 장애 중 큐에 있던 사용자가 **자기 자리 유지** | 사용자별 score 추적 |
| **RC6** | 지표·내부 상태가 장애 이전 값으로 수렴 | EWMA·히스테리시스·노드 분모 |

**RC4가 가장 중요하다.** 나머지가 전부 통과해도 RC4가 깨지면 회복이 곧 2차 장애다.

## 5. 카오스 시나리오

각 시나리오는 **진입 → 유지 → 회복** 3단계로 판정한다.
회복 단계는 위 RC1~RC6에 시나리오별 기준을 더한다.

### C1 — Redis 완전 정지 → 복구

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 스냅샷 유지(지우지 않음), 큐 등록 실패 → fail-open 상한 | 전면 차단 0, 무제한 통과 0 |
| 유지 | 상한 안에서 통과. **어떤 노드도 빠지지 않는다** | 통과량 ≤ 상한, 갱신 루프 정지 0, 503 유출 0, `dataStale` 진입 |
| 회복 | 스냅샷 즉시 재적재, 큐 순번 전원 유지 | RC1~RC6 + 첫 스냅샷까지 5초 이내 |

> **fail-open이 큐를 추월하지 않는지**(F1)를 여기서 함께 본다.
> Redis가 죽으면 큐 등록 자체가 불가하므로 F1의 3번째 규칙(그때만 fail-open)이
> 적용되는 유일한 시나리오다.

### C2 — Redis 지연 주입 500ms → 해제

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 스냅샷 타임아웃 발생, 판정은 로컬이라 영향 없음 | 정상 구간이 뒷단까지 간다 |
| 유지 | 폴링 응답 지연, 갱신 루프는 계속 돎 | 판정 꼬리 불변 · 주입 확인 · 뒷단 도착 |
| 회복 | 지연 해제 후 정상 주기 복귀 | 지연 해제 확인 · 중복 0 · 증폭 |

> **판정 경로가 Redis를 안 치므로 발급 지연이 변하지 않아야 한다.**
> 변한다면 어딘가에서 Redis를 치고 있다는 뜻이다 — G5.1의 실전 검증이다.
>
> **"갱신 루프 정지 0" 은 아직 못 잰다** (CY-828). 그 관측값은 루프의 틱 나이인데
> 고정 시계에서는 항상 0 이라 "돌고 있다" 가 공허하게 참이 된다.
>
> **RC1·RC2·RC5·RC6 도 없다.** 줄이 안 서는 한산한 쿠폰만 때리므로 순번도 자리도
> 생기지 않는다. 버스트 쪽은 닫힌 루프라 못 잰다 (CY-817).

### C3 — Redis 클러스터 노드 failover

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | MOVED/ASK 리다이렉트 처리, 해당 슬롯만 일시 실패 | 다른 샤드 영향 0 |
| 유지 | 복제본 승격 대기 중 그 샤드만 fail-open | 영향 범위가 샤드에 국한 |
| 회복 | 토폴로지 갱신 후 정상 | RC1~RC6 + 승격된 복제본에서 순서 역행 0 (C13) |

> Phase 10 이후에만 실행 가능. 그 전에는 단일 노드이므로 C1으로 대체한다.

### C4 — 배분 리더 강제 종료 → 승계

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | `admitted` 임계 정지, 게이트웨이는 `dataStale` 전까지 정상 판정 | 판정 중단 0 |
| 유지 | `dataStale` 진입 → fail-open. **큐가 있으면 추월 금지**(F1) | 추월 0 |
| 회복 | 3틱 내 새 리더 승계, EWMA·히스테리시스 이월(F9) | RC1~RC6 + 승계 ≤ 3틱, 진동 0 |

### C4b — 리더가 물러나고 다른 노드가 이어받는다

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 두 노드가 서 있고 하나가 리더다 | 노드 둘 · 둘째가 이어받을 수 있다 · 추월 0 |
| 유지 | 남이 락을 가져가 둘 다 내려온다 | **낡음이 안 열린다** · 판정이 멎지 않는다 · 추월 0 |
| 회복 | 산 노드 중 하나가 이어받는다 | 펜스 번호 전진 · 산 노드가 잡았다 · 자리 보존 |

> **C4 는 승계가 아니라 리더 부재를 잰다** (CY-821). 저쪽은 대기 노드가 없어
> 낡음을 강제로 열고, 회복도 같은 노드의 재획득이다. 여기는 둘째가 실제로 서
> 있고, **낡음이 열리지 않는 것이 설계 의도**다 — 리스가 낡음 문턱보다 짧다.
>
> **락을 비워 다투게 하지 않는다.** 그러면 두 연장 루프의 위상이 고정돼 늘 같은
> 쪽이 먼저 닿고, 무리더 구간의 길이도 시험이 정하게 된다 — 리스가 낡음 문턱을
> 지키는지가 안 재진다. 리더의 제어 평면만 세우면 락이 만료까지 남아 그 구간이
> 프로덕션 리스 그대로이고, 후보가 하나뿐이라 누가 이어받는지도 결정적이다.
>
> **낡음은 창 전체로 본다.** 나이는 새 리더의 첫 발행 직전에 가장 크고, 그 시점은
> 회복 단계 안이다 — 유지 판정에 한 점으로 걸면 가장 얕은 순간을 본다 (AIJ-0174).
>
> **RC1·RC3·RC4·RC6 은 안 잰다.** RC5 는 앞줄 제거가 재개 유예에 걸려 구조적으로
> 안 깨진다 (CY-844).
>
> **시계 스큐(C11)와 유령 리더의 배분(C5b)은 여기서 못 만든다.** 앞엣것은
> 컨테이너를 따로 띄워야 하고, 뒤엣것은 한쪽의 레디스만 끊어야 한다.

### C5 — 리더 네트워크 분단 (스플릿 브레인) → 복구

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 구 리더가 락 만료를 모른 채 한 틱 더 수행 가능 | 창이 열렸다 · 그 창에서 추월 0 |
| 유지 | 낡음 진입 → fail-open. **큐가 있으면 추월 금지**(F1) | 낡은 갈래를 밟았다 · 추월 0 · 사실로 강등 |
| 회복 | 분단 해소 후 구 리더가 락 상실을 인지하고 물러남 | 분단이 실제로 걸렸다 (펜스 번호 전진) |

> 펜싱 토큰을 쓰지 않는 근거의 실전 검증이다. **여기서 초과 발급이 1건이라도
> 나오면 근거가 무너진 것이므로 펜싱을 도입해야 한다.**
>
> **그런데 초과 발급을 여기서 못 잰다.** 뒷단이 스텁이라 재고를 안 깎는다.
> 재는 것은 **줄 선 사람을 추월하지 않는가** 하나이고, 그건 게이트웨이의 몫이다.
> 발급 계층과 붙여야 초과 발급 쪽이 열린다 (AIJ-0170).
>
> **RC1~RC6 도 안 잰다.** 자리 유실(RC5)은 스위퍼의 재개 유예가 승계마다 0 부터
> 다시 서서 시험 수명 안에 앞줄 제거가 한 번도 안 돌아, 판정을 무력화해도 초록이다
> (CY-844). RC4·RC6 은 표본과 관측이 없다 (CY-848).
>
> **그 유예가 시험만의 사정이 아니다.** 프로덕션에서도 승계가 잦으면 유예가 계속
> 0 으로 되돌아 이탈자 청소가 영영 안 돈다 — 해제 조건이 없다 (CY-846).
>
> **되돌릴 수 없는 쓰기 중 펜스가 걸린 것은 매진 큐 삭제 하나뿐**이고, 재고가 남은
> 이 시나리오에서 한 번도 실행되지 않는다. 펜스 번호는 값으로만 검증됐고 **문으로서는
> 검증되지 않았다** (CY-844 · CY-845).
>
> **유령 리더가 실제로 배분을 도는 경우는 아직 못 만든다.** 노드 둘은 섰지만
> (CY-821) 둘이 같은 레디스를 본다 — 한쪽만 끊으려면 노드마다 프록시를 둬야 한다
> (CY-862). 그것이 서면 C5b 와 스냅샷 발행 울타리(CY-845)를 같이 잰다.

### C6 — 게이트웨이 노드 1대 종료 → 복귀

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 헬스체크 503 → LB 제외. 즉시 등록 해제 | 5xx 유출 0 |
| 유지 | 남은 노드가 큰 분모를 써서 과소 통과 (안전 방향) | 초과 0 |
| 회복 | 복귀 노드가 하트비트 → **분모 즉시 반영**(F5) | RC1~RC6 + 총 통과 ≤ globalCredit + **복귀 노드의 유입 비율 오차 ≤ ±15%** (G9.12) |

> F5의 비대칭 반영을 검증하는 시나리오. 분모 반영이 늦으면 여기서 초과가 나온다.
> **복귀 노드의 라우팅 품질도 같이 본다** — 로컬 관측이 0 이라 열화 인스턴스를
> 구별하지 못하는 구간이 여기서 드러난다 ([09-routing.md](09-routing.md#cold-start)).

### C7 — 백엔드 인스턴스 1대 종료 → 콜드 복귀

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 그 인스턴스 보고가 낡아 합산에서 제외 → globalCredit 감소 | 유입이 즉시 조정 |
| 유지 | 남은 인스턴스 여유에 맞춰 배분 | 남은 인스턴스 포화 0 |
| 회복 | **콜드 인스턴스가 램프업**(F6) | RC1~RC6 + 복귀 직후 그 인스턴스 유입이 램프 곡선을 따름 (`startedAt` 전에는 2차, 후에는 선형 — A-13) |

### C9 — 뒷단이 5xx 를 낸다 (PRD 필수 시나리오)

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 평시 판정. 줄이 서 있고 대조 쿠폰은 뒷단까지 간다 | 추월 0 · 줄에 섬 · 대조군 통과 |
| 유지 | 대기열 순번이 Redis에 남아 유지됨 | 순번 유실 0 · 500 이 그대로 유출 · 대조군 통과 |
| 회복 | 뒷단 복구 후 통과 경로가 되살아난다 | 대조군 통과 · RC2 순번 보존 · RC5 자리 보존 · 중복 발신 0 |

> **표제를 5xx 로 바꿨다.** 스텁이 내는 것은 500 이고, DB 커넥션 끊기는 그것을
> 만드는 원인 중 하나일 뿐이다. 아래 8.1 절의 "C9 는 존재하지 않는 진입 조건을
> 판정하고 있다" 는 지적이 가리키던 것이 이 어긋남이다.
>
> **서킷은 여기서 안 열린다.** 표본이 모자란 것도 있지만 더 앞의 이유는 배선이다 —
> 서킷 필터에 `statusCodes` 를 안 넘겨서 500 이 성공으로 집계된다 (CY-853).
> 그래서 진입 판정에 "서킷 오픈" 을 안 적는다. C8 과 갈리는 것은 **스텁이 내는
> 값**(응답 없음 대 500)이다.
>
> **초과 발급은 못 잰다.** 뒷단이 스텁이라 재고를 안 깎는다. 가진 것은 뒷단이
> 같은 회원을 두 번 받았는지뿐이고, 그건 게이트웨이가 중복 발신했는지만 말한다.
>
> **RC1·RC3·RC6 도 안 잰다.** 회복까지의 시간 판정도 없다. 재등록 갈래의 생존
> 신호 갱신은 그 수명이 시험 수명보다 길어 못 잰다 (AIJ-0171).

### C16 — 가용량 읽기만 느리다

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 가용량 읽기만 예산(틱의 1/4)을 넘긴다. 수요·발행은 성공 | 예산 안은 성공하고 밖은 실패한다 · 유예 안에서는 크레딧이 직전 값 그대로 · 평시에 관측이 실렸다 |
| 유지 | 유예 뒤로는 줄되 바닥이 노드를 받친다 | **유예를 한 회차 넘기면 딱 한 번 반토막** · 노드당 몫 ≥ 유휴 역수 (R1) · 뒷단이 보고한 0 은 안 올라간다 · 게이지가 배분값을 따라간다 |
| 회복 | 첫 성공 회차에 실측으로 복귀 | 정확히 실측값이다 (RC6) · 유예가 다시 차서 바로 다음 실패에 안 깎인다 · 램프 창을 넘긴 장애도 첫 회차에 실측이다 |

> **감쇠가 실제로 도는 구간은 여기뿐이다.** 레디스가 통째로 죽으면 수요 읽기도
> 같이 죽어 회차가 통째로 실패하고, 감쇠값이 배분에 닿지도 않는다. 읽기 예산이
> 틱의 1/4 이라 이 부분 장애가 가장 흔한 형태다.

> **임기가 짧으면 감쇠가 한 번도 안 돈다.** `leadershipAcquired` 가 유예를 0 으로
> 되돌리므로, 임기가 유예보다 짧으면 그 모드에 도달할 수 없다. 그런데 읽기를 예산
> 밖으로 미는 지연은 리스 갱신도 같이 밀어, **그 사고가 바로 짧은 임기를 만든다** —
> 대비하려던 장애에서만 방어가 안 도는 셈이다. 감쇠를 임기의 회차가 아니라 마지막
> 성공 관측 이후의 시간으로 세야 한다 (티켓 미발번).
>
> **뒷단이 0 을 말한 뒤 읽기가 죽으면 빠져나올 길이 없다.** 0 은 감쇠가 안 올리고
> 하한 재적용도 못 건진다. 그동안 한산한 쿠폰까지 전 노드에서 큐로 가고 그 큐는
> 안 빠진다 (R1). "길어지면 관측이 아니라 추측" 이라는 논거를 양수에만 적용하고
> 0 에는 안 적용한 자리다 (티켓 미발번).
>
> **그 모드에는 진입 로그도 해제 로그도 없다.** 감쇠 창은 0 → 0 이라 안 열리고,
> 하한 창은 성공한 회차에서만 평가된다. 운영자가 보는 것은 읽기 실패 경고 한 줄과
> 그 뒤의 침묵이다 (LG-2 · 티켓 미발번).
>
> **회복의 계단을 받칠 것이 하필 그 사고에서 콜드다.** 첫 성공 회차에 크레딧이
> 바닥에서 관측치로 한 번에 뛰고, 그 사이에 서 있는 것은 평활화뿐이다. 이월을 못
> 받은 회차는 관측치를 생으로 내는데 (CY-864), 이월 읽기와 가용량 읽기가 같은
> 레디스라 하필 여기서 콜드일 확률이 가장 높다. 게다가 그때 뒷단이 보고하는 여유는
> **우리 억제가 만든 값**이라 지속 가능한 처리량이 아니다. CY-835 의 램프가 들어올
> 때 서킷 닫힘만이 아니라 이 모서리도 덮어야 한다 (티켓 미발번).
>
> **시나리오는 수집기에서 끝난다.** 값이 배분에 닿는 데까지는 안 본다 — 평활화·하한
> 재적용·게이팅이 전부 밖이고, 리더십도 안 갈린다. RC4 의 제어 평면 절반(틱당
> 크레딧이 비탈로 돌아오는가)은 큐 하네스 없이도 잴 수 있다 (티켓 미발번).

### C18 — 뒷단 무응답 (TCP 는 받고 헤더를 안 보냄)

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 평시에 길이 열려 있다 | 대조군 통과 · 격벽 비어 있음 |
| 유지 | 붙기는 하는데 응답을 안 보낸다 | **503 + 다시 올 시각 + 사유** · 격벽 누수 0 · 서킷 창에 표본 > 0 |
| 회복 | 뒷단 재기동 | 통과 경로 복귀 · 중복 발신 0 |

> **자극은 C8 과 같다. 판정으로 갈린다.** 둘 다 응답을 안 내는 뒷단을 쓴다.
> C8 은 서킷이 열렸다 닫히는 것을 보고, 여기는 **멎은 요청이 격벽 자리를 쥐지
> 않는가**와 **어떻게 끝내는가**를 본다 — 504 가 아니라 503 에 다시 올 시각을
> 실어 끝낸다 (6.2.4 · AIJ-0177).
>
> **half-open 프로브 수와 회복 시도 횟수는 C8 의 자리다.**
>
> **RC4 의 절반은 잰다** — 중복 발신 0 과 증폭 1.0 배다. RC1·RC2·RC3·RC5·RC6 은
> 안 잰다. 줄이 안 서는 한산한 쿠폰만 때리므로 순번도 자리도 안 생긴다.
>
> **서킷은 여기서 한 번도 안 열린다.** 운영값이 창 10초에 최소 20건이고 이 시험은
> 세 건을 보낸다. 그래서 관측되는 503 은 열린 서킷의 폴백이 아니라 **닫힌 서킷의
> 오류 폴백**이다 — F3 과 half-open 은 이 시험을 안 지난다. C8 은 그 값을 낮춰
> 재고, 운영값에서의 OPEN 구간은 아직 어느 시나리오도 안 지난다 (CY-871).
>
> **"줄이 안 선다" 는 그 사실에 기댄다.** 서킷이 열리면 사다리가 한산한 쿠폰에도
> 줄을 세우고, 그 순간 RC2·RC5 가 생긴다.
>
> **헤더는 오고 본문이 안 끝나는 변종은 반대로 통과한다.** 서킷은 헤더 도착을
> 성공으로 집계하고, 격벽 자리는 그 순간 이미 반납됐고, 503 대신 잘린 200 이
> 나간다 (CY-870).
>
> **`BackendStallTest` 도 C18 을 자칭한다.** 저쪽은 서킷 설정을 낮춰 표본이
> 쌓이는 것만 보고, 이쪽은 운영값 그대로 돌며 끝내는 방식과 격벽을 본다.
>
> **C8 은 지연, C9 는 5xx 를 전제한다.** 응답 자체가 안 오는 구간은 그 둘 사이로
> 빠지는데, 스레드풀이 마르거나 DB 커넥션이 끊기면 뒷단은 5xx 를 내는 것이 아니라
> **아무것도 안 낸다.** C9 의 표제를 "DB 커넥션 끊기" 에서 "뒷단이 5xx" 로 고쳐
> 그 어긋남을 없앴고, 안 낸다는 쪽은 이 C18 이 맡는다.

> **끊는 자리가 서킷 안팎 중 어디인지가 이 시나리오의 핵심이다.** 밖에서 끊으면
> 서킷이 받는 것은 오류가 아니라 취소이고, 취소는 창에 안 쌓인다 — 표본이 0 이라
> 서킷이 영원히 안 열리고, 그동안 게이트웨이는 죽은 뒷단에 계속 밀어 넣는다.
> 초록불은 그대로다. 이 시나리오만이 그것을 잡는다.

> **회복 단계의 RC4 를 꼭 넣는다.** 재기동으로 회복하면 물려 있던 커넥션이 한
> 순간에 끊기고 격벽 자리가 같은 초에 통째로 풀린다. 초당 리미터가 잡아 준다는
> 가정이 실제로 성립하는지는 여기서만 확인된다.
>
> **지금은 그 회복을 안 만든다.** C18 의 회복은 스위치를 되돌리는 것이라, 물려
> 있던 커넥션이 한꺼번에 끊기는 순간이 안 생긴다 — 요청이 순차라 회복 시점에
> 물린 것이 없다. 중복 발신 0 과 증폭은 재지만, 위 문단이 요구하는 시나리오는 뒷단을
> 실제로 재기동하고 열린 루프로 물려 둬야 만들어진다 (CY-872).

### C17 — 시계 역행과 유령 인스턴스

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 승격한 복제본의 시각이 뒤로 간다 | 평시에 관측이 실렸다 · 보정값이 바닥값이다 · 단조 가드가 **정확히 한 번** 걸린다 · 역행 폭이 지표에 남는다 |
| 유지 | 보정한 시각으로 걷어 크레딧이 유지된다 | 승격 전 값과 같다 — **도메인 계약만 잰다.** 배선은 아직 이 값을 안 쓴다 (아래 인용문) |
| 회복 | 시계가 따라잡으면 바닥값을 놓는다 | 실측값과 **정확히** 같다 |
| 회복(유령) | 시계가 앞선 뒷단이 죽는다 | 마지막 보고가 신선도 창 + 허용치까지만 세어진다 · 허용치를 넘게 앞선 보고는 처음부터 안 받는다 · **그 몫이 갓 뜬 뒷단의 콜드 램프값과 같은 스냅샷에 실리고, 창을 넘기면 빠진다** |

> **유령이 회복 첫 구간에 겹친다.** 죽은 인스턴스가 새 식별자로 돌아오면 그
> 몫이 콜드 램프값과 함께 실린다 — 뒷단이 가장 차가울 때 유입이 가장 높다
> (F6·RC4). 그래서 앞섬 허용치를 신선도 창과 따로 둔다. 유령이 네 번째 단계가
> 아니라 회복 판정인 것도 그래서다. 떼면 그 겹침이 안 재진다.

> **앞섬 허용치는 양쪽으로 물린다.** 줄이면 시계가 앞선 뒷단이 아예 등록이 안 되고,
> 늘리면 죽은 뒤 창의 두 배 가까이 산다. 값 하나가 아니라 두 방향의 균형이다.
>
> **RC6 를 밴드로 안 잰다.** 보정이 먹히면 크레딧이 안 떨어져 이 시나리오에는
> 저하되는 대상이 없다 — 밴드로 재면 같은 값끼리 비교하는 셈이다. 정확 일치로
> 재고, 그것이 RC6 의 기준을 포함한다.
>
> **실제 승격이 아니라 서버 시각 관측을 손으로 부른다.** 레디스가 승격 순간에 어떤
> 시각을 내는지는 여기서 안 잰다 — 그건 C13 이고 Phase 10 이후다.

> **시계가 뒤로 가면 크레딧이 하한에 박힌다.** 30초 뒤진 복제본이 승격하면 모든
> 보고의 나이가 -30초가 되어 앞섬 허용치에 전부 걸린다. 20,000명 줄에서 초당 다섯
> 명만 나가고, 시계가 따라잡을 때까지 그대로다. 보고를 읽는 자리가 단조 가드를
> 부르면서 **반환값을 버리기** 때문이다.
>
> **단조 바닥값으로는 안 닫힌다** (CY-875). 실제로 붙여 보고 알았다. 나이는 레디스
> 시각과 뒷단이 찍은 시각의 차인데, 바닥값은 **분자만 얼린다** — 분모는 뒷단의 자기
> 시계라 계속 앞으로 가서 허용치 1 초를 두 틱 만에 다시 넘는다. 30초 역행에서 억제가
> 28초로 줄 뿐이고, 뒤진 복제본이 계속 그 상태로 돌면 영구 억제인 것도 그대로다.
>
> 근본 원인은 **분자와 분모가 서로 다른 벽시계**라는 것이라, 어느 한쪽만 만져서는
> 안 닫힌다. 값을 고르지 않고 결정으로 올렸다 —
> [90-decisions.md](90-decisions.md) D-C4. 그 전에는 이 자리에 무엇도 처방하지 않는다.
>
> **그래서 유지 판정을 배선까지 안 올린다.** 지금 값을 그대로 단언하면 이 전면
> 억제가 "회복력 시나리오 통과" 로 기록된다 — 기준을 낮추는 것이고, 8절이 금지하는
> 자리다. 유지 구간은 도메인 계약만 재고, 배선은 **G8.14 미충족으로 남긴다.**
>
> **C17 은 진입 순간만 잰다.** 한 회차를 걷고 끝나므로 위의 "두 틱 뒤부터 다시 버린다"
> 를 구조적으로 못 본다. 여러 틱을 흘려보내며 신선 건수가 유지되는지 보는 시나리오가 따로
> 있어야 한다 (C17b, 아래 5절 제안).
>
> **자바 쪽 반환값을 쓰는 것으로 고치면 안 된다.** 바닥값이 프로세스 메모리라,
> 역행 직후에 한 노드만 재기동하면 그 노드는 전부 신선하다고 보고 나머지는 전부
> 낡았다고 본다. 리더가 누구냐에 따라 유입이 수천 배 갈린다 (F9).
>
> **펜스 번호도 생 시각에서 나온다.** `leader_acquire.lua` 가 획득 때마다 `TIME` 으로
> 펜스 번호를 만들고, 승격(FOLLOWER→LEADER)은 그 값을 그대로 받는다. 시계가 뒤로 간
> 뒤 뽑힌 리더의 펜스 번호는 옛 리더가 남긴 것보다 작아, 매진 큐 삭제의 울타리가 새
> 리더를 옛 리더로 보고 거절한다. 반환이 0 이고 그건 "안 지웠다" 와 "지울 것이
> 없었다" 를 못 가르므로 **로그도 안 남는다.** 펜스 번호를 시계에서 유도할 이유가
> 없다 (티켓 미발번).
>
> **겹침의 실제 폭은 창보다 길다.** 수집기 안에서는 신선도 + 허용치에서 끝나지만,
> 배분이 쓰는 값은 평활을 한 번 더 지난다. 잔차가 매 틱 0.7 배로 줄 뿐 끊기는
> 지점이 없어, 유령이 만료된 뒤로도 과대 상태가 이어진다 — 몇 틱인지는 시작 오차와
> 그 뒤 관측이 정한다. 그리고 겹침 최대 배율은
> `1 + (신선도 + 앞섬허용) / 램프` 다 — 운영값에서는 1.07 배지만 램프를 20초로
> 줄이면 1.2 배가 되어 RC4 가 그 자리에서 깨진다. 어디에도 안 적혀 있던 관계다.
>
> **RC4 의 분모가 이 구간에서 틀린다.** 겹침 최대치를 장애 이전 정상값으로 나누면
> 1.05 배라 한계를 여유 있게 통과하는데, 같은 순간 뒷단이 실제로 감당할 수 있는
> 것과 비교하면 스무 배다. 회복 구간의 위험은 "장애 전보다 많이 들어가는가" 가
> 아니라 "지금 뒷단이 감당할 수 있는 것보다 많이 들어가는가" 다. 램프가 존재하는
> 이상 둘이 갈리는 구간이 반드시 생기고, 그 구간이 정확히 F6 이 노리는 곳이다.
>
> **관측이 없다.** 앞섬 거절과 낡음 거절이 같은 값으로 접혀 어느 쪽도 안 세어진다 —
> 운영자가 보는 것은 "신선한 보고가 없다" 한 줄이라 뒷단을 보러 간다. 램프가 깎은
> 몫도 세어 놓고 판정에만 쓰고 버린다. 겹침 구간을 밖에서 볼 지표가 하나도 없다
> (LG-2 · 티켓 미발번).

### C11 — 노드 간 시계 스큐

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 초당 윈도우 경계가 노드마다 어긋남 | |
| 유지 | 신선도 판정이 스큐만큼 편향 | 낡은 데이터를 신선하다고 판정 0 (앞섬 허용치 이내는 제외) |
| 회복 | 시계 동기화 후 정상 | RC1~RC6 |

> `capacity` 보고의 `ts`, 리더 락 TTL, 초당 윈도우가 전부 시계 의존이다.
> 스큐 허용 범위를 명시하고 그 밖에서는 보수적으로 동작해야 한다.
>
> **앞섬은 1초까지 받는다.** 기준 시각과 보고를 동시에 읽으므로 시계가 맞아도
> 초 절단으로 1초가 어긋난다. 그 대가로 죽은 인스턴스의 마지막 보고가 신선도
> 창보다 1초 더 산다 — 그 폭을 값으로 재는 것이 이 시나리오다.

> **아직 못 돈다.** 두 노드가 한 JVM 이라 시계가 공유다. 노드마다 시계를 달리
> 주려면 컨테이너를 따로 띄워야 한다.

### C12 — Redis `kill -9` 후 영속성 복구

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 평시 판정. 줄이 서 있고 대조 쿠폰은 뒷단까지 간다 | 추월 0 · 줄에 섬 · 대조군 통과 |
| 유지 | 줄에 세울 방법이 없어 fail-open 이 열린다 | 판정이 멎지 않는다 |
| 회복 | 유실 구간의 등록은 사라지고 그 사람들은 재등록한다 | 영속이 일했다 · 증발이 일어났다 · 남은 자리 보존 · 재등록자가 추월 0 |

> **유지 구간의 fail-open 은 C1 이 재고 여기서 다시 안 잰다.** 레디스가 죽으면
> 줄에 세울 방법 자체가 없어 F1 의 세 번째 규칙이 적용되는 유일한 구간인데,
> 그 통과가 상한 안인지를 두 시나리오가 각자 재면 기준이 갈린다.
>
> **증발을 결정적으로 만든다.** 그냥 등록하고 죽이면 everysec 이 이미 내려쓴
> 뒤라 열에 열이 살아남고, 그러면 회복 구간의 재등록이 재조회가 되어 추월
> 판정이 원래 자리를 다시 읽는 데 지나지 않는다 (AIJ-0172).
>
> **추월 0 은 시계가 정상인 동안 자명하게 성립한다.** 새 점수가 이미 남은
> 사람보다 크기 때문이다. 바닥값 방어가 값을 하는 상황은 C13 이 만든다.
>
> **`kill -9` 로는 부분 유실이 안 난다.** everysec 은 매 루프마다 커널에 넘기고
> fsync 만 미루므로, 프로세스만 죽으면 페이지 캐시가 남는다. 그래서 시험이
> 경계를 직접 긋는다 — everysec 유실을 재현하는 것이 아니라 **그 최악 유실의
> 끝 상태를 만드는 것**이다 (AIJ-0172).
>
> **스위프의 생존 신호 가드와 임계 단조성은 여기서 검증되지 않는다.** 앞엣것은
> 앞줄 제거가 재개 유예에 걸려 안 돌고(CY-844), 뒤엣것은 회복 뒤 배분이 임계를
> 다시 올려 되돌아간 값이 관측되지 않는다.
>
> **되살아난 입장자를 안 본다.** 폴링을 한 번도 안 부르기 때문이다 (CY-854).
>
> **초과 발급·RC1·RC3·RC6 은 안 잰다.** 뒷단이 스텁이라 재고를 안 깎는다.

> `everysec` 라 최대 1초 분량이 증발한다(E-6). **증발 자체는 허용**하고,
> 남은 대기자를 재등록자가 추월하지 않는지만 본다. 새 score 가 더 크므로
> 성립해야 한다.

### C13 — 복제본 승격 + 시계 역행 ★

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 마스터 정지, 시계가 **뒤처진** 복제본을 승격 | 판정 중단 0 |
| 유지 | 새 등록의 score 가 `maxscore` 바닥에 걸려 밀려 올라간다 | **순서 역행 0** |
| 회복 | 시계가 따라잡으면 score 가 다시 실제 시각을 쓴다 | RC1~RC6 |

> **A-9 의 단조 가드를 검증하는 유일한 시나리오다.** 시계 역행이 실제로
> 일어나는 지점이 승격이고, 여기가 깨지면 **줄 선 사람이 통째로 추월당한다**
> (불변식 4). 하네스는 시계 조작과 `failover` 를 지원해야 한다 (6.0절).

### C14 — 호스트 서스펜드 5초 ★

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 리더 노드의 호스트를 정지. **단조 시계가 안 흐른다** | 판정 중단 0 |
| 유지 | 서버 TTL 은 벽시계라 락이 풀리고 다른 노드가 잡는다 | 새 리더가 뽑힌다 |
| 회복 | 깨어난 노드가 **한 회차 안에** 남이 쥐었다는 사실을 물고 내려온다 | 겹침 ≤ 1틱 · RC1~RC6 |

> **C10(STW)으로 대체할 수 없다.** STW 동안은 단조 시계가 흐르므로 나이 판정이
> 잡아내지만, 서스펜드는 안 흐른다 — 깨어난 노드의 나이가 거의 0 이라
> **`isLeader()` 가 여전히 참**이다. 리더십에서 나이 방어가 안 듣는 유일한
> 경로이고, 여기만 "남이 쥐고 있다" 는 사실 확인에 기댄다.

### C15 — Redis 지연 상승 유지 ★

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 응답 지연을 `leader.attempt` 위로 올린다 | 평시에 리더가 하나다 · 지연 진입에도 하나다 (시도 상한이 답 없는 시도를 끊는다) |
| 유지 | 연장만 매번 상한에 걸린다 | **확인 없이 리스가 지나면 내려온다** — 둘이 되는 대신 0 이 된다 |
| 회복 | 지연이 걷힌다 | 한 회차 안에 다시 하나다 · 펜스 번호를 들고 돌아온다. **RC4 는 못 잰다** |

> **시도 상한을 조이면 리더가 둘이 되는 대신 아무도 리더가 아니게 된다.** 배분이
> 멎고 크레딧이 안 갱신되며, 5초 뒤 `dataStale` 이 뜨는데 그걸로는 503 을 못 내니
> 조용히 fail-open 한다. `G4.1` 이 "정확히 1대" 라 0대를 이미 배제하므로, 이
> 시나리오는 그 게이트를 **지연 구간에서도** 재는 것이 목적이다.

> **재는 것은 리더십뿐이다.** 이 시나리오는 줄도 뒷단 유입도 안 세워서 "밀린 크레딧이
> 한꺼번에 안 나간다" 를 못 잰다 — 그건 열린 루프가 있어야 한다 (CY-817).
>
> **시계를 못 주입한다.** 시계를 받는 생성자가 제어 평면 패키지 안에서만 열려 있어,
> 리스와 시도 상한을 비를 지킨 채 축소하고(250ms·50ms) 여유를 리스의 세 배로 잡았다.
> 운영값으로 재면 한 회차가 수십 초다.

### C19 — 전역 폴링 배수 하강 ★

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 큰 쿠폰 A 와 작은 쿠폰 B 를 함께 띄워 배수를 올린다. **분모가 노드 하나라 걸린다** — 설계 규모 20 대에서는 같은 줄로 안 걸린다 | 평시에 배수가 안 걸려 있었다 · 평시 간격이 밴드 그대로다 · 배수가 정확히 8.275 로 오른다 |
| 유지 | B 의 앞·중간·꼬리가 각각 무엇을 받는가 | 앞의 둘은 밴드×배수 · **꼬리는 천장에 막히고, 거기서도 흔들린다** · 부하가 예산의 2.2~2.4 배다 · **배수를 아무리 올려도** 부하가 `대기자/천장` 위에서 멎고 그 바닥이 예산 위다 |
| 회복 | A 의 재고를 0 으로 만들어 **한 틱에** 배수를 1.0 으로 떨군다 | 배수가 1.0 이다 · 간격이 밴드로 돌아온다. **RC4 는 못 잰다** — 아래 |

> **배수에는 평활도 히스테리시스도 없다.** 매 틱 처음부터 다시 계산되고, 쿠폰
> 하나가 매진되는 한 틱에 1.0 으로 떨어진다. 그동안 입장 토큰은 폴링해야 받으므로
> 배수만큼 미청구 입장자가 쌓여 있고, 배수가 풀리는 순간 그것이 평시 유입에 얹혀
> 나간다 — **RC4 가 겨눠야 할 자리인데 이 시나리오로는 못 잰다** (아래).
>
> `CreditSmoother`·`QueueingHysteresis`·가용량 램프업이 다 붙어 있는 구성에서
> 배수만 맨몸이다. 하강에만 램프를 걸면 적체가 서서히 풀린다 (CY-731). **다만 그
> 램프를 이 시나리오로는 못 잰다** — 배수가 상태 없는 함수라 램프를 넣어도 여기는
> 안 빨개지고, 그 전이는 배분 회차를 세우는 단위 시험이 이미 잰다.

> **"실측 폴링 ≤ 예산" 은 배수율이 느리면 성립하지 않는다.** 갈리는 것은 천장이
> 아니라 배수율이다 — 설계점(노드 20 · 배수율 4,000)에서는 전원이 첫 밴드라 실측이
> 예산의 1.02 배이고, 배수율이 50 이면 대부분이 가장 먼 밴드에 몰려 천장에 막힌다.
>
> **닫힌 형태로 상한이 나온다.** 배수를 아무리 올려도 간격이 **지터 전 천장**을 못
> 넘으므로 부하가 `대기자 / 천장` 아래로 안 내려간다. 그래서 노드 하나가 담을 수
> 있는 대기자는 많아야 `예산 × 천장` 이다.
>
> **정확히 그 값은 아니고 그보다 작다.** 개인이 받는 값은 지터가 흔든 뒤라 천장이
> 아니라 [천장×0.8, 천장×1.2] 이고, 1/x 가 볼록해서 평균 부하가 1/천장보다 크다 —
> 2만 명 구성에서 404 가 아니라 409 다. 상한으로 읽고 실제 용량은 그 아래로 본다.
> 실측과 유도는 [AIJ-0182](../ai/journal/2026/09/AIJ-0182-c19-poll-scale.md) 에 있다.

> **한 틱 하강이 폴링 빈도에 하는 일을 값으로 재 봤다.**
>
> | 밴드 | 배수 걸린 간격 | 하강 뒤 | 빈도 |
> |---|---|---|---|
> | 1초 | 8.3초 | 1초 | 8.3배 |
> | 3초 | 24.8초 | 3초 | 8.3배 |
> | 10초 | 50초 | 10초 | 5.0배 |
> | 30초 | 50초 | 30초 | 1.7배 |
>
> 가까운 밴드일수록 크다 — 그리고 차례가 가까운 사람이 곧 발급 경로로 갈 사람이다.
> **그 유입이 실제로 1.2 배를 넘는지는 여기서 못 잰다.** 닫힌 루프라 발신 속도가
> 게이트웨이 지연으로 정해진다 (CY-817). 이 표는 그 위험의 크기를 값으로 남긴 것이지
> RC4 판정이 아니다.
>
> **`overshoot.ticks` 계수는 여기서 안 본다.** 그 계수는 배분 회차가 올리는데, 이
> 시나리오는 예산 계산과 폴링 정책만 걷는다. **배분 회차를 세워 그 계수와 진입·해제
> 로그를 재는 단위 시험이 이미 있다** — 여기서 다시 재면 사본이다.
>
> **RC3 의 기산점은 배수 하강이 아니라 하강 뒤 첫 폴링이다.** 발급 경로에
> 트래픽을 넣는 것은 폴링해서 차례를 확인한 사람인데, 배수가 걸린 동안 그들이
> 받은 간격이 40~60초다. 하강한 틱부터 30초를 재면 아직 아무도 안 돌아왔으므로
> 어떤 구현으로도 못 넘긴다 — 없는 결함을 찾게 되거나 기준을 임의로 낮추게 된다.
> **한 폴링 주기(≤60초) 안에 복귀**로 읽는다.

### C20 — 혼재 버전 스냅샷

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 리더가 옛 형식으로 낸다 | 새 버전이 그것을 받는다 · 옛 버전이 새 형식을 받는다 |
| 유지 | 재고 미상과 자리 수가 갈린 스냅샷 | 미상이 예약 자리로 왕복한다 · **남는 자리는 무시하고 모자란 자리는 안 받는다** |
| 회복 | 리더를 새 형식으로 승계 | — **노드를 안 세워서 못 잰다** |

> **배포는 한 순간에 안 끝난다.** 쿠폰 값의 필드 수를 바꾸면 그 구간에 한쪽이
> 상대의 재료를 통째로 버리고, 새 파드는 발행된 스냅샷을 하나도 못 받아 준비
> 상태가 안 된다 — 롤아웃이 그 자리에서 멈춘다. E-12 가 정책 값에서 이미 겪은
> 결함이다. 모르는 필드는 무시하고, 모자란 것만 뺀다.

> **부호화만 걷는다.** 노드도 줄도 안 세워서 "새 파드가 준비 상태가 된다" 와 "옛
> 노드가 5초 안에 정상 판정" 은 못 잰다 — 그건 노드 둘짜리 하네스의 일이다.
> 여기서 재는 것은 그 상태를 만드는 **부호화의 관대함**이다.
>
> **옛 버전을 실제로 못 부른다.** 그 회차가 냈던 필드 수로 손수 만든다. 그래서 이
> 시나리오는 "옛 버전이 이렇게 냈었다" 는 기억에 기댄다 — 그 기억이 틀리면 관대함을
> 엉뚱한 모양에 대고 재게 된다.

### C21 — 배수가 걸린 채 노드 절반 소실

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 배수 5 인 상태에서 20대 중 10대를 죽인다 | 평시 노드당 몫이 설계값이다 · 분모가 한 틱에 안 내려간다 |
| 유지 | 노드 수 하강 지연을 넘겨 유지 | 마지막 틱 전까지 안 내려가고 그 틱에 내려간다 · 내려간 뒤 노드당 몫이 설계값이다 · 관측 실패가 하강 연속을 끊는다 · **지연 구간이 살아남은 노드 비율을 안 넘는다** |
| 회복 | 10대 복귀 | 분모가 즉시 올라간다 · 노드당 몫이 설계값으로 돌아온다(앞 둘에서 나오는 산술) |

> **분모의 올바른 비대칭이 발급과 폴링에서 서로 반대다.** 발급 상한은 증가 즉시·
> 감소 지연이 맞다 (F5). 폴링 예산은 거꾸로다 — 노드가 줄면 예산은 즉시 줄어야
> 살아남은 노드가 설계값의 두 배를 안 받는다. 지금은 F5 의 분모를 그대로 쓴다
> (CY-732). X4 와 인접하지만 X4 는 크레딧 분모를, 이건 폴링 예산 분모를 본다.

> **재 봤더니 정확히 두 배다.** 설계 규모(노드 20 · 대기 2만 · 배분율 4,000)에서
> 평시 노드당 폴링이 200 이다. 절반이 죽고 분모가 아직 20 이면 예산이 4,000 그대로라
> 총 부하도 4,000 이고, 그것을 열 대가 나눠 **노드당 400** 을 받는다. 지연이 끝나
> 분모가 10 이 되면 예산 2,000 · 배수 10 · 노드당 200 으로 돌아온다.
>
> **그 두 배를 통과 조건으로 안 삼는다.** 지연 구간이 설계값을 넘는 것이 CY-732 가
> 고치려는 결함이다. 판정은 부등호이고 **상한을 설계 상수에서 뽑는다** — 노드당 예산의
> 노드 비율 배다. 등호로 걸면 CY-732 를 고쳤을 때 이 시나리오가 빨개지고, 상한을 평시
> 관측에서 뽑으면 분모가 약분되어 무엇을 바꿔도 안 문다. 값은 여기와 G8.15 에 남긴다.
>
> **배수는 프로덕션이 조립하는 자리에서 받는다.** 시나리오가 예산을 직접 조립하면,
> CY-732 를 폴링 전용 분모로 고쳤을 때 이 시나리오만 낡은 값을 초록으로 단언한다. 조립은
> `PollBudgetPlanner.scaleFor` 하나가 쥔다.
>
> **이 시나리오는 뮤테이션 점수에 기여하지 않는다.** 판정은 전부 물지만 무는 뮤턴트를
> 단위 시험이 이미 전부 죽인다. 값은 세 구간을 한 순서로 잇는 데 있다.
>
> **못 재는 것 셋.** 죽은 노드의 표가 `freshness` 동안 살아 있어 실제 초과 구간은
> 하강 틱보다 길다 — 지속을 줄여 적고 있다. 회복 시 배수가 한 틱에 절반이 되는 것
> (RC4)과 관측이 오르내리며 연속이 리셋되는 경우도 안 밟는다.

### C17b — 뒤진 시계가 유지된다

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 복제본이 뒤진 채 승격한다 | 첫 회차의 신선 건수가 평시와 같다 |
| 유지 | **여러 틱을 흘려보낸다** | 신선 건수가 평시와 같다 · 크레딧이 하한에 안 박힌다 |
| 회복 | 시계가 따라잡는다 | 30초 안에 평시로 수렴 · 어느 틱도 평시의 1.2 배를 안 넘는다 |

> **C17 은 진입 순간만 잰다.** 한 회차를 걷고 끝나므로 "두 틱 뒤부터 다시 버린다" 를
> 구조적으로 못 본다. 이 시나리오가 그 구간을 연다 — 그리고 **지금은 유지에서
> 떨어진다.** D-C4 가 정해지기 전에는 통과할 수 없다.

### C22 — 레디스가 쓰기를 거부한다

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | `maxmemory` 를 지금 사용량 아래로 내린다 | 가용량 읽기가 성공한다 |
| 유지 | 쓰기만 막힌 채로 둔다 | 크레딧이 하한으로 안 떨어진다 · 읽기 실패 계수가 안 오른다 |
| 회복 | 한도를 되돌린다 | 평시로 수렴 · 첫 다섯 틱이 평시의 1.2 배 이내 |

> **읽기 경로에 쓰기를 섞으면 이 시나리오가 필요해진다.** 배선은 `noeviction` 이라
> 한도에 닿으면 쓰기만 거부되고 읽기는 멀쩡한데, 스크립트 안의 쓰기 하나가 실패하면
> 이미 읽은 것까지 통째로 사라진다. 그러면 크레딧이 깎이고, 큐가 안 빠져 메모리가
> 안 줄고, 메모리가 안 줄어 거부가 안 풀린다 — **해제 조건이 시스템 안에 없다.**
>
> 지금 가용량 읽기는 순수 읽기라 이 사고가 없다. 그 성질을 잃는 변경이 들어오면
> 이 시나리오를 같이 넣는다.

### C23 — 앞선 바닥값이 주입된다

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 기준 시각의 바닥값에 미래 값을 넣는다 (밀리초 · 한 시간 뒤 · 무한대) | 판정이 안 멎는다 |
| 유지 | 그대로 둔다 | 오염을 알리는 지표가 오른다 |
| 회복 | — | **역행 폭과 무관하게 한 틱 안에 실제 시각으로 돌아온다** |

> **영속되는 바닥값을 두면 이 시나리오가 필요해진다.** 미래 값이 한 번 들어가면
> 역행 갈래가 덮어쓰기를 안 하므로 스스로 안 낫고, 프로세스 메모리와 달리 재기동도
> 치료가 아니다. 밀리초 오입력·무한대는 읽기를 매 틱 터뜨리고, 그럴듯한 미래 값은
> 로그 한 줄 없이 크레딧을 하한에 묶는다.

### 조합 시나리오

단일 장애만 테스트하면 실제 사고를 못 잡는다. 최소 아래 조합을 포함한다.

| ID | 조합 | 노리는 것 |
|---|---|---|
| X1 | C4(리더 사망) + C1(Redis 정지) 동시 | fail-open과 큐 추월 금지가 동시에 걸릴 때 |
| X2 | C7(백엔드 복귀) + C6(게이트웨이 복귀) 동시 | 분모와 credit이 동시에 급변 — **닫힘** (CY-881) |
| X3 | C8(서킷) + 20,000 스파이크 | 억눌린 트래픽 + 회복 버스트의 최악 조합 |
| X4 | C15(지연 상승) + C6(게이트웨이 복귀) | 리더가 없는 동안 분모가 급변한다 — **닫힘** (CY-882) |

> **X4 는 분모가 리더십에 안 묶였다는 것을 못 잰다.** 시험이 관측을 직접 부르므로
> 하트비트 배선을 통째로 잘라내도 초록이다 — 그것을 잡는 것은 C6 하나다. 여기서
> 서는 것은 "리더 없는 구간을 지나 돌아온 리더가 **지금** 분모를 쓴다" 까지다. 하트비트는 리더의 일이
> 아니라 리더가 없는 구간에도 계속 센다 — 묶으면 그 구간에 분모가 얼어붙고, 돌아온
> 리더가 옛 값으로 첫 배분을 낸다. 남은 노드가 죽은 노드의 몫까지 쓰는 초과 방향이다.
>
> 리더십과 분모만 걷는다. 리스와 시도 상한은 C15 와 같은 이유로 비를 지킨 축소판이다.

> **X2 가 재는 것은 노드당 몫의 방향이다.** 분모는 증가라 즉시 반영되고 분자는
> 램프를 타므로, 둘이 같이 돌아오면 노드당 몫이 복귀 순간에 **오히려 줄어야 한다.**
> 하나씩 오면 C6·C7 이 각자 재는데, 같이 오면 그 방향을 어느 쪽도 안 본다.
>
> **돌아오는 뒷단은 새 식별자다** (R-3). 같은 이름으로 픽스처를 만들면 옛 램프
> 기록이 살아 있어 램프가 안 걸리고, 이 시나리오가 재려던 것이 통째로 사라진다 —
> 처음에 그렇게 만들었다가 빨개져서 알았다.
>
> 줄을 안 세워서 RC1·RC2·RC5 는 안 잰다.

#### X1 — 리더가 죽은 채로 레디스까지 멈춘다

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 죽은 리더가 락을 쥔 채 레디스가 멈춘다 | 재료가 안 지워졌다 · 아직 안 낡았다 |
| 유지 | 줄에 못 세우므로 **그때만** 연다 (F1 셋째 줄) | 한산한 쿠폰이 평시만큼 간다 · 줄 선 쿠폰도 열린다 · 상한이 물린다 · 초당 상한 × 걸친 창 이내 · 넘친 몫도 답을 받는다 |
| 회복 | 레디스 복귀 · 리더 재획득 | 판정 중단 0 · 회복 뒤 추월 0 · RC3 · **RC5** |

> **진입에서 전제를 못 박는다.** 레디스가 죽었다고 재료를 버리면 판정이 멎고,
> 주입 직후에 이미 낡았으면 이 시나리오가 재려는 구간(신선한 재료 + 죽은 레디스)을
> 통째로 건너뛴 것이다. 둘 다 유지 구간의 결과를 **무의미하게 만드는** 전제라
> 거기서 재야 한다 — 뒤에서 재면 이미 늦다.

> **C1 이 못 잰 두 자리를 여기서 잰다.** 저쪽은 한산한 쿠폰 하나로 재는데 그 쿠폰은
> fail-open 경로를 안 거쳐 상한이 안 물린다. 그리고 `--appendonly no` 라 끊었다
> 붙이면 줄이 통째로 사라져 RC5 를 구조적으로 못 잰다. 여기는 재료를 둘 두고
> 영속을 켜고 띄운다.

> **상한을 재려면 같은 초에 몰아쳐야 한다.** 레디스가 죽은 동안 요청 하나가 줄
> 등록 시도에 600ms 를 쓰므로, 줄 세워 보내면 40 건이 24 초에 걸쳐 초당 예산이
> 스물네 번 다시 찬다 — 상한이 멀쩡히 무는데 시험이 못 만난다.
> **대조군과도 초를 가른다.** 리미터가 노드 하나를 세는 것이라 예산을 같이 쓴다.

#### X3 — 서킷이 열린 채 억눌린 트래픽이 몰린다

| 단계 | 기대 동작 | 판정 |
|---|---|---|
| 진입 | 뒷단이 멎어 서킷이 열린다 | 주입 직후라 잴 것이 없다 |
| 유지 | 신규는 줄로 (F3) · 토큰 보유자는 프로브 자리만 먹는다 | 서킷이 열렸다 · **뒷단에 닿은 것이 프로브 허용 이내다** · 답이 200·202·429·503 안이다 · **한산한 쿠폰이 줄에 선다** · 그 쿠폰이 뒷단에 안 간다 |
| 회복 | 서킷이 닫힌다 | 답을 받는다 · 증폭 없음 · **열린 횟수 ≤ 2 (G8.12)** · 중복 수신 0. **RC1·RC4 는 못 잰다** |

> **사다리 2번이 6' 번보다 앞이지만 서킷 필터는 판정 뒤에 붙는다.** 그래서 토큰
> 보유자도 결국 서킷이 가로챈다 — 유지 구간 30 건 중 뒷단에 닿은 것은 두 건이고
> 그 둘이 half-open 프로브 자리다.
>
> **폴백이 토큰 보유자에게 1 초 밴드로 다시 오라고 답한다.** 열린 서킷 아래에서
> 그 사람들이 1 초마다 되돌아오므로, 운영값(대기 5초 · 프로브 10)에서는 half-open
> 으로 넘어가는 순간 프로브 자리가 그 재시도로 채워지고 아직 찬 뒷단이 그걸
> 떨어뜨려 곧바로 다시 열린다. **F3 이 막으려던 그림이 토큰 경로에 남아 있다** —
> F3 의 대책인 6' 번은 정의상 토큰 없는 사람만 본다.
>
> **RC4 는 이 시나리오에서 아무것도 안 잰다.** 억눌린 트래픽이 회복 순간에 풀리는 사건이
> 없다 — 배분을 껐으므로 큐가 한 번도 안 빠지고, 대신 시험이 스스로 재생한다.

#### T8.2.5 · 오류 경로의 지터와 백오프 (F7) — **완료**

- **산출물** `domain/queue/ErrorBackoff.java`, 오류 경로의 `Retry-After` 계산
- **근거** [05-data-plane.md](05-data-plane.md) 4절. 장애 중 503 을 받은 대기자
  **전원이 같은 초에 돌아온다.** 정상 경로에는 지터가 있는데 오류 경로에만
  없었고, 그때가 지터가 가장 필요한 순간이다
- **선행** 없음

**정상 경로보다 넓게 잡는다.** 오류 시점은 전원이 같으므로 분산이 더 필요하다.

1. **RED** `오류_경로의_지터가_정상_경로보다_넓다`
2. **GREEN** 오류 전용 지터 폭
3. **RED** `연속_실패에_백오프가_붙고_상한이_있다`
4. **GREEN** 지수 백오프 + 상한
5. **완료** 값 1만 개의 표준편차 ≥ 0.5s (G5.7 과 같은 자)

**단계를 요청 수로 안 센다.** 피크에서는 한 노드가 초당 수천 건을 처리하므로,
레디스가 끊긴 순간 카운터가 밀리초 만에 상한에 닿는다. 첫 실패자와 1초 뒤
실패자가 같은 안내를 받으면 백오프가 있으나 마나다. `FailureAge` 가 실패가
시작된 시각을 들고, 이어진 시간으로 단계를 낸다.

**폴링 예산이 정한 바닥을 함께 넘긴다.** 장애 구간이 곧 배수가 커져 있는
구간이라, 무시하면 하필 그때 거절받은 사람만 예산 밖으로 돌아온다. 바닥과
백오프 중 큰 쪽에서 **위로만** 흔든다 — 아래로 흔들면 그 바닥이 깨진다.

**흔들고 나서 자르지 않는다.** 자른 만큼이 상한 한 점에 쌓여 그 구간의 흔들림이
0 이 된다. 처음에 그렇게 만들었고 표본 10만에서 50.9%가 정확히 상한이었다 —
하필 장애가 길어진 구간이라 F7 이 막으려던 파도가 거기서 그대로 다시 생겼다.
천장을 상한/(1+폭)으로 낮추고, 바닥이 높아 여유가 모자라면 폭을 줄여 편다.

**성공 하나로 풀지 않는다.** 샤드 하나가 죽으면 사용자의 일부만 실패하는데,
피크에서는 성공이 초당 수천 건이라 실패 사이에 반드시 성공이 낀다. 성공마다
풀면 단계가 영원히 1 이고 백오프가 전면 장애에서만 돈다 — 현장에서 더 흔한
것은 부분 장애다. 마지막 실패로부터 유예가 지나야 푼다.

> **앞 네 계단은 안 보인다.** 조회 경로의 바닥이 30초라, 기본 2초에서 배로 느는
> 앞쪽은 바닥에 가린다. 관측되는 상승은 다섯째 계단부터다. 문서가 "2초에서
> 배로 는다" 만 적으면 프로덕션에서 한 번도 안 일어나는 동작을 말하게 된다.

> **상한에 걸린 거절은 안 바꿨다.** 그것은 장애가 아니라 노드가 밀린 배압이다.
> 같은 값으로 뭉개면 관제에서 둘을 못 가른다. 발급 경로의 거절도 아직 정상
> 경로의 폭을 쓴다 — 과부하가 길어지면 같은 파도를 만드는지 C8 에서 재고 정한다.
