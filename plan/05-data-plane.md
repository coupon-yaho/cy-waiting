# Phase 5 — Data Plane

> 요청이 실제로 지나가는 경로. 판정 필터, 큐 API, 입장 토큰, 식별자 처리.
> **여기서 지켜야 할 불변식은 "Redis 왕복 0"이다** — 판정 재료는 전부 로컬
> 스냅샷에서 읽는다. 이걸 어기면 Phase 4의 존재 이유가 사라진다.

**선행**: Phase 2, Phase 3 · **상세 수준**: 제목 + 근거 (진입 시 승격)

---

## Goal

> **판정 경로의 Redis 왕복이 0이다.**
> 그리고 게이트웨이가 발급한 토큰 검증이, 게이트웨이 필터를 타지 않는 경로까지
> 빠짐없이 걸린다.

| 통과 수치 | |
|---|---|
| 발급 판정 통과 경로의 Redis 명령 | **0건** (계측) |
| 미지 쿠폰 ID 1만 건 요청 후 Redis 키 증가 | **0건** |
| 위조·만료 토큰 (순번 조회 경로 포함) | **403** |
| `X-Member-Id` 누락·형식 오류 | **400** |
| 발급한 `Retry-After` 값 1만 개의 표준편차 | **≥ 0.5s** (F7) |

**Redis 왕복 0 을 어기면 Phase 4 의 존재 이유가 사라진다.**
상태 조회 ops 가 RPS 에 비례하는 순간 게이트웨이가 병목이 된다.

## 2. 왜 라우트별 필터인가

`GlobalFilter`가 아니라 라우트별 `GatewayFilter`로 만든다.

- 경로 매칭과 경로변수 추출은 `Path` predicate가 이미 한 일이다.
  글로벌 필터로 만들면 그 작업을 필터 안에서 다시 하게 된다
- 경로 패턴이 YAML과 코드 두 곳에 생긴다
- 폴링 요청마다 쓸데없이 패턴 매칭이 돈다

지키는 규칙 셋:

| 규칙 | 이유 |
|---|---|
| **판정 경로에서 바디를 읽지 않는다** | 파싱하면 전체를 버퍼링해야 해 메모리와 지연이 같이 터진다. **조회 경로의 응답 코얼레싱**(Phase 6 6.10)은 상한을 두고 예외로 둔다 |
| **Redis를 요청마다 치지 않는다** | 판정 재료는 전부 로컬 스냅샷 |
| **판정은 항상 일어난다** | 대기열이 꺼져 있어도 필터는 돌고 즉시 통과. 토글되는 것은 대기열 로직이지 판정 자체가 아니다 |

## 3. 식별자 — 위조를 전제로 설계한다

**이 서비스에는 로그인이 없다.** 회원가입·로그인이 과제 범위 밖이라 100만 명의
mock 회원을 쓰고, 회원 식별자와 등급을 요청 헤더(`X-Member-Id`·`X-Member-Grade`)로
받는다. **인증이 아니라 사용자 구분 수단이고, 위조가 자유롭다.**

서명 없는 클레임을 검사하는 것은 방어가 아니라 장식이다. 그래서 헤더를 신뢰하려
들지 않고, **게이트웨이가 발급한 것만 신뢰한다**로 방어선을 옮긴다.

| 무엇 | 신뢰하는가 | 근거 |
|---|---|---|
| `X-Member-Id` · `X-Member-Grade` | **아니다** | 서명이 없다. 형식만 검증한다 |
| `queueToken` · 입장 토큰 | **그렇다** | 게이트웨이가 HMAC 서명해 발급한다 (5.5.7 · 5.6) |

그래서 **남의 자리를 건드리려면 그 사람의 토큰이 필요**하고, 토큰은 추측할 수 없다.
`X-Member-Id` 를 바꿔 봐야 얻는 것이 없다.

### 3.1 함정: 순번 조회는 게이트웨이 필터를 타지 않는다

순번 조회(`GET /api/v1/coupons/{id}/queue`)는 게이트웨이가 직접 응답한다 —
폴링 트래픽을 백엔드로 흘려보내면 대기열의 존재 이유가 없어지기 때문이다.
그래서 `RouterFunctionMapping`(order -1)으로 매칭되고, 게이트웨이
`RoutePredicateHandlerMapping`(order 1)보다 먼저 잡힌다.

**결과: 게이트웨이 필터로만 검사를 붙이면 순번 조회는 검사 없이 뚫린다.**
토큰 검증을 게이트웨이 필터에만 두면 정확히 이 경로가 빠진다.

### 3.2 결정

식별자 형식 검증은 **`WebFilter`로** 구현한다 — 게이트웨이 라우트와 RouterFunction
양쪽에 모두 적용되는 유일한 계층이다.

```
WebFilter (형식 검증)  ─┬─> RouterFunctionMapping (order -1)  → 순번 조회
                        └─> RoutePredicateHandlerMapping (order 1) → Admission 필터 → 백엔드
```

- `X-Member-Id` 가 없거나 형식이 아니면 **400**. 발급 계층의 `COMMON-001` 과 맞춘다
- **주입도 제거도 하지 않는다.** 인증 계층이 없으므로 주입할 검증된 subject 가 없고,
  제거하면 회원 식별자가 통째로 사라진다
- 자리를 다루는 요청은 **게이트웨이가 발급한 토큰**으로 대상을 특정한다.
  위조·만료 토큰은 **403**

`401` 은 쓰지 않는다. 인증 체계가 없으므로 "자격 증명을 다시 제시하라"가 성립하지 않는다.

**상위 PRD 12절은 사전 발급 HS256 JWT 를 전제하지만, 발급 계층이 그것 없이
구현됐다** — API 명세 v2.0 에 `Authorization` 헤더가 없고 `X-Member-Id` 가 필수다.
게이트웨이만 JWT 를 요구하면 계약이 갈린다.
**구현된 계약을 정본으로 삼는다** → [90-decisions.md](90-decisions.md) D-A1

## 4. F7 — 고정 `Retry-After`는 회복 시 thundering herd를 만든다

순번 조회가 실패하면 `503 + Retry-After: 2`를 준다. 장애 중 이 응답을 받은
대기자 **전원이 정확히 2초 후 동시에 재시도**한다.

```
Redis 3초 단절
  → 대기자 20,000명이 503 + Retry-After: 2 수신
  → 복구 직후 2초 시점에 20,000 요청 동시 도착
  → 회복이 곧 2차 장애
```

정상 경로의 `nextPollMs`에는 지터가 있는데(폴링 간격 정책), **에러 경로에만
지터가 없었다.** 정확히 지터가 가장 필요한 순간이다.

**결정**:

- 에러 경로 `Retry-After`에도 지터를 적용한다 (기본 2초 ± 50%)
- 지터 폭을 정상 경로(±15%)보다 **넓게** 잡는다 — 에러 시점이 전원 동일하므로
  분산이 더 필요하다
- 연속 실패 시 지수 백오프 (상한 있음)

RC4(회복 버스트 ≤ 1.2×)를 만족시키는 주 수단이다.

### 5.7 남용 방지 리미터 (S-1·S-2)

**한 사용자가 노드 예산을 다 먹을 수 있다.** tier 1 은 한산한 쿠폰별,
tier 2 는 노드 전역이라 **사용자 단위 상한이 어디에도 없다.** 큐가 결국 막긴 하지만, 정상 사용자를 전부 큐로
밀어넣는 것 자체가 공격 성공이다 — R1 이 공격 한 명에게 무너진다.

**필터 체인에서는 인증(5.2) 바로 뒤, 판정(5.3) 앞에 둔다.** 판정에 들어가면 남용 요청이 tier2 예산을 만지게 되고,
큐에 넣으면 공격자가 자리를 차지한다. **여기서 `429` 로 끊는다.**

**폴링 경로에는 다르게 건다.** 게이트웨이가 `nextPollMs` 로 **폴링을 지시해놓고**
그 폴링을 남용으로 막으면 정상 대기자가 끊긴다. 발급 경로는 좁게, 폴링 경로는
**지시한 간격에서 역산한 값**으로 느슨하게 잡는다.

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 5.7.1 | `memberId` 기준 초당 상한 — 초과 시 **429 `RATE_LIMITED`** (큐에 넣지 않는다) | 한 사용자가 노드 예산을 독식하지 못한다 |
| 5.7.2 | **클라이언트 IP 기준 상한**을 함께 건다 | `memberId` 를 바꿔가며 우회하는 것을 막는다 |
| 5.7.3 | IP 는 **신뢰하는 프록시 홉만** 인정 (`X-Forwarded-For` 맨 끝) | 헤더를 채워 넣어 남의 IP 로 위장하지 못한다 |
| 5.7.4 | 두 리미터의 맵에 **크기 상한과 축출** (T2.2.3 재사용) | `memberId` 를 무한히 바꿔도 메모리가 유계 |
| 5.7.5 | `429` 에 `Retry-After` + 지터 | 동기화된 재시도를 만들지 않는다 (F7) |
| 5.7.6 | 차단을 지표로 (사유·키 종류별) | 정상 사용자가 걸리는지 본다 |
| 5.7.7 | **발급 경로와 폴링 경로에 다른 상한** | `nextPollMs` 를 지킨 클라이언트가 429 를 받지 않는다 |
| 5.7.8 | `pollScale` 이 커져 간격이 늘면 폴링 상한도 **같이 내려간다** | 지시와 상한이 어긋나지 않는다 |

> **`memberId` 기준만으로는 부족하다.** 로그인·회원가입이 없어 `X-Member-Id` 를 바꾸는
> 비용이 0 이라, 사용자 단위 상한은 우회된다. IP 상한이 실질적인 방어고
> `memberId` 상한은 **정상 클라이언트의 폭주(재시도 루프·버그)를 잡는 쪽**에 가깝다.
> 둘의 역할이 다르므로 둘 다 둔다.
>
> IP 는 NAT 뒤에서 공유되므로 **상한을 사용자 상한보다 넉넉히** 잡는다. 좁게 잡으면
> 같은 회사·같은 통신사 사용자가 서로를 막는다.
