# Phase 6 — Protection

**선행**: Phase 5 · **상세 수준**: 제목 + 근거 (6.5·6.6 은 완전 명세)

---

## Goal

> **요청 경로가 뒷단 장애에 버티고, 그것이 실측으로 증명된다.**

| 통과 수치 | |
|---|---|
| 게이트웨이 오버헤드 p99 (백엔드 제외) | **< 5ms** |
| 동시 조회 1만 건이 뒷단에 도달하는 수 | **1건** |
| 한산한 쿠폰의 큐 등록 (실부하) | **0건** |
| 뒷단이 멎었을 때 게이트웨이 | **물리지 않는다** |
| 쿠폰 2,000개에서 격벽 카운터 메모리 | **유계** |
| 종료 중 5xx | **0건** |

---

## 1. 왜 보호와 측정을 같이 두는가

**보호 장치는 부하를 걸어야 검증된다.** 격벽이 실제로 막는지, 타임아웃이 걸리는지,
드레인이 되는지는 전부 부하가 있어야 잰다. 둘을 다른 페이즈에 두면 앞 페이즈가
자기 게이트를 닫을 수 없다.

그리고 **타임아웃이 없으면 격벽이 무의미하다.** 자리를 잡은 요청이 영원히 안 놓으면
격벽이 가득 찬 채로 굳는다. 서킷도 같은 이유로 타임아웃에 기댄다 — 실패를 세려면
실패로 판정되는 시각이 있어야 한다. 셋은 한 덩어리다.

| 6.1.2 | **`/fallback/issue` 핸들러 구현** | 서킷 오픈 시 404가 아닌 503 |
| 6.1.3 | 503 + `Retry-After` + 지터 | |

> 6.1.2 가 없으면 서킷이 열리는 순간 사용자는 404를 받는다.
> 장애 시에만 드러나므로 일반 테스트로는 잡히지 않는다.

**설정값** — 값이 없으면 `G8.12`(half-open 회복 시도 ≤ 2회)를 판정할 수 없다.

| 설정 | 기본값 | 근거 |
|---|---|---|
| `slidingWindowType` | **TIME_BASED** | 100K RPS 에서 건수 창 100은 수 ms 분량이다. 순간 변동에 열린다 |
| `slidingWindowSize` | **10s** | |
| `minimumNumberOfCalls` | **20** | 표본이 적을 때 열지 않는다 |
| `failureRateThreshold` | **50%** | |
| **`slowCallDurationThreshold`** | **타임아웃의 50%** | 아래 참조 |
| **`slowCallRateThreshold`** | **50%** | |
| `waitDurationInOpenState` | **5s** | 지연이 걷히면 늦어도 2번째 시도에 닫힌다 → `G8.12` |
| `permittedNumberOfCallsInHalfOpenState` | **10** | 서킷이 회복을 판정할 표본 수 |

**half-open 에 트래픽이 몰리는 것을 막는 것은 이 설정이 아니다.** 이 값은 서킷이
회복을 판정할 표본 수일 뿐이고, 실제 유입 억제는 **판정 쪽**에서 한다 —
`HALF_OPEN` 이면 유효 credit 을 소량으로 제한해 시험 트래픽만 흘린다
([08-resilience.md](08-resilience.md) F3). 둘은 층이 다르고 **둘 다 필요하다.**
판정 억제가 없으면 half-open 전환 순간 도착한 트래픽 전량이 약한 백엔드를 재포화시킨다.

**타임아웃만으로는 느려진 인스턴스를 못 잡는다.** 타임아웃을 3초로 잡으면
2.9초로 느려진 인스턴스는 **전부 성공으로 집계되어 서킷이 안 열린다.** 그동안
격벽이 먼저 굳는다 — `6.3` 이 *"초당 100건이어도 각각 10초 걸리면 동시 1,000건"*
이라며 격벽을 정당화한 논리가 **서킷에도 그대로 적용된다.**

그래서 `slowCallDurationThreshold` 를 타임아웃보다 낮게 두어 **타임아웃이 쌓이기
전에 연다.** `C8` 이 "백엔드 전체 지연" 시나리오이므로, 이 장치가 없으면 그
시나리오에서 타임아웃 임계를 넘길 때까지 아무 일도 일어나지 않는다.

**서킷은 인스턴스별이다** (R-10). 백엔드 전체를 하나로 묶으면 한 대가 죽어도 전
트래픽이 막힌다. 인스턴스별이어야 로드밸런서가 그 한 대만 빼고 나머지로 흘린다.

**그래서 판정이 보는 값도 바뀐다.** "서킷이 열렸는가"가 아니라 **"살아 있는 인스턴스
비율"** 이다 (B-7). 10대 중 3대가 열렸으면 통과 상한도 그만큼 줄어야 한다 — 안 그러면
남은 7대에 10대분이 몰린다.

### 6.2 뒷단 요청 타임아웃

**격벽은 타임아웃 없이는 무의미하다.** 자리를 잡은 요청이 영원히 안 놓으면 격벽이
가득 찬 채로 굳는다. 서킷도 같은 이유로 타임아웃에 기댄다 — 실패를 세려면 실패로
판정되는 시각이 있어야 한다.

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 6.2.1 | 뒷단 프록시 응답 타임아웃 | 뒷단이 멎어도 게이트웨이가 물리지 않는다 |
| 6.2.2 | 타임아웃을 **서킷의 실패로 집계** | 멎은 인스턴스의 서킷이 열린다 |
| 6.2.3 | 타임아웃 시 격벽·in-flight 자리 반납 | 누수 0 |
| 6.2.4 | 타임아웃 응답은 504 가 아니라 **503 + `Retry-After`** | 대기열 문맥에서는 재시도 안내가 맞다 |

> 타임아웃 값은 뒷단 p99 에서 정한다. 너무 짧으면 정상 요청을 죽이고, 너무 길면
> 격벽이 굳는다. 6.6 부하 하네스로 재고 확정한다.

### 6.3 격벽

레이트 리밋으로는 못 막는 것이 있다. **초당 100건이어도 각각 10초 걸리면 동시 1,000건**
이다. 세는 단위가 다르다 — 리미터는 초당 건수, 격벽은 동시 건수.

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 6.3.1 | **인스턴스별 동시 요청 상한** | 느려진 한 대가 커넥션을 다 붙잡지 못한다 |
| 6.3.2 | **쿠폰별 동시 요청 상한** | 핫 쿠폰이 콜드 쿠폰의 통로를 막지 못한다 |
| 6.3.3 | 상한값은 배분된 크레딧에서 구한다 | 크레딧이 줄면 격벽도 같이 조여진다 |
| 6.3.4 | 격벽이 꽉 차면 503 + `Retry-After` + 지터 | 서킷 오픈과 같은 응답 형태 |
| 6.3.5 | 쿠폰별 카운터는 **리미터의 맵과 축출을 함께 쓴다** | 쿠폰 2,000개에서 메모리 유계 |
| 6.3.6 | 격벽 포화를 지표로 노출 | 어느 쿠폰·인스턴스가 막혔는지 보인다 |

**쿠폰 2,000개가 문제되지 않는 이유**는 리미터가 이미 쿠폰별 카운터를 들고 있어서다.
격벽은 거기에 "초당 몇 건" 대신 "동시 몇 건"을 세는 값을 얹는다. 클라이언트 입력으로
맵이 무한 증식하는 것도 이미 막혀 있다 — **스냅샷에 없는 쿠폰은 404** (B-8).

### 6.4 무중단 종료

배포로 노드가 내려갈 때 **진행 중인 요청을 죽이지 않고 빠져나가야 한다.** 이게 없으면
롤링 배포마다 사용자가 오류를 본다.

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 6.4.1 | 종료 신호를 받으면 **readiness 를 먼저 503 으로** | LB 가 뺄 기회를 준다 |
| 6.4.2 | **LB 가 뺄 때까지 기다린 뒤** 드레인을 시작한다 | 대기 없이 드레인하면 유입이 남아 5xx 가 샌다 |
| 6.4.3 | 진행 중인 요청이 끝날 때까지 기다린다 (상한 있음) | 종료 중 5xx 0 |
| 6.4.4 | **`gw:instances` 에서 자신을 지운다** | 남은 노드의 몫이 곧바로 늘어난다 |
| 6.4.5 | 상한을 넘으면 강제 종료하고 그 사실을 로그로 | 영원히 안 죽는 노드가 없다 |

**순서와 값**

```
readiness 503  ──[ LB 제외 대기 ]──▶  드레인  ──[ 상한 ]──▶  종료
                   앞단 LB 의 체크 주기 × 실패 횟수 + 여유
```

| 설정 | 기본값 | 근거 |
|---|---|---|
| LB 제외 대기 | **6s** | 앞단 체크 `inter 2s` × `fall 2` = 4s 에 여유 2s |
| `spring.lifecycle.timeout-per-shutdown-phase` | **30s** | 드레인 상한 (6.4.5) |

**대기를 안 넣으면 `종료 중 5xx 0` 이 깨진다.** readiness 를 내려도 LB 가 알아채기
전까지는 계속 보내기 때문이다. 이 값은 앞단 LB 설정과 **짝**이므로 한쪽만 바꾸면
어긋난다.

**두 값을 더한 것이 종료 예산이다.** LB 제외 대기는 `ContextClosedEvent` 리스너에서
막는 것이라 `timeout-per-shutdown-phase` 의 **밖**이다 — 그 상한은 이벤트를 다 돌린
뒤의 단계별 정지에만 걸린다. 그래서 예산은 `6s + 30s = 36s` 이고, 오케스트레이터의
`terminationGracePeriodSeconds` 가 이보다 커야 한다. 기본값 30s 를 그대로 두면 드레인
도중에 강제 종료되어 6.4.3 이 매 배포마다 깨진다. 프레임워크가 못 끊는 구간이므로
대기 값의 상한은 코드가 건다 (`DrainWait.MAX_WAIT`).

> 6.4.3 이 빠지면 죽은 노드가 `N` 에 계속 잡혀 **남은 노드가 자기 몫을 못 쓴다.**
> 노드 수 감소를 지연 반영하는 결정(C-4)은 노드가 **말없이** 사라질 때의 안전장치지,
> 정상 종료까지 지연시키라는 뜻이 아니다.

### 6.8 운영 튜너블 (P-1)

**장애 중에 배포 없이 되돌릴 수 있어야 롤백 전략이 성립한다.** 스냅샷은 이미 매 틱
전 노드에 도달하므로, 설정 서버를 새로 붙이지 않고 그 경로를 쓴다 (C-6 과 같은 배선).

**운영자가 바꿀 자리가 있어야 한다.** 스냅샷은 전파 수단이지 입력이 아니다.
`gw:tunables` 키를 사람이 고치고, 리더가 매 틱 읽어 스냅샷에 실어 퍼뜨린다.

```
사람 → gw:tunables (Redis, JSON) → 리더가 틱마다 읽음 → 스냅샷 메타 → 전 노드
```

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 6.8.1 | `gw:tunables` 키 정의 (JSON) — 격벽 상한 배수·뒷단 타임아웃·**서킷 임계(느린 호출 포함)**·`idle-credit-ratio` | 키가 없으면 전부 기본값 |
| 6.8.2 | 리더가 매 틱 읽어 **스냅샷 메타에 실어 보낸다** | 값을 바꾸면 다음 틱에 전 노드가 따른다 |
| 6.8.3 | **범위 검사** — 벗어나거나 파싱 실패면 기본값으로 떨어지고 경고 | 잘못된 값이 게이트웨이를 멈추지 못한다 |
| 6.8.4 | 적용 중인 값과 **마지막 변경 시각**을 지표로 노출 | 대시보드에서 지금 무엇이 걸려 있는지 보인다 |
| 6.8.6 | **불변 레코드를 통째로 교체**한다 (필드별 `volatile` 금지) | 낡은 타임아웃 + 새 격벽 상한 같은 조합이 나오지 않는다 |
| **6.8.7** | 뒷단 타임아웃을 바꾸면 **`slowCallDurationThreshold` 도 같이** 재계산된다 | 타임아웃보다 느린 임계가 남지 않는다 |
| 6.8.5 | 값 변경을 감사 로그로 (이전값 → 새값) | 장애 후 무엇을 건드렸는지 되짚을 수 있다 |

> **값 하나가 전 노드에 즉시 퍼진다 — 잘못된 값도 그렇다.** 6.8.3 이 선택이 아닌 이유다.
> 필드별 `volatile` 로 두면 읽는 순간마다 조합이 갈려 **존재한 적 없는 설정**으로
> 판정한다. 스냅샷을 통째로 바꾸는 것(Phase 4)과 같은 이유다 — `JS-5` 의 가변 필드
> 예외를 쓰지 않고 교체로 푼다.
>
> 튜너블은 **보호 장치를 느슨하게 하는 방향으로만** 열어둔다. 조이는 방향은 배포로
> 한다 — 장애 중에 급히 조이다 정상 트래픽을 죽이는 것이 더 흔하다.

### 6.9 알람 규칙 (P-2)

**증상에만 건다.** 원인마다 걸면 장애 하나가 열 개를 울리고, 그러면 아무도 안 본다.

**게이트웨이가 실제로 볼 수 있는 것에만 건다.** 초과 발급 여부는 재고를 가진
발급 계층만 안다 (비목표: 게이트웨이는 재고를 차감하지 않는다). 그래서 불변식 2는
**게이트웨이 쪽 선행 지표**로 대신 감시한다.

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 6.9.1 | 호출 — **틱 배분 합계 > `globalCredit`** (불변식 2의 선행 지표) · **순위 역행 > 0** | 둘 다 게이트웨이가 스스로 계산하는 값이라 관측 가능하다 |
| 6.9.2 | SLO 소진율 — 5분·1시간 **이중 창** | 순간 스파이크로 울리지 않고, 느린 소진도 놓치지 않는다 |
| 6.9.3 | 티켓 규칙 — `dataStale` 5분 지속 · 서킷 오픈 지속 · 큐 18,000 초과 | 자동 복구 여지가 있는 것은 호출하지 않는다 |
| 6.9.4 | 개별 노드 `fetchStale` 은 **알람을 걸지 않는다** 는 회귀 테스트 | LB 가 이미 뺀다. 사람이 할 일이 없으면 알리지 않는다 |
| 6.9.5 | 규칙 파일을 `promtool check rules` 로 검증 | 문법 오류가 배포되지 않는다 |

> 임계값(18,000)은 R4 의 한계 20,000 에서 역산한 것이다. 한계에 닿은 뒤 알리면 늦다.
>
> **초과 발급 자체는 발급 계층이 알린다.** 게이트웨이 알람이 조용해도 그쪽이 울릴 수
> 있고, 그 경우 원인이 배분에 있는지는 6.9.1 의 선행 지표로 가른다.

### 6.10 조회 코얼레싱 (B-15·B-16)

**발급은 게이트웨이가 막아주는데 조회는 그대로 통과한다.** 오픈 순간 사용자는
큐에 서기 전에 쿠폰 페이지를 먼저 연다 — 100K RPS 가 뒷단에 꽂힌다.

그리고 이건 `R2` 까지 갉아먹는다. 인스턴스가 조회로 포화되면 `credits` 를 낮게
보고하고, **발급 유입까지 같이 조여진다.**

```
100K RPS · 노드 10대 · TTL 200ms
  → 노드당 키 하나에 초당 5회 → 뒷단 조회 50 RPS
```

#### 두 겹인 이유

**코얼레싱은 동시에 도착한 것만 모은다.** 1ms 차이로 어긋난 요청은 각각 나간다.
짧은 TTL 을 얹어야 연속 도착까지 흡수된다. 반대로 캐시만 두면 **첫 요청이 나가는
동안 도착한 전부가 miss** 로 뒷단에 몰린다 — 캐시가 비는 순간이 가장 위험하다.

| ID | 작업 | 주요 테스트 |
|---|---|---|
| 6.10.1 | 인플라이트 싱글플라이트 — 같은 키는 **뒷단 호출 1회** | 동시 1만 요청 → 뒷단 도달 1건 |
| 6.10.2 | 마이크로 캐시 (TTL 200~500ms, 라우트별 설정) | TTL 안의 연속 요청이 뒷단에 안 간다 |
| 6.10.3 | **화이트리스트로만 켠다** — 기본 꺼짐 | 설정에 없는 경로는 그대로 프록시 |
| 6.10.4 | 키 = 경로 + 쿼리 + `Vary` 가 지목한 헤더 | 언어가 다르면 다른 응답을 받는다 |
| 6.10.5 | **개인화 응답이면 즉시 실패**시키는 회귀 검사 | `Authorization`·`X-Member-Id` 가 응답을 가르면 검출 |
| 6.10.6 | 상한 넘는 응답은 **버퍼링하지 않고 그대로 흘린다** | 큰 응답이 메모리를 먹지 않는다 |
| 6.10.7 | 5xx·타임아웃은 캐시하지 않는다 | 장애 응답이 TTL 동안 고정되지 않는다 |
| 6.10.8 | 상류 `Cache-Control: no-store` 를 존중 | 뒷단이 막으면 우리도 안 모은다 |
| 6.10.9 | 캐시 맵 크기 상한·축출 | 키를 무한히 바꿔도 메모리 유계 |
| 6.10.10 | 적중률·병합 배수·뒷단 조회 RPS 를 지표로 | 효과가 수치로 보인다 |

> **`6.10.5` 가 이 기능의 안전장치다.** 지금은 조회 응답에 개인화가 없다(확인함).
> 하지만 나중에 "내가 발급받았는지" 필드가 하나 붙는 순간 **남의 응답을 받는다.**
> 사람 리뷰로 막을 수 없으니 회귀 테스트로 못박는다.
>
> **바디 버퍼링은 판정 경로의 금지 규칙(Phase 5 2절)에 대한 의도적 예외다.**
> 조회 라우트에만, 크기 상한 안에서만 한다. 넘으면 버퍼링을 포기하고 흘린다 —
> 보호 장치가 메모리 사고의 원인이 되면 안 된다.

```yaml
waiting:
  coalescing:
    enabled: true
    max-body: 256KB          # 넘으면 그대로 프록시
    routes:
      - path: /api/v1/coupons          ttl: 300ms   key: [path, query]
      - path: /api/v1/coupons/{id}     ttl: 200ms   key: [path]
```

> 재고 신선도는 문제가 안 된다. 판정이 이미 최대 1.5초 낡은 스냅샷을 쓰므로
> 200ms 캐시가 그보다 훨씬 신선하다.
